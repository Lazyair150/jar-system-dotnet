# 10 模块边界与规范化升级路线（多模块职责分离，而非围绕核心打补丁）

> 用途：回答"这个系统下一阶段该怎么升级"——**不是**再围绕 `JarSystem` 加功能，而是让每个模块采用它所在领域的**完整规范形态**，
> 模块之间只通过**显式产物**（契约）耦合，从而每块都能独立整体升级。
> 本文所有判断都带证据（文件:行）或官方出处链接。研究回执见 §7。
> **新会话请先读 `00_从这里继续.md`**，本文是按需读的路线文档。

## 1. 诊断：为什么"每次改动都要回到核心去配合"

### 1.1 最硬的一条证据：整个解决方案的外部依赖是 0

| 项目 | PackageReference |
|---|---|
| `src/JarSystem.Core` | **无**（仅 `net10.0` + `ImplicitUsings` + `Nullable`） |
| `src/JarSystem.Web` | **无**（只引 Core + ASP.NET Core 共享框架） |
| `test/JarSystem.Test` | **无**（`OutputType=Exe` 的普通控制台程序） |
| `test/StrategyExperiment` | **无** |

零依赖对**核心**是优点（可移植到 Godot/Unity，见 `问题/作为游戏系统模块的评价.txt`），
但对**周边**意味着：每个周边领域都被手写了一个近似品 —— 而近似品永远长不成"完整形态"，所以每加一个需求，都要回到核心去配合它。

### 1.2 周边模块的手写清单（与"该领域的完整体"对照）

| 周边模块 | 现状（手写近似品，含位置） | 该领域的完整形态 |
|---|---|---|
| 依赖注入 | 手写构造注入 + `Bootstrap/SystemBootstrapper.cs` | `Microsoft.Extensions.DependencyInjection`（**只在宿主层**） |
| 日志 | 自定义 `ISystemLog` + `Services/ConsoleSystemLog.cs` | `Microsoft.Extensions.Logging`（结构化 + `LoggerMessage` 源生成） |
| 测试框架 | `test/JarSystem.Test/Program.cs`（699 行 top-level + 自写 `Run(name, scenario)`） | xUnit v3 + Microsoft.Testing.Platform |
| 不变量/随机测试 | 手写 `2000 随机 + 3000 容量` 循环 | **性质测试**：FsCheck（生成器 + 收缩 + 可复现 Replay） |
| 契约验证 | 手写反射 dump（**现为 223 行**文本）+ 人工基线 + `fc` | **JSON Schema 产物** + 快照测试（Verify） |
| WS 协议 | 手写 `WebSocketHub` + `switch` 18 命令 + 匿名对象 JSON | 契约单一事实源（见 §3.2；**不建议**换传输层） |
| 序列化 | 手写 DTO + `[JsonPropertyName]`（无 schema 产物，靠人读文档） | `System.Text.Json` 源生成 + `JsonSchemaExporter`（.NET 9+ 官方） |
| 前端 | 原生 JS（无构建、无类型）+ 手写 Canvas + 重复形状清单 + 按液体硬编码 CSS（`.jar-full-wine`/`.jar-full-honey`） | Vite + TypeScript + 类型由 schema 生成 |
| 配置/数据驱动 | 形状/液体/模板**硬编码 C#**（`Config/Rules.cs`），而 `appsettings.json` 是空模板 | `Microsoft.Extensions.Configuration` + Options 校验 + 外部规则表 |
| 后台任务 | 手写 `System.Threading.Timer` ×2（`CommandDispatcher`） | `BackgroundService` + `PeriodicTimer` |
| 仓库级约定 | **无** `Directory.Build.props`/`Directory.Packages.props`/`global.json`/`.editorconfig`/`.gitignore`/CI | 中央构建基线 + CI 作为"整体升级"闸门 |

### 1.3 已经发生的真实损害（不是理论风险）

| # | 事实（已核实） | 含义 |
|---|---|---|
| 1 | **契约漂移已经发生且被手工补丁掩盖**：`wwwroot/js/app.js:19-33` 在收到 `state/tick/init` 后，把客户端缓存的旧 `feasibilityResult` **整体覆盖**服务端新值（`:23`），并自行从 `directSatisfactions.length` 推导 `directCount`（`:25-30`） | 前端存在一份**没有规格、没有测试**的兼容层；今天它是死代码还是"其实在救命"，谁都说不清——因为契约没有可执行规格（`directCount` 在 `FeasibilityStateDto:75` 里是有的） |
| 2 | **同一份协议在仓库里有两套版本**：`app.js` 用 `orderId`，`js/app_original.js` 与 `重构报告/_backup/阶段0/...` 里是 `orderIndex` | 没有版本控制 + 没有契约产物 ⇒ 历史协议副本混在源码树里 |
| 3 | **前端没有任何断线恢复**：`app.js:1` 只有 `ws.onopen`/`ws.onmessage`，全仓库无 `onclose`/`onerror`/重连（grep 实证） | 后端一重启，页面永久静默失效 |
| 4 | **存在未被使用的第二条序列化路径**：`Web/Program.cs:23` 的 `MapGet("/api/state")` 直接返回 `GetState()`，而前端从不调用它（grep 无 `fetch`） | 两条路径各自序列化同一 DTO，将来必分叉 |
| 5 | **性质测试的核心逻辑手写在测试里**（2000/3000 循环 + 不变量断言），且真正的随机源在 `src` 侧不可复现：`Executor/JarStrategies.cs`（`RandomJarSelection`）、`Services/WorkshopService.cs:32`、`Services/OrderService.cs:33` 都是裸 `new Random()` | "跑了很多随机用例" ≠ 可复现的反例最小化；出问题无法重放 |
| 6 | **前端内联 `onclick` 与 ES module 互斥**：`app.js` 用字符串拼 HTML 且内联 `onclick="toggleSelect(this,'base')"`（`:262`）、`onclick="this.parentElement.remove()"`（`:245`）、`editCapacity(${index})` 等 | 直接上 `type="module"`（Vite/TS 前提）会**当场全坏**；迁移顺序被这一条约束 |
| 7 | **没有版本控制痕迹**：读 `.git/HEAD` 失败，全仓库无 `.gitignore`，`bin/`、`obj/`、`_backup/` 全部在树内（glob 实证） | "每个模块独立升级"的前提是可回滚的版本控制 —— **这条请你确认**（若确实没有 git，它是 §5 P0 的第一项） |

### 1.4 结论（一句话）

**问题不是"核心太中心"，而是"边界没有被表达成产物"。**
现在核心与客户端之间的边界是一堆隐式约定（键名、camelCase、18 个命令字符串、前端重复的形状清单、手写的基线文本），
所以任何改动都只能"回到核心去配合它"，周边永远无法独立成完整模块。

## 2. 目标架构：契约即边界（contract-first）

```
                    ┌───────────────────────────────┐
                    │  JarSystem.Core  （零依赖核心） │  ← 规则/求解/执行，唯一不可替代的部分
                    │  Domain · Solver · Executor    │
                    └───────────────┬───────────────┘
                                    │  产出：JSON Schema（生成物，进仓库）
                                    ▼
        ┌──────────────────────────────────────────────────┐
        │  contracts/  （模块间的唯一接口产物，带版本）        │
        │  state.schema.json · commands.schema.json · …      │
        └───────┬───────────────────────┬──────────────────┘
                │ 生成类型               │ 生成类型
                ▼                       ▼
      ┌──────────────────┐   ┌──────────────────────┐
      │ Web 宿主（DI/日志）│   │ Godot 宿主 / CLI     │
      │ + TS 客户端（Vite）│   │ （引用 Core 程序集）  │
      └──────────────────┘   └──────────────────────┘
                │                       │
                └──────┬────────────────┘
                       ▼
        ┌──────────────────────────────────────────┐
        │ 验证：xUnit v3 + FsCheck（性质）+ Verify  │
        │ （消费同一份 schema，独立于任何宿主）        │
        └──────────────────────────────────────────┘
```

三条规则：
1. **核心零依赖不变**：DI/日志/配置/宿主能力只在宿主层（官方"库作者"模式：核心给默认值，宿主可覆盖）。
2. **契约是产物不是约定**：schema 由代码生成、进仓库、版本化；客户端类型由 schema 生成 ⇒ 后端改契约，客户端**编译期**报错。
3. **每块可独立整体升级**：只要 schema 不变，宿主、前端、测试、文档可以各自换代。

## 3. 四个关键决策（含理由与出处）

### 3.1 传输层：**保留裸 WebSocket，不迁 SignalR**

- 官方 WebSockets 文档确实写"多数应用推荐 SignalR"，但**同一批官方 Native AOT 兼容表**把 `WebSockets` 标为完全支持、`SignalR` 仅 partial——本项目正走零依赖 + 可能 AOT 的路线。
- SignalR 的卖点在本场景全是空集：传输降级（本地浏览器必支持 WS）、backplane/群组（单用户）、`IHubContext`（已有 `IWebSocketSink` 做依赖倒置）。
- 代价却是实打实的：Hub 协议把消息包成"方法名 + 参数数组"，与现有 `{type, data}` 一元结构不同构，9 类消息要全部重映射 ⇒ 违反"契约逐字节不变"。
- **缺口补法**：前端补断线重连 / `onerror`（约 20 行原生 WS，不必换栈）。
- 出处：[WebSockets in ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/websockets?view=aspnetcore-10.0)、[Native AOT 支持表](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/native-aot)

### 3.2 契约：**JSON Schema 成为仓库产物**（本路线的中心）

- `JsonSchemaExporter` 是 **.NET 9 起的官方 API**（`JsonSerializerOptions.GetJsonSchemaAsNode(Type)`），**不需要**引入 JsonSchema.NET/NJsonSchema。
- 现状的 **223 行**文本基线（`重构报告/_contract/state_keys.txt`）有两个固有缺陷：① 依赖一个固定场景的数据；② 时间戳要人工打 `<volatile>`。**schema 基线没有这两个问题**（结构而非取值）。
- 附加收益：**词汇表下发**。前端 `js/constants.js` 只有 2 行（`SHAPES` 8 个 / `LIQUIDS` 2 个），为它上代码生成不划算——正确做法是后端在 `init`/`state` 里下发形状/液体清单，前端删掉这份副本（同一份清单现在有 3 处：`Config/Constants.cs:7-8`、`js/constants.js`、CSS 类名）。
- **真正需要类型的是 20 处 `ws.send({type, data:{...}})` 的字面量键名**（`producerName`/`shape`/`rate`/`orderId`/`index`）——那才是"拼错即炸"的地方。
- 出处：[Extract JSON schema（.NET 9+）](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/extract-schema)、[源生成](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/source-generation)

### 3.3 宿主：**核心零依赖，DI/日志/配置只在宿主层**

- 官方"库作者 Options 指南"的标准模式：**库给默认值，宿主可覆盖**。把 `SystemBootstrapper` 的手写装配降级为 `JarSystemOptions` 的 `Configure(默认值)`，于是 `new JarSystem()` 仍走同一套默认（无 DI 也能用），DI 只是第二条入口。
- 核心不引 `Microsoft.Extensions.Hosting`，最多引 `DependencyInjection.Abstractions` / `Logging.Abstractions`（**是否引这两个抽象本身就是决策**，见 §6）。
- 规则表外置（`config/rules.json` + schema）用官方 Configuration + Options 三层校验（`ValidateDataAnnotations` → `IValidateOptions<T>` → `ValidateOnStart`）。⚠️ **`Constants` 里的 `OrderPhase`/`CheckMethod`/`SwitchCaseType` 等字符串是输出契约，不要配置化**。
- 出处：[库作者 Options 指南](https://learn.microsoft.com/dotnet/core/extensions/options-library-authors)、[Options 校验](https://learn.microsoft.com/dotnet/core/extensions/options)、[泛型主机](https://learn.microsoft.com/dotnet/core/extensions/generic-host)、[托管服务 + PeriodicTimer](https://learn.microsoft.com/aspnet/core/fundamentals/host/hosted-services)

### 3.4 测试：**xUnit v3 + MTP + FsCheck（性质）+ Verify（快照）**，旧 runner 保留为"基线守护"

- 平台：.NET 10 起 `dotnet test` 原生支持 MTP（`global.json` 写 `{"test":{"runner":"Microsoft.Testing.Platform"}}`）；**同一解决方案不要混用 VSTest 与 MTP**。推荐 xUnit v3（项目即 Exe，内置 MTP），本项目纯托管，不需要 AOT 包。
- 性质测试：FsCheck 3.4（`Prop.ForAll`、`Configuration.Quick.WithMaxTest(n).WithReplay(...)`、`FsCheck.Xunit.v3` 的 `[Property(MaxTest=…, Replay=…)]`）。**2000/3000 用例不是"多跑几次"，本质是性质测试**——迁移的正确姿势是：不变量各写一个 Property，失败自动 shrink 出最小反例 + Replay 种子可重放。
- 状态机测试：`FsCheck.Experimental.Machine<Actual,Model>`（官方标 experimental）**双轨**搭配差分测试（领域模型作 oracle）。
- 迁移安全阀：**保留旧 runner 原样**，并加一个测试断言它仍输出 `0 bugs / 2000 random + 0 bugs / 3000 capacity + 20 deterministic` —— 基线不丢，新体系并行生长。
- **不迁**：`--dump-contract` 契约快照（它是被守护的 CLI 契约 + 重构 diff 工具）、`StrategyExperiment` 的报告路径与结论。StrategyExperiment 属"参数扫描 + 报告"而非微基准，**不要**上 BenchmarkDotNet。
- 出处：[测试平台对比](https://learn.microsoft.com/en-us/dotnet/core/testing/test-platforms-overview)、[xUnit v3 入门](https://xunit.net/docs/getting-started/v3/getting-started)、[xUnit v3 + MTP](https://xunit.net/docs/getting-started/v3/microsoft-testing-platform)、[FsCheck QuickStart](https://fscheck.github.io/FsCheck/QuickStart.html)、[FsCheck 状态机](https://fscheck.github.io/FsCheck/StatefulTestingNew.html)、[Verify](https://github.com/VerifyTests/Verify)

### 3.5 核心算法：**保留自研求解器**，只补三样（研究结论）

先给它一个规范定位：本系统的主体是**经典规划（classical planning）的状态空间搜索**——工作台容量是 PDDL 的数值流（numeric fluents），"标记派生转换能力"是条件效果；B 类的 2^N 需求划分是**集合划分（set partitioning）**。所以准确的描述是"**PDDL + 数值资源 + 集合划分两阶段分解**"，而不是 RCPSP（那是有工期-资源约束的调度，没有状态转换），也不是纯 CSP（CSP 没有动作序列）。

**为什么不用 OR-Tools / CP-SAT 替换**（有据）：
- `Google.OrTools` 最新 9.15.x（2026-01）的目标框架是 `net8.0`，`net10.0` 只靠兼容性计算通过；且**不是纯托管**（依赖 `Google.OrTools.runtime.*` 原生库，**没有 win-arm64**），AOT/trim/单文件发布有风险。
- 可解释路径要自建 step 变量与决策字面量，模型规模爆炸，还要再回放成 `POUR_IN/POUR_OUT/RESHAPE/MATCH`。
- CP-SAT 默认可多线程 + 时间预算，必须固定 workers/seed 才确定 —— 相对现在的**确定性 DFS 是倒退**（本项目刚花大力气保住"可复现"）。
- 状态空间本就很小（20 罐/30 液体/8 形状），收益不抵依赖与构建复杂度。

**为什么不用规则引擎**：`NRules`（Rete + 内部 DSL）、`Microsoft RulesEngine`（JSON 工作流）、`JsonLogic` 三者的定位都是"事实→条件→动作"的推理链；本项目的规则是**纯函数 + 规则表数据**（`ShapeRules` + `Rules.WORKSHOP_TEMPLATES`），上规则引擎属过度设计。

**真正该补的三样**（都在自研求解器内部，属"把领域规范做法补齐"，不是换模块）：
1. **状态规范化键 + 置换表（transposition table）**：当前 DFS 没有状态去重 ⇒ 重复子问题被反复展开（这是最大收益点，`NodesExplored/DeadEnds` 会明显下降）。
2. **迭代加深（IDDFS/IDA*）**：小内存下先证伪、再取最短路径。（A* 只在有可采纳启发式时占优；形状/标记转换很难构造可采纳启发式，勉强加会更慢。）
3. **固定转移顺序 / 候选排序**：让同一输入的搜索顺序确定，配合已有的固定种子，得到**可复现**的路径。
> 注意：`beam search` 一类近似搜索**不能**用于本项目的可行性判定——要证明"不可行"就必须穷尽。

## 5. 分阶段路线（每阶段一个验证门，可独立回滚）

| 阶段 | 内容 | 验证门（用户本机） | 回滚 |
|---|---|---|---|
| **P0 前置** | T6（git + `.gitignore` + 中央构建基线 + `global.json`）；T1、T2 | `verify.bat` 五步 `exit=0`；基线 `0 bugs / 2000 + 0 bugs / 3000 + 20 deterministic` | 纯新增文件 |

- **为什么值得替换文本基线**：schema 描述**结构**而非某次运行的数据 ⇒ 不受固定场景与 `<volatile>` 时间戳影响；且**天然覆盖路径步骤 14 个字段**（文本基线因固定场景里路径为空而完全没覆盖，见 `06` §10）。
- **`loose=N` 的含义**：schema 里"什么都能通过"的节点（布尔 `true` / 空对象）数量。它不是缺陷指标而是**待强类型化的清单** —— 清掉 `Dictionary<string,object>` / `List<object>` 逃逸后它应降到 0。
- ⚠️ **首次运行的回执与修复（值得记住的教训）**：8 个类型全部报
  `InvalidOperationException: JsonSerializerOptions instance must specify a TypeInfoResolver setting before being marked as read-only`。
  根因是**我的写法**：`new JsonSerializerOptions { ... }` 没有 `TypeInfoResolver`，而 `JsonSchemaExporter` 要求它 ——
  正确写法是**拷贝构造** `new JsonSerializerOptions(JsonSerializerOptions.Default) { ... }`（官方示例即如此）。已修两处（导出用的 options 与写文件的 options）。
  > 这次能一眼定位，是因为我把导出包在 try/catch 里、**把异常消息当作输出**打印：一个会硬崩的步骤变成了可读诊断，`verify.bat` 仍 `exit=0`，其余 4 步照常通过。
- **第二次运行的回执：`loose=0` 是我的度量假阴性，不是契约干净**。首版计数器只认"布尔 `true` / 空对象"，
  而 STJ 对 `object` 类型导出的是 `{"type":"object"}`（**无 `properties`、无 `additionalProperties:false`**）——
  这同样等于"随便什么都能过"。实测证据（`state.schema.json`）：
  ```json
  "producerStatus": { "type": "object" },
  "eventHistory":  { "type": "array", "items": { "type": "object" } }
  ```
  已按四条规则重写计数器：① 布尔 `true`；② 空对象；③ `type:object` 但无 `properties` 也无 `additionalProperties:false`；④ `type:array` 但无 `items`；并补 `TypeIncludes` 以处理 `["integer","null"]` 这类类型数组。
  > 教训：**度量本身也要能被自己的预测推翻** —— 我预测 `StateDto` 有 2 处空洞、实测 `0`，正是这个矛盾查出了计数器写窄。
- ✅ **本批同时关掉第一个洞**：`StateDto.ProducerStatus` 由 `Dictionary<string,object>` 改为强类型
  `ProducerStatusDto`（含 `ProducerInfoDto` / `GeneratorStatusDto` / `ProducerWarehouseDto`），投影写在 `StateSerializer`
  （投影层唯一归属）；键名与顺序按原字典插入顺序声明 ⇒ 序列化逐字节相同。

- ⏸ **剩下唯一的洞：`eventHistory`** —— 决策见 §5.3。

### 5.3 `eventHistory` 的处置决策（唯一剩下的契约空洞）

它**异构**：两种条目形状，且两种形状里 `operations` 的元素类型也不同。

| 写入处 | 条目键 | `operations` 元素 |
|---|---|---|
| `WorkshopService.SetMaster`（切换事件） | `type` / `from` / `to` / `caseType` / `operations` / `timestamp` | 匿名 `{action, description}` |
| `OrderService.ExecuteOrder`（成功） | `order` / `master` / `slave` / `success` / `timestamp` / `operations` | `ExecutionLogEntry`（强类型） |
| `OrderService.ExecuteOrder`（失败） | 同上 + `reason` | 同上 |

三条路线：

| 路线 | 做法 | 代价 | 判断 |
|---|---|---|---|
| (A) 保持现状 + **记录为有理由的例外** | 不动；schema 里它就是 `{"type":"object"}`；在文档里写明"异构审计日志" | 0 | ✅ **推荐** |
| (B) STJ 多态（`[JsonPolymorphic]` + `[JsonDerivedType]`） | 但**必须给订单条目补一个 `"type":"order"` 键** ⇒ 改对外字节 | 契约变更（新增键） | ❌ 与"契约冻结"冲突，除非你明确批准 |
| (C) 自定义 `JsonConverter` + `TransformSchemaNode` 注入片段 | 字节不变、内部强类型、schema 也可描述 | 约 80–100 行 + 一段手写 schema 片段（易与写入处漂移） | ⏸ 留到"真有客户端消费 eventHistory"时再做 |

**推荐 (A) 的理由（不是偷懒，是有据）**：
1. **前端零消费**：`wwwroot` 全量 grep 无 `eventHistory`（只有 `caseType` 在切换提示里用到，属另一条消息）；
2. **键集合已被守护**：165 行契约快照里就有 `state.eventHistory[0]...` 与 `operations[0].*` 的完整键路径，
   写入处一旦改键，快照立刻 diff —— 所以 (C) 的"防漂移"收益已经被现有机制覆盖；
3. (C) 的价值要等到**真有客户端渲染事件日志**才兑现（Godot 侧若要做时间线，再上 (C) 不迟）。

> 结论：`loose` 的目标值不是 0，而是 **1（已知例外：`eventHistory`）**。任何**新的**空洞出现都是回归，必须解释。

## 6. 明确"不做什么"（含理由）

| 不做 | 理由 |
|---|---|
| 迁 SignalR / AsyncAPI / JSON-RPC | 三者都改对外字节，而"契约逐字节不变"是硬约束；收益（多消费者/多 channel/一问一答关联）在本场景为空集 |
| 给核心库套 Generic Host / DI 容器 | 破坏"零依赖可移植"这一核心资产（Godot/Unity 直接引用程序集） |
| 让 `JarSystem` 持 `IServiceProvider` | 服务定位器反模式，等价于把 DI 容器变成隐藏全局 |
| 为 2 行的 `constants.js` 上代码生成 | 收益 < 维护成本；改为后端下发词汇表 |
| `Constants` 的契约字符串（`OrderPhase`/`CheckMethod`/`SwitchCaseType`）配置化 | 它们是输出契约，配置化 = 让契约可被数据改坏 |
| 拆 `CommandDispatcher` 的 18 个 handler 类 | 纯结构收益，风险/收益比差；保留 `switch`，只把匿名对象换成显式 DTO |
| StrategyExperiment 上 BenchmarkDotNet | 它是参数扫描 + 报告，不是微基准 |
| 为了"更 OOP"继续增加抽象层 | 本项目已完成 3 阶段重构 + A–F 加固；继续加抽象的边际收益已为负 |
| 用 OR-Tools / CP-SAT 替换自研求解器 | 目标框架仅 `net8.0`（net10 靠兼容计算）、**非纯托管**（`runtime.*` 原生库、无 win-arm64）、默认可多线程+时间预算 ⇒ 破坏刚保住的确定性；路径还要自己回放。详见 §3.5 |
| 引入规则引擎（NRules / Microsoft RulesEngine / JsonLogic） | 本项目的规则是"纯函数 + 规则表数据"，规则引擎的"事实→条件→动作"推理链在此属过度设计 |
| 用 beam search 之类的近似搜索做可行性判定 | 要证明"不可行"必须穷尽；近似搜索会漏解（这也是保留 DFS 的原因之一） |
