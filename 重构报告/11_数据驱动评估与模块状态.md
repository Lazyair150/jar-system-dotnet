## 1. 数据分三层：规则 / 词汇表 / 世界数据

| 层 | 含义 | 现状位置 | 是否可配置 |
|---|---|---|---|
| **① 语义不变量**（规则本体） | 一罐一操作、禁令不影响满罐转移、满罐需求不放宽、选择性转移、溢出丢弃不回收、形状转换的派生公式 | `Config/Rules.cs` 的 `ShapeRules.GetPossibleTransforms`、`Domain/*`、`Orders/*` | ❌ **不该配置**：这是玩法语义，配置化 = 让玩法可被数据改坏 |
| **② 词汇表** | 有哪些形状、哪些液体 | `Config/Constants.cs:7-8`（`SHAPES` 8 个 / `LIQUIDS` 2 个） | ⚠️ 目前是 C# 常量；**前端另有一份副本** |
| **③ 世界数据** | 工作台模板（基础/附加标记、禁令）、生产者与速率、初始库存、容量、流入参数 | `Config/Rules.cs:11-15`（模板）、`Bootstrap/SystemBootstrapper.cs:17-33`（4 生产者 + 6 工作台 + 初始酒蜜 20）、`JarSystem.cs:33/67`（速率、流入） | ⚠️ 硬编码在 C#，但**形态已是"数据表"** ⇒ 外置成本低 |

**契约字符串（不可配置）**：`Constants` 里的 `OrderPhase`（none/master/slave）、`CheckMethod`（single_phase/slave_only/partition）、`SwitchCaseType`（same_bans/different_bans）、`OperationType` —— **它们是对外 JSON 的取值**，配置化等于让契约可被数据改坏。这一条与"数据驱动"不矛盾，是边界。

## 2. 增删"罐子种类"（形状）的兼容性逐项核对

| 环节 | 加第 9 种形状后是否自动工作 | 说明 |
|---|---|---|
| 需求/订单校验 | ✅ 自动 | `Order.ValidateOrder` 用 `Constants.SHAPES` 判域（`Orders/Order.cs:40-43`） |
| 工作台标记 | ✅ 自动 | 标记就是字符串集合（`Domain/Workshop.cs`） |
| **形状转换规则** | ✅ **自动** | `ShapeRules` 由标记派生，**没有固定配对表**（`Config/Rules.cs:31-48`）：新形状若不在任何标记中，则"可变形成全部基础标记" |
| 求解器 | ✅ 自动 | `Solver.WorkshopInfo.GetPossibleTransforms` 委托 `ShapeRules`（`StateSpaceSolver.cs:67`） |
| 执行器/命令 | ✅ 自动 | 形状只是字符串标签 |
| **生产者产出** | ❌ **静默缺口** | `SystemBootstrapper.cs:17-20` 的 4 个生产者只覆盖 8 种形状。新增形状**没有生产者 ⇒ 中央仓库永不产出该形状**（但工作台内仍可通过改形得到） |
| **前端下拉框/标记选择器** | ❌ **必须手工同步** | `wwwroot/js/constants.js:1` 是 `SHAPES` 的**前端副本**（`app.js:245/262-263` 用它渲染下拉与标记） |
| 契约快照 | ⚠️ 会变化 | 若新形状出现在默认世界里，`state_keys.txt` 的行数/内容会变（需重建基线） |

**结论**：后端基本兼容，但**有一处静默缺口（产出）与一处手工副本（前端）**。
⇒ 数据驱动的目标形态：形状清单只保留**一处权威**（后端），前端由 `state`/`init` 下发；生产者由**配置数据**声明，装配时校验"每个形状至少有一个生产者或显式声明无产出"。

## 3. 增删"液体"种类的兼容性：❌ 不兼容（当前最硬的一处硬编码）

如果把 `Constants.LIQUIDS` 改成 `["酒","蜜","醋"]`，会发生：

| 环节 | 结果 | 证据 |
|---|---|---|
| 需求/订单校验 | ✅ 放行 | `Order.cs:42` 用 `LIQUIDS` 判域 |
| 工作台液体存储 | ✅ 自动 | `Workshop.LiquidStorage` 是字典，键动态 |
| 中央仓库液体库存 | ✅ 自动 | `ProduceLiquid` 用索引器建键（`ProducerModule.cs:151-156`） |
| 丢弃计数 | ✅ 自动 | `DiscardLiquids` 同样用索引器（`ProducerModule.cs:99`） |
| **每 tick 的液体产出** | ❌ **永远不产「醋」** | `ProductionService.cs:24-27` **硬编码两行**：`wineRate = LiquidProductionRate["酒"]`、`honeyRate = ...["蜜"]`，然后只对 酒/蜜 调 `ProduceLiquid` |
| 初始库存 | ❌ 无 | `SystemBootstrapper.cs:22-23` 只产 酒/蜜 各 20 |
| 速率表初始化 | ⚠️ 只有 酒/蜜 | `JarSystem.cs:33`：`{["酒"]=1, ["蜜"]=1}` |
| **前端液体下拉** | ❌ 硬编码两项 | `app.js:245` 的 `<option value="酒">`/`<option value="蜜">` |
| **前端配色** | ❌ 只有两种 | `style.css:69-74` 的 `.jar-full-wine`/`.jar-full-honey`；`app.js:160` 的三元 `liquid === '酒' ? 'jar-full-wine' : 'jar-full-honey'` ⇒ **第三种液体会被渲染成"蜜"色** |
| 契约快照 | ⚠️ `liquids.<液体名>` 键会变 | `_contract/state_keys.txt` |

**结论**：**形状已接近数据驱动，液体没有**。而且失败方式是"静默"的——加了液体不报错，只是永远产不出来、前端显示成别的颜色。这正是"围绕核心打补丁"的典型后果。

## 4. 是否具备数据驱动的改造条件：✅ 具备，缺三件

**已经具备的基础（重要，不是从零开始）**：
1. 规则**已经**是数据驱动的：形状转换从"标记"派生，`Rules.WORKSHOP_TEMPLATES` 已是声明式数据表；
2. 世界装配**已经**集中在一处（`Bootstrap/SystemBootstrapper.cs`），替换为"读配置"很直接；
3. 契约层已强类型化（DTO + `[JsonPropertyName]` + 可导出的 JSON Schema）⇒ 配置化不会污染契约；
4. 测试基线（5000 用例 + S1–S20 + 165 行快照）可以当**黄金回归**，用来证明"配置化前后行为一致"。

**缺的三件**（对应 `10_...md` 的 P6 / P4）：
1. **外部配置 + 三层校验**：`config/rules.json`（形状/液体/模板/生产者/初始库存）+ `Microsoft.Extensions.Configuration` + `ValidateDataAnnotations` → `IValidateOptions<T>`（跨字段：模板引用的形状/液体必须存在、生产者形状必须存在、模板重名）→ `ValidateOnStart`（启动即失败，而不是静默缺产出）；
2. **词汇表下发**：`state`/`init` 里带上 `shapes`/`liquids`（**这是对外契约的**新增键**，需要你批准**），前端删掉 `constants.js` 副本与硬编码 `<option>`；配色改为按索引/后端给的色值，而不是"酒=红、蜜=金"；
3. **产出环节去硬编码**：`ProductionService.Tick` 改为遍历 `Constants.LIQUIDS`（或配置的液体表），而不是写死两行。

**顺序建议**：先做 ③（1 行循环，零契约风险）→ 再做 ①（配置外置 + 校验，黄金回归守护）→ 最后做 ②（需要一次**加键**的契约变更，与前端 P4-c 同批）。

## 5. 可行性分析有效吗：✅ 有效，且是被双向守护的

不是"看起来对"，而是**被 5000 个用例双向断言**（`test/JarSystem.Test/Program.cs`）：

```
41-47  bool feasible = fr?.Feasible == true;
       if (feasible && !exec.Success) → BUG        // 判定可行，执行必须成功
50-52  else if (!feasible && exec.Success) → BUG-REVERSE   // 判定不可行，执行必须失败
87-99  容量压力组（3000 例）同款双向断言
```

即：**可行性判定与真实执行之间存在双向一致性约束**，任何一侧漂移都会让 `bugs` 计数非零。
当前结果：`=== 0 bugs / 2000 random + 0 bugs / 3000 capacity + 20 deterministic ===`。
另有 S1–S20 确定性场景覆盖：Case1/Case2 切换、禁液边界（不影响满罐转移）、容量溢出丢弃、选择性转移、A/B 类路径。

**可信度边界（诚实说明）**：
- 覆盖的是"随机场景 + 容量压力 + 20 个定向场景"，不是形式化验证；
- `--dump-contract` 的固定场景里订单都不可行，`feasibilityResult` 的部分键**未覆盖**（`06` §10 已记录）——不过 schema 现在覆盖了**结构**；
- B 类的 2^N 划分搜索上限是 `MAX_ORDER_REQUIREMENTS = 10`（需求数 > 10 直接拒绝）。

## 8. 冒烟发现的性能问题：换主从工作台时明显卡顿

**现象**（用户实测）：网站功能正常，但切换主/从工作台时明显卡顿。

**定位（代码证据，按嫌疑排序）**：

1. **`updateUI()` 每次全量重建 DOM**：`app.js:105-115` → `renderWorkshops/renderOrders/renderWarehouse/renderProducers` 各自 `innerHTML = ...` 全量替换（`renderWorkshops:132` 就是 `c.innerHTML = currentState.workshops.map(...)`）。它在**每条 `state` 消息**后调用（2s tick + 每条命令后），切换时又要再来一次。
2. **切换动画的 DOM 节点会被下一次重绘"夺走"**：`animateWorkshopSwitch`（`app.js:478-531`）对**每个 operation** 挂一串 `setTimeout`（每 150ms 生成一个漂浮圆点），而它引用的 `oldCard`/`newCard` 在下一条 `state` 消息触发 `updateUI` 后**已被 innerHTML 换掉（detached）**；回调继续跑在野节点上 ⇒ 动画被打断、定时器堆积、视觉上就是"卡一下"。
3. **Canvas 每帧无条件重绘**：`canvas.js:25-28` 的 `animate()` 无条件 `requestAnimationFrame` 自循环，`render()` 每帧重绘网格 + 仓库 + 生产者 + 网络 + 粒子。稳态 CPU 占用本就偏高，任何额外 DOM 工作都会表现为掉帧。
4. **不太可能是后端**：Core 的切换是有限嵌套循环（形状 × 液体 × 罐子 ≤ 8×2×20，且不调用求解器），量级是毫秒；可用一次计时证实（见下）。

**请你做一次测量（我无法运行浏览器/无法计时）**：

```text
1) F12 → Performance → 点录制 → 切换主台 → 停止
   看 Long Task 落在 updateUI/renderXxx（前端）还是 setMaster 的等待（后端往返）
2) F12 → Network → WS → 看 setMaster 发出到 workshopSwitched/state 回包的**时间差**
3) Console 输入：  JSON.stringify((await new Promise(r=>{...})))  ← 无需，改用下面这条更简单
   在 Console 里执行： performance.now()  然后记下切换后日志时间戳
4) 顺便看一眼切换产生的操作数：在 Console 执行
   (window.currentState? 'n/a' : 'n/a')  ← 若日志有"工作台切换: <caseType>"后的 operations 条数，请数一下
```

（若你愿意，把 DevTools 的 Performance 截图/耗时表贴回来，我按数据定方案，而不是猜。）

**修复方向（归属 P4-c 前端规范化，或单开一批）**：
- **a. 增量更新**：`renderWorkshops/renderOrders` 按 id/index 做局部更新；至少在切换动画进行中暂停重绘（或动画改为对**稳定容器**操作）；
- **b. Canvas dirty flag**：数据未变不重绘（省 CPU，也顺手解决"页面闲置也满帧跑"）；
- **c. 动画与数据解耦**：切换动画改为**固定上限**的 CSS 动画（当前按 operation 数量线性开定时器，操作多时会成倍放大）；
- **d. 状态消息合并节流**：把 tick 与命令触发的多条 `state` 合并到同一帧处理。

> 这四条都属于"前端作为独立模块"的规范形态（`10_...md` P4-c），且**不需要改任何对外契约**。
