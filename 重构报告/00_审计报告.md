## 0. 结论速览

先给结论：代码**骨架是对的**（分层清晰、规则数据驱动、快照隔离、命令模式雏形、测试可跑），但**面向对象的封装与抽象几乎不存在**——全仓库 **0 个 `interface`**，领域状态**全部**是可写公共属性，资源账目在 5 个模块里被直接改写。这不是"风格问题"，而是"改一处坏三处"的结构性风险。

| 级别 | 问题 | 证据 |
|---|---|---|
| **P0** | **静默吞异常**：回滚失败、WebSocket 异常被空 `catch` 吃掉，故障无痕迹 | `CommandExecutor.cs:59-60`、`Program.cs:38,41,49,141,146` |
| **P0** | **零抽象层（DIP 完全缺失）**：无接口、无注入，`new` 硬编码在业务逻辑中 | 全仓库 `grep interface` = 0；`FeasibilityChecker.cs:12,90,138`、`JarSystem.cs:17-18,29` |
| **P0** | **封装破坏**：跨模块直接改写他人可变状态（绕过校验与记账） | 11 处，见 §2.3 |
| **P1** | **God class**：5 个类/文件承担 4–6 项职责 | `JarSystem.cs`(339 行)、`IndependentExecutor.cs`(389)、`FeasibilityChecker.cs`(321)、`WorkshopSwitchEvent.cs`(301)、`Program.cs`(203) |
| **P1** | **静态可变全局状态**：进程级 ID 计数器 | `Jar.cs:12,20`、`Order.cs:11,21` |
| **P1** | **弱类型契约贯穿领域层**：`Dictionary<string, object?>` 既是 UI 契约又是执行器输入 | `FeasibilityChecker.MakeSummary`、`IndependentExecutor.NormalizeStep/ApplySolverStep`、`JarSystem.GetState` |
| **P1** | **表现层关注点泄漏进领域层**：可行性检查器负责生成中文 UI 文案 | `FeasibilityChecker.cs:288-318` |
| **P1** | **基本类型偏执 + null 语义**：`string Shape/Liquid/Type/Status/Phase`，`Liquid == null` 既表示"空罐"又是合法值 | `Jar.cs:16`、`Order.cs:15-16`、`OrderEvent.cs:19` |

### 修复策略（已确认）

**分阶段渐进**：①封装与安全 → ②职责拆分 + 依赖注入 → ③按需设计模式。每阶段独立可编译、可测试、可回滚；设计模式**按需精选**（引入 11 项，另 12 项记录为"评估后不引入"并说明理由，见 §5）。

## 2. 横向问题（跨板块，按严重度）

### 2.1 【P0】静默吞异常

| 位置 | 现状 | 风险 |
|---|---|---|

### 2.2 【P0】零抽象层（依赖倒置缺失）

`grep "interface"` 全仓库 **0 命中**。后果：

- 无法替换/模拟：`FeasibilityChecker` 里 `new StateSpaceSolver()`（`:12` 字段、`:90`、`:138`），测试无法注入桩；`JarSystem` 里 `new ProducerModule()`、`new OrderEvent(...)`、`new FeasibilityChecker()`、`new IndependentExecutor()`。

| 18 | **Iterator** | ❌ 不引入 | 用 `IReadOnlyList<T>` 暴露即可，专门迭代器无收益 |

| 20 | **Flyweight** | ❌ 不引入 | 8 形状 2 液体用 `readonly record struct Shape/Liquid` 值对象已足够，享元池属过度设计 |
| 21 | **Bridge** | ❌ 不引入 | "操作类型 × 载体"仅 4×2，抽象维度过少 |
| 22 | **Interpreter** | ❌ 不引入 | 转换/禁令规则用 `ShapeRules` 纯函数已足够；规则解释器会引入难以验证的动态行为（与"不改变规则"冲突） |
| 23 | **Visitor** | ❌ 不引入 | 对 `SolverStep` 的日志/校验/序列化用强类型方法 + 适配器更直观 |
| — | **Abstract Factory** | ❌ 不引入 | 只有一个产品族（罐子/工作台/订单三类对象彼此独立），工厂方法足够 |

**小结**：引入 12 项（含补位模式）、降级/消解 3 项、明确不引入 8 项。目标是**消除具体问题**，而非凑齐 23 个名词。
