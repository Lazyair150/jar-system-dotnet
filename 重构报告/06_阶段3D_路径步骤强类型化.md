# 06 阶段 3-D：路径步骤强类型化（`SolverStepDto`）

> 状态：**代码已改完，等待用户本机验证**（`重构报告\verify.bat`）。
> 范围：`src/JarSystem.Core` 内的路径步骤生产/存储/消费三端；**不改 JSON 键名、不改规则语义、不改执行行为**。
> 这是加固清单里**风险最高**的一项（原报告标注"必须一次改完"），本文用「逐字段对照 + 逐调用点对照」证明等价。

## 1. 动机：最后一处"运行期才会发现的契约"

阶段 3 把 `GetState()` 的整棵树强类型化了（`Services/StateDtos.cs`，键名由 `[JsonPropertyName]` 钉死），
但**可行性路径的每一步**仍是弱类型字典：

```csharp
// 改前（PathSummaryFormatter）
return (object)new Dictionary<string, object?>
{
    ["step"] = s.Step,
    ["jarIndex"] = ji,
    ["jarsAfter"] = ...
};
```

消费端（执行器）这样读：

```csharp
// 改前（SolverStepApplier / IndependentExecutor）
var type = SolverPathAdapter.ReadType(step);          // TryGetValue + as string
var step = SolverPathAdapter.Normalize(solverPath[si]); // 还要拍平"旧格式"
```

两个后果：

1. **键名写错不会编译报错**：把 `["jarsAfter"]` 写成 `["jars_after"]`，生产端照样跑，前端路径弹窗静默少一列。
2. **读取路径上有 9 个 `ReadXxx` + 1 个 `Normalize`**：每一步执行都经过 `object` 装箱、`TryGetValue`、`as` 转换，
   且要额外维护一段"旧嵌套格式兼容"（`operation` 子字典、`ji/ts/tl/cst` 缩写）——那是重构前 Node 版遗留，
   在本代码库里**不可达**。

本批把这三端一起换成强类型：**14 个键名集中在 `SolverStepDto` 的 `[JsonPropertyName]` 上，生产端拼错字段编译不过，消费端读错字段也编译不过。**

## 3. 逐字段对照（14 个键，键名与取值逐一核对）

| 原字典键（= 契约） | `SolverStepDto` 属性 | `[JsonPropertyName]` | 类型/取值来源（**未改**） |
|---|---|---|---|
| `step` | `Step` | `step` | `s.Step`（int） |
| `requirement` | `Requirement` | `requirement` | `满罐(形状,液体)` / `空罐(形状)`，同一三元表达式 |
| `operation` | `Operation` | `operation` | 同一 `switch(type)` 生成的人读描述（4 个分支字符串逐字相同） |

| `jarIndex` | `JarIndex` | `jarIndex` | `s.Operation?.JarIndex`（int?，**无条件写入**，与原实现一致） |
| `jarId` | `JarId` | `jarId` | `Before[ji].Id`，越界为 null |
| `jarShape` | `JarShape` | `jarShape` | `Before[ji].Shape`，越界为 null |
| `jarLiquid` | `JarLiquid` | `jarLiquid` | `Before[ji].Liquid`，越界为 null |
| `targetShape` | `TargetShape` | `targetShape` | `s.Operation?.TargetShape` |
| `targetLiquid` | `TargetLiquid` | `targetLiquid` | `s.Operation?.TargetLiquid` |
| `costLiquid` | `CostLiquid` | `costLiquid` | `s.Operation?.CostLiquid` |
| `reshapeMode` | `ReshapeMode` | `reshapeMode` | `type=="RESHAPE" ? (FullReshape?"full":"empty") : null` |
| `consumed` | `Consumed` | `consumed` | `new Dictionary<string,int>(s.Operation.Consumed)`（**防御性复制保留**），无消耗为 null |
| `jarsAfter` | `JarsAfter` | `jarsAfter` | `j.Shape + ("/" + j.Liquid 或 "空")` 列表，`After` 为 null 时空列表 |

**唯一的结构性简化**（行为等价）：原实现把同一段越界判断（`ji.HasValue && Before != null && 0 <= ji < Before.Count`）
在 `jarId`/`jarShape`/`jarLiquid` 三个键上**重复了三遍**；现在提成一个局部 `JarState? src`，
越界时三者仍同时为 null、不越界时仍取自同一元素——取值集合完全一致。

## 5. 为什么删除"旧格式兼容"是安全的（等价性论证）

`SolverPathAdapter.Normalize` 做两件事：拍平 `operation` 子字典、把 `ji/ts/tl/cst` 改名。它只在被传入
`Dictionary<string, object?>` 时生效，且**只有在数据里真的存在这些旧键时才有意义**。而：

1. 全仓库对路径步骤的**唯一生产端**是 `PathSummaryFormatter.Summary`（grep 14 个键名证实：
   除本文件外无第二处构造，`JarCommands` 里的 `targetShape/costLiquid` 属于**命令历史**的另一套契约，不相关）；
2. 路径从未被持久化、也没有任何入口从外部 JSON 反序列化路径：
   WebSocket 的 18 个命令（`createOrder`/`checkFeasibility`/`executeOrder`…）都不携带路径，
   `GetState()` 只**输出**路径；
3. 因此 `Normalize` 的旧格式分支与"步骤为 null → 无效路径步骤"分支在运行期**不可达**；
   删除它们不改变任何可达路径的行为，只是把"运行期才发现"变成"编译期不可能"。

> 若未来真的需要从外部导入旧格式路径，正确做法是写一个**显式的导入适配器**（`Dictionary → SolverStepDto`）
> 并配测试，而不是让每一步执行都背着一个永不可达的兼容分支。

## 6. JSON 输出等价性（含一处此前未被记录的契约面）

`SolverStepDto` 的 14 个 `[JsonPropertyName]` 与原字典键**逐字相同、顺序相同**，可空性相同 ⇒ 序列化结果不变。
有两条输出通路：

| 通路 | 载荷 | 本批影响 |
|---|---|---|
| `getState` → `state.orders[i].feasibilityResult.solverPath/masterPath` | `FeasibilityStateDto`（10 个键） | 元素形状不变；`[JsonPropertyName]` 未动 |
| **`autoCheckResults` → `result.solverPath/masterPath`** | ⚠️ **`FeasibilityResultData` 本体**（`OrderService.CheckAllFeasibility` 用匿名对象直接内嵌它，走 `JsonArgs.Options` 的 camelCase 策略） | 元素形状不变（同上）；**外层属性名也未动** |

> ⚠️ **新发现（务必记入硬约束）**：`autoCheckResults` 消息里 `FeasibilityResultData` 的**属性名本身就是对外契约**：
> `feasible/blockage/reason/timestamp/directCount/operationCount/solverPath/masterPath/path/directSatisfactions/operationsNeeded/stats/checkMethod/transferJarIds/transferLiquids`。
> 这也解释了为什么 `FeasibilityResultData.Path`、`.Stats`（在 `GetState()` 的 DTO 里**没有**对应键）
> **不能删**——它们虽然恒为 null，却会作为 `"path":null`、`"stats":null` 出现在 `autoCheckResults` 里。
> 本批**未动**这两个属性。

## 10. 可选后续：让契约快照真正覆盖这 14 个键

契约快照（`--dump-contract`）的固定场景里两条订单都**不可行**（`solverPath` 为空），
所以快照其实**没有覆盖**这 14 个键 —— D 之后它们由 `SolverStepDto` 的 `[JsonPropertyName]` 保证，
但快照本身还看不到。若要让快照真正锁住它们：把 `test/JarSystem.Test/Program.cs` 的 `DumpContract()`
改成"先 `Tick` 出罐子 → 再建一条必然可行的订单 → `CheckFeasibility`"，使快照出现非空路径。
⚠️ 这会改变快照行数（当前 165），必须**同时重建基线** `state_keys.baseline.txt`。见 `00_从这里继续.md` §11。
