## 0. 一句话结论

**核心侧（领域/契约/数据驱动）已经"过度达标"，而周边侧（前端、CI、测试框架、版本控制纪律）严重滞后。**
继续往核心深处做，边际收益已经很低；**当前最合理的一步是横向补齐**——尤其是：修掉用户可见的卡顿、给前端上类型、把验证从"人手跑 bat"变成"机器守门"。

## 3. 我对自己这几批的"内部审视"（哪些是必要的、哪些可以更省）

| 批次 | 值不值 | 复盘 |
|---|---|---|

## 4. 不合理的"味道"（诚实记录，暂不改）

| 味道 | 说明 | 判断 |
|---|---|---|
| `WorldOptions` 与 `Vocabulary` 概念重叠 | 形状/液体在两个类型里都出现（`Vocabulary` 由 `WorldOptions.BuildVocabulary()` 派生，是唯一权威） | 可接受：一个是"内容配置"，一个是"运行时目录"；但确实多一层理解成本 |
| `Jar` 实例携带 `Vocabulary` 引用 | 实体带配置（context-carrying entity 的味道） | 可接受：单例不可变、罐子数量 ≤ 20/台；若将来罐子数量级变大再考虑进程级目录 |
| 装配行为仍在门面里（`InitializeDefault()`） | 纯化观点：装配属于宿主；现在门面仍会"装配自己" | 刻意妥协：为了保住 `new JarSystem()` 可用（测试与文档都依赖它） |
| `eventHistory` 仍是弱类型 | 异构审计日志；schema 里是 `loose=1` | 已记录为**有理由的例外**（键集合由 223 行快照守护、前端零消费） |

## 6. 建议的下一步顺序（横向补齐，不再往核心深挖）

1. **收尾 S4 的"可见部分"**：✅ 词表下发（独立 `world` 消息，未动 `StateDto`）+ ✅ 删 `constants.js` 副本 + ✅ 18 个 `ws.send` → 受检的 `send(type,data)` + ✅ 类型产物 `contract.d.ts`；**剩下**：内联 `onclick` → 事件委托、Vite/TS 真编译（把 `ws.send` 键名变成编译期受检）。
2. **修卡顿**（可与 1 同批，或独立小批）：`updateUI` 增量更新 / Canvas dirty flag / 动画与数据解耦 / 状态消息合并节流。**先做一次 Performance 测量会更省事**，但即使不测，这四条里至少"动画期间不重建 DOM""Canvas 仅脏时重绘"是稳赚的。
3. **上安全网**：✅ **已完成** —— git 已提交 10 次（最新 `196a5ff`「代码规范化后」）+ CI 已补（`.github/workflows/verify.yml` 直接复用 `verify.bat`，设 `CI=1` 跳过 `pause`，失败上传日志）；后续每批验证通过后由你提交一次。
4. **测试框架化**（P2/P3）：xUnit v3 + FsCheck + Verify，旧 runner 保留为**基线守护**。
5. **命令契约（P4-b）**：命令名常量化 + 客户→服务端载荷 DTO 单一事实源。
6. **Godot 侧最小可跑**：只接 `JarSystem.Core` + 一个场景显示 `GetState()`，验证"零依赖可移植"是真资产而不是文档承诺。

> 判据：什么时候**停止**改核心？——当"新增能力主要体现在**其他模块**能否独立升级"时，就不该再动核心的内部结构了。现在正是这个点。

### 7.2 有意保持"不可配置"（这是设计，不是缺口）

| 项 | 理由 |
|---|---|
| 玩法不变量（一罐一操作、禁令边界、满罐需求不放宽、选择性转移、溢出丢弃不回收、形状转换公式） | 配置化 = 让玩法可被数据改坏 |
| 契约字符串（`OrderPhase`/`CheckMethod`/`SwitchCaseType`/`OrderType`/`OrderStatus`/`OperationType`） | 它们是对外 JSON 的取值 |
| `MAX_ORDER_REQUIREMENTS = 10` | 与 B 类 2^N 划分搜索的成本绑定（语义上限） |
| 液体**数量**恰好 2 | 玩法语义（用户明确） |

### 7.4 结论

**以"通过配置装配世界/工作台"为判据：后端框架已经改完了**（并有第 6 步的机械证明）。
**唯一的端到端缺口在客户端** —— 前端还没有消费词表，所以"改配置加形状"对你**目前还不可见**；这正是下一步 S4 要解决的，也是我建议**停止深挖核心**的原因。
