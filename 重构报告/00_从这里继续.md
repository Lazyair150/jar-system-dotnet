#### 收尾：`ws.send` 类型约束的做法（下轮可直接照做）

`contract.d.ts` 已由后端生成（含 `CommandName`、`MessageType`、18 个载荷接口与 `CommandPayloadMap`，见 verify.bat 第 5 步）。只需**一处**泛型标注即可覆盖全部调用点：

```js
/**
 * 发送命令（命令名与载荷键名都由 contract.d.ts 约束）
 * @template {CommandName} T
 * @param {T} type
 * @param {CommandPayloadMap[T]} [data]
 */
function send(type, data) {
  ws.send(data === undefined ? JSON.stringify({ type }) : JSON.stringify({ type, data }));
}
```
然后把 `app.js` 里 20 处 `ws.send(JSON.stringify({ type: 'x', data: {…} }))` 改成 `send('x', {…})`
（无载荷的写 `send('startTick')`）—— **JSON 字节完全不变**，但键名拼错会在 `jsconfig.json(checkJs)` 下报错。
改完需要一次浏览器冒烟（`verify.bat` 不覆盖 JS）。

## 6. 已知坑与约定（避免重复踩）

- **验证只能由用户执行**；`.bat` 必须纯 ASCII、无 `if (...)` / `for ... do (...)` 括号块、不切 `chcp`（本机实测：LF 换行 + 中文路径会让脚本静默失败）。
- **`问题/` 目录不能移动**：`test/StrategyExperiment/Program.cs` 输出路径写死为相对路径 `问题/问题十测试记录-重跑.txt`。
- **契约快照**：`test/JarSystem.Test --dump-contract` 输出 `重构报告/_contract/state_keys.txt`（现在输出**真实 JSON 键名**）。若改了快照格式，请先删 `state_keys.baseline.txt` 重建基线。
- **配置查找必须"向上足够深"**（真实 bug，由新测试 `ShippedWorldConfig_ParsesAndValidates` 抓出）：`…\bin\Debug\net10.0\` 到**仓库根要向上 6 层**；`JarSystemService.ResolveConfigPath()` 原先只找 4 层 ⇒ 只有"从仓库根启动"才命中 cwd 那条，其它启动方式会**静默找不到 `config/world.json`**（退回内置世界，不报错）。现已改为 8 层。测试侧的 `FindUpward` 同理。
- **不要假设测试运行器的工作目录**：xUnit v3 的 in-process runner 的 cwd **不是**仓库根（而 `dotnet run --project test\JarSystem.Test` 那个 CLI 是）⇒ 测试里找仓库文件必须用"当前目录 + 应用目录向上"的查找，不能写相对路径。
- **日志编码（易误判为故障）**：`_build_output.txt`（纯 `dotnet` 输出）与 `_contract\state_keys.txt` 是 **UTF-8**；`_verify_output.txt` 是**混合编码**（`.bat` 自己的 `echo` 走 cmd 的 GBK + `dotnet` 输出走 UTF-8）故工具常报"invalid UTF-8"。**控制台里看到的乱码只是 GBK 控制台回显 UTF-8 字节**，与程序正确性无关（见 §10 ③），不要在运行时加 `chcp`/改 `Console.OutputEncoding`。

⇒ **契约键集合未被破坏**，是 `state_keys.baseline.txt` 格式过期。
