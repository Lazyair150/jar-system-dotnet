### 1.5.11 第十一批（2026-09-16 续）：两条"多专家佐证"的发现 —— 复核结论（一否证、一记为权衡）

本批**没有改行为**：两条都先当作真缺陷去查，结论一条被否证、一条属于设计权衡且两条修法都需要你拍板。

**① "自动检测会覆盖执行承诺"（`Order.RecordFeasibility` 覆盖 vs 执行器读取）→ 判定：不是缺陷**

三条证据（都读过代码，不是推断）：

1. **执行器不盲信它**：主台路径任何一步失败即报"状态与可行性分析不一致"并终止，不带着错误继续
   （`OrderExecutor` 的 `masterPathErrored` 分支，`OrderExecutor.cs:116-119`）；
2. **预算按次重置**：`FeasibilityChecker.Check` → `budgeted.BeginCheck(NodeBudget)`，
   而 `BeginCheck` 会重置 `_nodesRemaining` 与 `BudgetExceeded`（`StateSpaceSolver.cs:145-150`）
   ⇒ 自动检测**不会**把"预算耗尽"传染给后续分析（否则跑一会儿会全是"未判定"—— 这是我这轮原本怀疑的点，已否证）；
3. **覆盖不会插进执行中途**：命令分派、Tick、自动检测**三条路径全在同一个 `svc.Gate` 内**
   （`CommandDispatcher.HandleAsync` / `TickBackgroundService.TickOnceAsync` / `AutoCheckBackgroundService.ExecuteAsync`）。

**残留的真实缺口是"新鲜度不可见"**：UI 看到的那份结果可能算自更早的世界状态，而 `timestamp` 装的是
**分析耗时毫秒**、不是时间点（`FeasibilityChecker.cs:66`），无法据此判断新旧。
要补得**新增契约键**（如"分析时的 tick 序号"）⇒ 属需批准的契约变更，**未擅自加**。
代码侧只做了文档澄清：`Order.FeasibilityResult` 的注释由一句话扩写成上面三条边界，
并写明"**别把它当承诺**、也别去'修'成自动检测不记录 —— 那会让每张订单的显示不再自动刷新"。

**② "闸门被自动检测占用 ⇒ Tick 被跳过且不补算" → 判定：设计权衡（两条修法请你定）**

事实与证据：自动检测在**闸门内**跑 `CheckAllFeasibility()`（N 个"待执行"订单），
而单次检查的上界约 **2 秒**（`DefaultNodeBudget` 的实测量级，见 `FeasibilityChecker.NodeBudget` 注释）
⇒ 闸门可能被占 **N×2 秒**；`PeriodicTimer` **不重入**，且这是 `TickBackgroundService` 注释里写明的
**有意改善**（"上一次未跑完不会叠加"，避免 Tick 堆积）⇒ 这段窗口内的推进**被跳过、不补算**。

**为什么"不补算"是对的**：1 tick = 一次"仓库→主台流入 + 产出"的步进，补算等于改变玩法语义
（不是补偿延迟，是凭空多推进世界）⇒ 不能做。

两条可选修法（都有**可观测代价**，故留给你定，我不擅自选）：

| 选项 | 做法 | 代价 |
|---|---|---|
| **A. 自动检测用更小预算** | 只给自动检测设一个较小的 `NodeBudget`（用户手动点"分析"仍用全预算） | `autoCheckResults` 里出现"未判定"的次数变多（**值**变了，键与形状不变） |
| **B. 自动检测分片** | 每周期只查一部分订单（轮转） | `autoCheckResults` 载荷从"全部待执行订单"变成"本周期的子集" ⇒ **契约与前端可见的变化**，需批准 |

> 刻意**不选**"分几次取闸"：那会让同一批结果在不同世界状态下算出、彼此不可比（今天的实现保证一批内同源）。

    用匿名对象**直接内嵌 `FeasibilityResultData` 本体**，因此该类属性名本身即契约。此前它有 16 键，

#### 收尾：`ws.send` 类型约束的做法（下轮可直接照做）

`contract.d.ts` 已由后端生成（含 `CommandName`、`MessageType`、18 个载荷接口与 `CommandPayloadMap`，见 verify.bat 第 5 步）。只需**一处**泛型标注即可覆盖全部调用点：

```js
/**
 * 发送命令（命令名与载荷键名都由 contract.d.ts 约束）
 * @template {CommandName} T
 * @param {T} type
 * @param {CommandPayloadMap[T]} [data]
 */
function send(type, data) {
  ws.send(data === undefined ? JSON.stringify({ type }) : JSON.stringify({ type, data }));
}
```
然后把 `app.js` 里 20 处 `ws.send(JSON.stringify({ type: 'x', data: {…} }))` 改成 `send('x', {…})`
（无载荷的写 `send('startTick')`）—— **JSON 字节完全不变**，但键名拼错会在 `jsconfig.json(checkJs)` 下报错。
改完需要一次浏览器冒烟（`verify.bat` 不覆盖 JS）。

## 6. 已知坑与约定（避免重复踩）

- **验证只能由用户执行**；`.bat` 必须纯 ASCII、无 `if (...)` / `for ... do (...)` 括号块、不切 `chcp`（本机实测：LF 换行 + 中文路径会让脚本静默失败）。
- **`问题/` 目录不能移动**：`test/StrategyExperiment/Program.cs` 输出路径写死为相对路径 `问题/问题十测试记录-重跑.txt`。
- **契约快照**：`test/JarSystem.Test --dump-contract` 输出 `重构报告/_contract/state_keys.txt`（现在输出**真实 JSON 键名**）。若改了快照格式，请先删 `state_keys.baseline.txt` 重建基线。
- **配置查找必须"向上足够深"**（真实 bug，由新测试 `ShippedWorldConfig_ParsesAndValidates` 抓出）：`…\bin\Debug\net10.0\` 到**仓库根要向上 6 层**；`JarSystemService.ResolveConfigPath()` 原先只找 4 层 ⇒ 只有"从仓库根启动"才命中 cwd 那条，其它启动方式会**静默找不到 `config/world.json`**（退回内置世界，不报错）。现已改为 8 层。测试侧的 `FindUpward` 同理。
- **不要假设测试运行器的工作目录**：xUnit v3 的 in-process runner 的 cwd **不是**仓库根（而 `dotnet run --project test\JarSystem.Test` 那个 CLI 是）⇒ 测试里找仓库文件必须用"当前目录 + 应用目录向上"的查找，不能写相对路径。
- **日志编码（易误判为故障）**：`_build_output.txt`（纯 `dotnet` 输出）与 `_contract\state_keys.txt` 是 **UTF-8**；`_verify_output.txt` 是**混合编码**（`.bat` 自己的 `echo` 走 cmd 的 GBK + `dotnet` 输出走 UTF-8）故工具常报"invalid UTF-8"。**控制台里看到的乱码只是 GBK 控制台回显 UTF-8 字节**，与程序正确性无关（见 §10 ③），不要在运行时加 `chcp`/改 `Console.OutputEncoding`。
- **不要用 `taskkill /f /im dotnet.exe`**（会杀掉所有 .NET 进程）；`run.bat` 里有这行，属潜在误伤。
- **待用户手动做的文件操作**（自动化工具有写权限、无删除/改权限）：
  1. 重命名 `src/JarSystem.Core/Executor/IndependentExecutor.cs` → `OrderExecutor.cs`（类名早已是 `OrderExecutor`）；
  2. 删除 `src/JarSystem.Core/Executor/SolverPathAdapter.cs`（阶段 3-D 后已废弃，文件内只剩下说明注释）。

### 11.1 ✅ 已修（2026-09-16，待你跑一次验证）：契约快照曾**没有覆盖 `SolverStepDto.consumed`**

- `SolverStepDto` 声明 **14** 个 `[JsonPropertyName]`（含 `consumed`，`Dictionary<string,int>?`），
  `Program.cs` 的 `DumpContract()` 注释（第 1160–1162 行）也自称覆盖这 14 个键。
- 但 223 行快照里 **`consumed` 一次都没出现**（`state_keys.txt` 与 `state_keys_config.txt` 均 0 命中），
  而**同一个** `solverPath[0]` 的邻居 `reshapeMode`（第 86 行）和 `jarsAfter`（第 87–89 行）都在。
- **根因（`Flatten`，`Program.cs` 第 1560–1588 行）**：
  `case null:` 会写出 `= null`，`case IDictionary:` 却**只遍历条目** ⇒ **空字典一条都不写**。
  该固定场景的这条路径是 `MATCH` 步骤（直接使用，无液体消耗）⇒ `consumed` 是**空字典**（**不是** null；
  若是 null 会留下 `= null`）⇒ 这个键对快照**完全不可见**。
- **后果**：`consumed` 的改名 / 删除 / 类型变化**不会**被快照门发现。同理，**任何空容器**
  （空 list / 空 dict，例如空 `jarsAfter`）在快照里都不可见 —— 属"门看着绿、其实没覆盖"的静默漏洞。
- **已实施的修法（2026-09-16，两处都做了）**：
  1. **`Flatten` 补空容器占位行**（`Program.cs`，`case IDictionary` 与 `IEnumerable`）：
     空字典/空列表现在写出 `path = <empty>`，让"这个键存在"本身被断言 —— 这同时堵住
     了**整类**"空容器在快照里不可见"的漏洞（空 `jarsAfter`、空 `eventHistory` 等）。
  2. **`DumpContract()` 场景补了一条真实消耗液体的订单**：追加

     选它的理由（已按代码核实，不是猜）：`RequirementOrdering.FullFirst` 把**满罐需求排在最前**，
