# 12 边界重审：核心 = 罐子×液体交互，其余皆为可装配模块

> 触发：用户的架构定位——**"整个系统的工作台、订单、生产源都是为了核心工作罐子与液体的资源交互而存在，并且都是可分离的"**；
> 数据驱动的判据不是"能不能加第三种液体"（**液体固定两种是语义，不改**），而是
> **"能否只靠配置装配出不同的工作台/生产源/订单"**。
> 本文按这个角度重审全仓库，所有结论带 `文件:行` 证据。配套：`10_...md`（路线）、`11_...md`（现状问答）。

---

## 0. 一句话结论

**核心交互（罐子×液体）已经干净；"可分离"这一侧，订单模块真的已经分离了，生产源分离了一半，而工作台没有分离——但它的"装配参数"其实已经具备（6 个构造参数），缺的只是"配置来源 + 校验 + 装配入口外移"。**
更关键的一条结构性判断：**形状是"纯词汇"（除名字外没有语义），规则语义全部落在工作台标记上** ⇒ 让形状数据驱动的成本远低于直觉。

## 2. 关键发现：`Workshop` 一个类压了三种角色

| 角色 | 内容 | 归属（按你的模型） | 现状位置 |
|---|---|---|---|
| **a. 资源容器 + 交互入口** | `Jars`、`LiquidStorage`、`MaxJars/MaxLiquids`、`AddJar/PourIn/PourOut/Reshape*/TryReceiveLiquid` | ✅ **核心** | `Domain/Workshop.cs` |
| **b. 能力参数** | `BaseMarks`、`AdditionalMarks`、`Ban`（+ 临时附加标记作用域） | ✅ **可装配的数据** | 同上（已是字段，`Workshop.cs:28-31`） |
| **c. 规则应用点** | `GetPossibleTransforms` / `IsBanned` / `IsBaseMarked` / `IsAdditionalMarked` | 公式属核心，参数属配置 | `Workshop.cs:82-93` → `Config/ShapeRules.cs:31-48` |

**代价（可直接指出的一处重复）**：同一份"能力参数"在系统里有**三份拷贝**——
`Workshop`（`_baseMarks/_additionalMarks/_ban`）→ `WorkshopSnapshot`（`BaseMarks/AdditionalMarks/Ban`，`Workshop.cs:295-296`）→ `Solver.WorkshopInfo`（`BaseMarks/AdditionalMarks/Ban`，由 `FeasibilityContext`/`WorkshopInfoFactory` 从快照重建），
三者各自把转换规则委托给同一个 `ShapeRules`。**参数一改，三处都要跟着改**，这正是"围绕核心打补丁"的温床。

**建议（批 S1）**：抽出一个不可变值对象 **`WorkshopCapability`**（`BaseMarks` / `AdditionalMarks` / `Ban` + `GetPossibleTransforms` / `IsBanned` / `IsBaseMarked`），
让 `Workshop` 持有它、`WorkshopSnapshot` 直接内嵌它、`WorkshopInfo` 直接复用它。收益：**参数只有一处**，求解器与领域层共用同一份能力语义，且"配置装配工作台"变成"配置就是 `WorkshopCapability` 的序列化形式"。
风险：低（纯结构重排，无行为改动），验证门仍是 **165 行契约快照不变 + 5000 用例 0 bugs + S1–S20 全 PASS**。

## 3. 形状数据驱动：**形状是纯词汇，成本远低于直觉**

**为什么成本低**：形状在系统里**只有名字**，没有任何行为分支——
- 转换规则由标记派生（`Config/Rules.cs:31-48`），**没有形状配对表**；
- 求解器不认形状名（`StateSpaceSolver.cs:67` 委托 `ShapeRules`）；
- 执行器/命令把形状当字符串标签；
- 前端只把形状当标签画（`j.shape[0]`），无按形状的样式分支。

⇒ **加/减形状不需要改规则引擎，只需要让"词表"从代码变成数据，并让依赖它的地方改成读词表。**

**当前依赖词表的切点（33 处，全部核出，按处理方式归类）**：

| 类别 | 位置 | 处理方式 |
|---|---|---|
| **① 校验用**（读词表判成员） | `Domain/Jar.cs:36`（`IsValidShape`）、`Orders/Order.cs:41,43`（需求的形状/液体） | 改为读注入的 `Vocabulary`（词表对象） |
| **② 随机生成用** | `Services/WorkshopService.cs:37,40,43`（随机工作台标记/禁令）、`Services/OrderService.cs:38,40`（随机订单需求） | 读 `Vocabulary` |
| **③ 遍历液体用**（液体固定 2，但名字属内容） | `Solver/StateSpaceSolver.cs:54`、`Orders/Switching/SwitchCases.cs:13,60`、`ResourceTransferrer.cs:44`、`PartitionSearch.cs:125`、`LiquidRequirementCalculator.cs:20,39,46`、`Executor/IndependentExecutor.cs:144`、`GreedyPlanBuilder.cs:82,124`、`Domain/Workshop.cs:58`、`Production/ProducerModule.cs:103,139`（形状维度） | 读 `Vocabulary`（液体仍是"必须 2 种"，只是名字来自配置） |
| **④ 默认值用** | `Domain/Workshop.cs:55-56`（`DEFAULT_MAX_JARS/MaxLiquids`） | 由配置提供默认容量（常量降级为"内置默认配置"） |
| **⑤ 世界内容**（**不属于词表，属于内容**） | `Bootstrap/SystemBootstrapper.cs:17-23,32-33`（4 生产者 + 初始库存 + 青龙台/白虎台）、`Config/Rules.cs:11-15`（模板 玄武台/朱雀台）、**`Services/WorkshopService.cs:33-34`（名字池 金木水火土…×工坊/作坊/窑/炉…）** | 抽成配置（`world.json` / `content.json`） |

> ⚠️ **⑤ 里最刺眼的一处**：一个**服务类**里硬编码了内容词（`WorkshopService.cs:33-34`）。这正是你描述的现象——内容为了配合核心而被塞进代码。

**形状数据化的完整清单**（缺一不可）：
1. 词表外置（`shapes: [...]`）+ 内置默认（保持 `new JarSystem()` 仍可用）；
2. **校验**：配置里引用的形状/液体必须存在于词表；工作台模板名不重复；生产者速率键必须存在于词表 → **启动即失败**（现在是静默无效）；
3. 生产源声明化（形状 → 速率），并校验"每个形状至少有一个生产者"或显式声明"该形状无产出"（现在是静默缺产出：`11_...md` §2）；
4. 前端词表下发（`state`/`init` 加 `shapes` 键 = **一次加键的契约变更，需要你批准**），前端删掉 `constants.js` 副本。

## 4. "通过配置装配出不同的工作台" —— 已经具备条件

**装配参数已经存在**：`new Workshop(name, baseMarks, additionalMarks, ban, maxJars, maxLiquids)`（`Domain/Workshop.cs:54`）
—— 这 6 个值**就是你说的那份配置**。今天缺的只有三件事：

| 缺什么 | 现状 | 目标 |
|---|---|---|
| **配置来源** | C# 字面量（`Rules.WORKSHOP_TEMPLATES` + `SystemBootstrapper` 的两台） | `config/world.json`（外部文件） |
| **校验** | 无（引用不存在的形状/液体 → 静默无效） | `IValidateOptions<WorldOptions>` + `ValidateOnStart`（跨字段校验） |

## 7. 结论：按你的模型，当前系统离"配置装配"有多远

| 目标 | 现状 | 差距 |
|---|---|---|
| 核心只管罐子×液体交互 | 核心已经干净（零依赖、规则派生、DTO 强类型） | 只需把三处"内容/词表"从核心挪出去（§5） |
| 订单模块可分离 | ✅ 已分离 | 无 |
| 生产源可分离 | 模块已独立（`ProducerModule`），但默认装配与液体产出写死 | S0 + S3 |
| **工作台可装配** | 装配参数**已存在**（6 个构造参数），能力语义由标记派生 | 配置来源 + 校验 + 装配入口外移（S2/S3）+ 参数去重（S1） |
| 形状数据化 | 词表是 C# 常量，33 处依赖 | S2（机械但量大） |
| 前端可分离 | 有词表副本、内联事件、全量重绘 | S4 |
