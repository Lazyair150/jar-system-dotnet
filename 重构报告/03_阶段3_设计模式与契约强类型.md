### 2.1 责任链的分派等价性（关键）

原实现：
```csharp
if (order.Type == "A") result = CheckTypeA(...); else result = CheckTypeB(...);
```
新实现：链上三个检查各自声明适用性 —— `SinglePhaseCheck` 仅当 `Type == A` 参与，`SlaveOnlyCheck`/`PartitionCheck` 仅当 `Type != A` 参与。

- **非 A 类型（含未来的第三种类型）仍走 B 类路径**：两个 B 检查的适用条件是「不是 A」而不是「等于 B」，与原来的 `else` 分支完全一致。
- **A 类**：`SinglePhaseCheck` 经 `FromSolverResult` 必然返回非 null（可行或不可行都有结果）⇒ 链在它这里终止，不会落入 B 检查。
- **B 类**：`SlaveOnlyCheck` 可行即返回（含把 `TransferJarIds/TransferLiquids` 置空的原有处理），否则返回 null 交给 `PartitionCheck`；后者无论成败都返回结果（失败时 `Blockage = lastBlockage ?? "资源冲突或液体不足"`），与原 `CheckTypeB` 的返回完全相同。
- **兜底**：`result ??= new FeasibilityResultData { Feasible = false, Reason = "无适用的可行性检查" }` 理论不可达，仅作防御。
- **计时**：`startTime` 在构造上下文前取，`Timestamp` 在链执行后写入 ⇒ 与原来「取时间 → 分派并求解 → 写 Timestamp」的顺序一致。

### 3.2.2 Observer：不引入（附证据）

1. **会改变推送顺序**：Web 层 `CommandDispatcher` 的「推送 state」与「推送其它消息」顺序**逐命令不同**——例如 `setMaster` 是「先 state，再 workshopSwitched/error」，`setAutoCheck` 是「先 autoCheckChanged，再 state」，`executeOrder` 是「orderExecuted → state」。若改成「核心变更 → 触发事件 → 适配层统一推送」，这条顺序必然改变 ⇒ 违反"行为不变"。
2. **与项目既定 Godot 方案冲突**：`Godot迁移指南.txt` §2.6 与 `Godot移植设计对话记录.md` §5 明确「核心不暴露 .NET 事件，由 `JarDriver` 把返回值翻译成 Godot 信号」，依赖方向单向（视图 → 驱动器 → 核心）。
3. **无订阅者即是投机 API**：只加事件不接线，等于引入无人使用的公开 API（审计本就把死代码列为问题）。
4. **已有等价抽象**：`IWebSocketSink`（阶段 2F）就是"适配层通知"的落点；Godot 侧同理可用 `JarDriver` 返回/信号实现。

### 3.2.3 Decorator：不引入

| 原候选用途 | 现状 | 结论 |
|---|---|---|
| 命令日志装饰器（消除 `OrderEvent` 的 `is XxxCommand` 分支） | 该分支只做"取罐子描述给日志"。更简单且无包装层的做法是给 `Command` 加 `DescribeTarget()` 虚方法（小规模 Template Method） | **装饰器不引入**；`DescribeTarget()` 列为可选清理项 |
| 仓库上限/丢弃计数装饰器 | `ProducerModule` 已在唯一入口（`Tick`/`ProduceLiquid`/`DiscardJars`/`DiscardLiquids`）处理；且 `ProducerModule` 会被 `Reset()` 整体替换，包装层需处理生命周期 | **不引入**（无收益、有额外耦合） |

### 3.2.4 Proxy：不引入

候选是「给仓库/液体存储加保护代理（上限 + 计数 + 只读视图）」。但真实的越权写路径已在阶段 1/2 消除：`Workshop` 侧由 `TryReceiveLiquid`/`ResizeLiquidCapacity` 收口，仓库侧由 `ProducerModule` 集中入口处理；再加代理层只增加间接性。`GetWarehouseJars()` 泄漏内部列表的建议改为 `WarehouseJarCount`（记录在板块 G 遗留项）。

**等价性论证（3-1）**

1. **键名由特性固定**，不再依赖序列化命名策略：旧写法用字典字面量（键原样输出），新写法用 `[JsonPropertyName]`（优先级高于 camelCase 策略）⇒ 两条序列化路径（`JsonArgs` 的 camelCase 与 ASP.NET `/api/state` 的 Web 默认）输出键名相同。
2. **null 语义一致**：旧写法把 `null` 值写入字典（默认不忽略 null），新写法未设置 `DefaultIgnoreCondition` ⇒ 仍输出 `"liquid": null`、`"currentMaster": null` 等。
3. **可空性逐项对齐**：`jars[].id` → `int?`、`orders[].id` → `int`、`currentMaster/currentSlave` → `int?`、`masterName/slaveName` → `string?`、`feasibilityResult` → 可空对象（无结果时为 null）——都与旧写法实际产出的值一致。
4. **`producerStatus` 与 `eventHistory` 保持原结构**（仍为 `Dictionary`/`List<Dictionary>`），避免改动 `ProducerModule.GetProducerStatus` 与各事件写入处的键集合；这两处的进一步 DTO 化列为后续项。
5. **`requirements` 仍用领域类型 `List<Requirement>`**（其 `shape`/`liquid` 由命名策略 camelCase 输出，与旧写法一致）。
6. **唯一受影响的非编译产物**：`_test_diag.csx`（临时诊断脚本，未被解决方案编译）里的 `st["workshops"]` 字典写法已失效，建议删除或改写。
