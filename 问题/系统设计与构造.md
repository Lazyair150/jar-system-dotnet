# 陶罐系统（Jar System）— 系统设计与构造

> 版本：.NET 10 移植版 | 源项目：jar-system-v4.0-logic-fixed (Node.js)
> 端口：`http://localhost:3457` | 测试框架：`test/JarSystem.Test`

---

## 一、系统设计理念

### 1.1 核心概念

陶罐系统是一个**规则驱动的资源调度模拟器**。玩家管理多个工作台（Workshop），每个工作台拥有特定的形状标记和禁令规则。中央仓库持续生产陶罐和液体，玩家需要：

1. 选择**主工作台**（接收仓库流入）和**从工作台**
2. 接受**订单**（要求特定形状和液体的罐子组合）
3. 系统**可行性分析**判断订单是否可完成
4. **执行订单**：主台预处理 → 选择性转移（交付罐 + 从台计划使用的工具罐，其余留在主台）→ 从台继续 → 从台交付

### 1.2 设计原则

| 原则 | 说明 |
|------|------|
| **领域驱动** | 核心逻辑集中在 `Domain` 层（Jar/Workshop），不含 UI 依赖 |
| **求解器独立** | 状态空间 DFS 求解器独立运行，仅读取快照，不修改实际状态 |
| **命令模式** | 所有操作通过 Command 封装，支持执行、撤销和日志记录 |
| **阶段隔离** | B 类订单严格分主台/从台两个阶段，可行性检查模拟两阶段 |
| **一罐一操作** | isMarked 标记防止同一罐子在单次执行中被重复操作 |
| **就简原则** | 优先使用工作台游离液体，不动满罐，除非游离液体不足 |
| **FIFO** | 同等条件下，优先使用低编号罐子 |

## 三、核心模块详解

### 3.1 陶罐 (Jar)

```csharp
public class Jar {
    int? Id;           // 唯一编号
    string Shape;      // 8 种形状之一
    string? Liquid;    // null=空, "酒"/"蜜"=满
    bool IsMarked;     // 本轮是否已被操作
}
```

### 3.2 工作台 (Workshop)

| 属性 | 说明 |
|------|------|
| BaseMarks | 基础标记（可倒液、可互转） |
| AdditionalMarks | 附加标记（仅可从基础标记转入） |
| Ban | 禁令列表（被禁液体不能存储/倒入/作为成本） |
| Jars | 当前罐子列表 |
| LiquidStorage | 液体存储（酒: N, 蜜: N） |

> **禁令边界**：禁令只限制「倒入空罐、游离液体存储、改形成本」；装满被禁液体的满罐不受影响，
> 可正常转移/回滚/被新主台接收（2026-08-01 确认）。

**操作**：
- `PourIn(jar, liquid)` — 空罐 + 基础标记 + 液体不违禁 → 满罐
- `PourOut(jar)` — 满罐 → 空罐 + 液体回工作台
- `ReshapeEmpty(jar, to, cost)` — 空罐改形，消耗 1 份液体
- `ReshapeFull(jar, to)` — 满罐改形，清空罐内液体（消耗自身液体）

**形状转换规则**：
```
基础标记中的形状 → 所有其他基础标记 + 所有附加标记
附加标记中的形状 → 所有基础标记
不在任何标记中   → 所有基础标记
```

### 3.3 订单 (Order)

| 属性 | 说明 |
|------|------|
| Type | A 类（主台完成）或 B 类（主台预处理→转移→从台继续） |
| Requirements | 有序列表（展示约定空罐在前；实际执行满罐优先） |
| Status | 待执行/执行中/成功/失败 |
| FeasibilityResult | 可行性分析结果缓存 |

> **满罐需求限制**：一罐一操作使「改形 + 倒液」两步不可行，满罐需求只能由现成满罐或「现成同形空罐 + 倒入」满足；
> 改形仅服务空罐需求。**设计定案（2026-08-01）：不放宽**，作为 puzzle 约束保留。
>
> **订单需求数量上限：10 个**（默认，约束 2^N 划分搜索规模）。

### 3.4 可行性分析 (FeasibilityChecker)

**A 类订单**：单阶段检查，在主台规则下运行求解器。

**B 类订单**：多策略尝试：
1. `slave_only` — 仅从台资源是否满足
2. `combined_under_slave` — 全部资源在从台规则下
3. `TwoPhaseSimulation` — 两阶段模拟：主台规则求解 → 个体需求补全 → 转移 → 从台规则确认

### 3.5 状态空间求解器 (StateSpaceSolver)

DFS 回溯搜索，合法操作类型：

| 操作 | 条件 | 效果 |
|------|------|------|
| MATCH | 已有匹配罐子 | 预订罐子，标记 |
| POUR_IN | 空罐 + 基础标记 + 液体不违禁 + 库存 ≥ 1 | 满罐 |
| POUR_OUT | 满罐 + 液体不违禁 | 空罐 + 液体回工作台 |
| RESHAPE(空) | 空罐 + 可转换 + 有液体库存 | 空罐(新形状) |
| RESHAPE(满) | 满罐 + 可转换 + 罐内液体不违禁 | 空罐(新形状)，清空液体 |

### 3.6 独立执行器 (IndependentExecutor)

| 阶段 | A 类 | B 类 |
|------|------|------|
| 主台 | 执行全部需求 | 按需求列表执行（ExecOnWs） |
| 转移 | 无 | 选择性转移：交付罐 + 从台计划使用的工具罐（按 Id 清单），其余留在主台；液体只转需要的量 |
| 从台 | 无 | 优先按求解器路径执行，失败则降级到 ExecOnWs |
| 交付 | 主台交付 | 从台交付 |

## 十一、工作台切换事件（WorkshopSwitchEvent）

### 设计目标

切换主工作台时，不简单丢弃或回仓旧台资源，而是通过一个事件空间智能传递资源，最大化新主台可利用的资产。

### 事件生命周期

```
旧主台(作为事件主台) + 新主台(作为事件从台)
       |
       v
  判定 Case 类型
  (禁令相同? 不同?)
       |
   +---+---+
   |       |
   v       v
Case 1  Case 2
   |       |
   v       v
  转移阶段
 (清isMarked+搬罐子+搬液体)
       |
       v
  新主台就位
```

### Case 1：禁令相同

目标：将游离液体尽可能装入罐子，以满罐形式传递，扩大新主台液体储备。

1. 游离液体倒入基础标记形状的空罐（while循环，直至液体耗尽或无空罐）
2. 若仍有无液体的空罐，从非基础标记形状的满罐倒出液体补充，再倒入空罐
3. 多余游离液体留在旧台，转移时一并送往新台

### Case 2：禁令不同

目标：利用旧台能力将罐子改形为新台可用形状，消耗无法传递的液体。

1. 旧台临时获得新台基础标记作为附加标记（try/finally 保证回退）
2. 游离液体用于将空罐改形为新台基础形状（while循环）
3. 满罐用自身液体改形为新台基础形状（ReshapeFull，while循环处理全部满罐）
4. 若仍不足，从满罐倒出液体补充改形
5. 残留液体按新台禁令/容量转移，被禁的丢弃（**丢弃而非回流中央仓库**）

### 转移阶段

- 清除所有罐子 isMarked
- 罐子逐一移入新台（容量满则丢弃）
- 液体移入新台（禁液则丢弃，容量满则丢弃）
- 全程操作写入操作日志

### 罐子选择策略化

IndependentExecutor 支持 JarSelectionStrategy 枚举：

| 策略 | 行为 |
|------|------|
| FIFO（默认） | 低编号优先 |
| LIFO | 高编号优先 |
| RareShapeFirst | 同形状空罐最少者优先 |
| Random | 随机选择 |

随机化测试（711模式x4策略=2844次对比）验证 FIFO 为最优默认策略（38.2%胜率）。

### 前端动画

- 旧主台卡片：0.3s 缩放至 95% + 透明度降至 0.6，0.6s 恢复
- 新主台卡片：0.4s 青色发光边框，每个操作产生粒子点飘入动画（150ms 间隔）
- Canvas：triggerTransfer 转移动画
- 日志区：逐条显示操作记录
