# .NET 测试架构调研报告（2025–2026）

## 1. 框架/平台现状

- 平台层：VSTest 与 Microsoft.Testing.Platform（MTP）二选一。官方明确：不要在同一解决方案/运行配置里混用 VSTest 与 MTP 项目；MTP 面向 Native AOT/裁剪、可执行优先；VSTest 兼容面更广（[对比](https://learn.microsoft.com/en-us/dotnet/core/testing/test-platforms-overview)）。
- `dotnet test`：.NET 10 SDK 起支持原生 MTP 模式，在 `global.json` 写 `{"test":{"runner":"Microsoft.Testing.Platform"}}`；.NET 8/9 SDK 用 MSBuild 属性 `TestingPlatformDotnetTestSupport`（[xUnit 文档](https://xunit.net/docs/getting-started/v3/microsoft-testing-platform)、[dotnet test](https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-with-dotnet-test)）。
- xUnit v3：测试项目是可执行文件（`OutputType=Exe`），内置 MTP 支持，可不装 `Microsoft.NET.Test.Sdk` / `xunit.runner.visualstudio`。3.2+ 可用 `xunit.v3.mtp-v1` / `xunit.v3.mtp-v2` / `xunit.v3.mtp-off` 选版本；4.0 默认 MTP v2 并移除 v1（[迁移指南](https://xunit.net/docs/getting-started/v3/migration)）。
- xUnit Native AOT：自 4.0 起支持，需 `xunit.v3.aot` 系列包 + 源生成器，仅 C#、最低 .NET 9；AOT 模式缺少泛型测试方法、接口式特性、序列化，失败信息里的对象内容也会被省略（[官方文档](https://xunit.net/docs/getting-started/v3/native-aot)）。
- NUnit：NUnit3TestAdapter 5.0+ 提供 MTP 桥接（`EnableNUnitRunner` + `OutputType=Exe`，[官方文档](https://docs.nunit.org/articles/vs-test-adapter/NUnit-And-Microsoft-Test-Platform.html)）；MSTest 走 MSTest SDK；官方博客宣布 MTP 已被主流 .NET 测试框架支持（[.NET Blog](https://devblogs.microsoft.com/dotnet/mtp-adoption-frameworks/)）。
- MTP v1 → v2 迁移说明：<https://learn.microsoft.com/en-us/dotnet/core/testing/microsoft-testing-platform-migration-from-v1-to-v2>

**推荐**：xUnit v3（稳定线 `xunit.v3.mtp-v2`）+ MTP + `dotnet test`。本项目为纯托管逻辑，**不推荐**为测试引入 AOT 包。

## 2. 性质测试（property-based testing）

- FsCheck 3.4（官方/主流）：
  - C#：`Prop.ForAll<T>(...)`、`Configuration.Quick.WithMaxTest(n).WithReplay(...)`、`QuickCheckThrowOnFailure()`（[Quick Start](https://fscheck.github.io/FsCheck/QuickStart.html)）。
  - 配置与复现：`Replay`、`Config.WithMaxTest/WithStartSize/WithEndSize/WithMaxRejected`（[Running tests](https://fscheck.github.io/FsCheck/RunningTests.html)）。
  - xUnit 集成：`[Property(MaxTest = ..., Replay = "s1,s2", Arbitrary = [typeof(...)])]`，装配级 `[Properties]`；包 `FsCheck.Xunit.v3`（3.4.0，[NuGet](https://www.nuget.org/packages/FsCheck.Xunit.v3)）。
  - 生成器/收缩：`Gen.*`、`Arb.fromGen`、`Arb.mapFilter`、`Arb.filter`，自定义 `Arbitrary<T>`（[Test data](https://fscheck.github.io/FsCheck/TestData.html)）。
- 把「2000 随机用例查不变量」改写成规范性质测试：
  1. 定义 `Arbitrary<Scenario>`：组合 master/slave/order 的生成器；前置条件用 `Arb.mapFilter` 表达，慎用大面积 `Where` 过滤（会因 `MaxRejected` 直接 Exhausted）。
  2. 每条不变量一个 `[Property]`：罐子守恒、液体非负、`feasible ⇔ exec.Success` 双向一致；断言用 `Prop.label` 附上下文。
  3. 失败最小化：FsCheck 自动 shrink，并打印 `Replay directly at failing step with (seed1,seed2,size)`；把该串写进 `[Property(Replay = "...")]` 即可固化。
  4. CI 确定性：CI 固定 `Replay`（或固定种子 + 固定 `MaxTest`）；本地/夜间跑更大 `MaxTest`。
- 社区备选：CsCheck 4.9（纯 C#、内置 shrinking、`Check.Sample`，[repo](https://github.com/AnthonyLloyd/CsCheck)）；Hedgehog .NET（`Property.recheck "seed"`、`counterexample`，[docs](https://hedgehogqa.github.io/fsharp-hedgehog/articles/getting-started.html)、[Hedgehog.Xunit](https://github.com/dharmaturtle/fsharp-hedgehog-xunit)）。生态与文档厚度均不及 FsCheck。

**推荐** FsCheck + `FsCheck.Xunit.v3`；**不推荐**自研随机循环 + 手写 bugReports 作为长期方案（无 shrinking、无 seed 复现、失败不可最小化）。

## 3. 模型/状态机测试（订单执行 + 主从切换）

- 规范做法：`model-based testing`。FsCheck 的 `FsCheck.Experimental.Machine<'Actual,'Model>`：实现 `Setup`（`Actual()` 建真实系统、`Model()` 建模型）、`Next`（按模型状态生成合法操作）、可选 `ShrinkOperations`；每个 `Operation` 实现 `Pre`（前置条件）/`Run`（更新模型）/`Check`（把操作作用于真实系统并与模型比对），最后 `StateMachine.toProperty spec` 交给 FsCheck 跑（[官方文档](https://fscheck.github.io/FsCheck/StatefulTestingNew.html)）。失败会收缩成**最短操作序列**并给出 Replay。
- 注意：`FsCheck.Experimental` 官方明示不受语义化版本保护（次版本可能破坏）。因此建议双轨：
  1. 状态机实验（建模主从切换、转移、ban 列表等状态约束）；
  2. 差分测试：领域模型/纯函数 oracle 与真实 `Executor` 对同一命令序列逐步比对（尤其 master/slave 切换后的快照、可行性判定与执行结果一致性）。
- 转移合法性（状态 × 事件 → 允许/拒绝）建议用表驱动 `[Theory] + MemberData` 固化，作为状态机测试的"规格锚点"。

## 4. 实验/参数扫描脚本（StrategyExperiment）

- 定位：它是**参数扫描 + 报告**（711 配置 × 3 种子 × 4 策略，输出胜率），不是微基准。
- **不推荐** BenchmarkDotNet：它以微基准/统计耗时为核心，参数用 `[Params]`，报告是性能表，不适合胜率矩阵与"结论工件"（[BenchmarkDotNet 入门](https://benchmarkdotnet.org/articles/guides/getting-started.html)）。
- **推荐**保留独立 CLI 项目（`OutputType=Exe`、MTP 兼容或纯 CLI），但做三点改造：
  1. 种子显式化：`test/StrategyExperiment/Program.cs` 已用 `new Random(hash(mode, seed))`（可复现），但 `src/JarSystem.Core/Executor/JarStrategies.cs`、`Services/WorkshopService.cs`、`Services/OrderService.cs` 里的 `new Random()` 不可复现——应改为注入的 `Random`（或可控 RNG 抽象），并把实际种子写进报告。
  2. 报告写固定路径的 CSV/MD（当前为 `问题/问题十测试记录-重跑.txt`），便于 diff 与 CI 工件上传。
  3. 退出码语义化（0 = 无回归，非 0 = 胜率跌破阈值），让 CI 能卡门禁。
- CI 中若只想卡阈值，可用 `[Theory] + MemberData` 取少量代表点断言"胜率 ≥ 下界"；重量级扫描仍留在 CLI。

## 5. 迁移方案（分步，可执行）

1. 建工程：`dotnet new install xunit.v3.templates` → `dotnet new xunit3` 生成 `test/JarSystem.Tests`（或 `dotnet new xunit3 -o test/JarSystem.Tests`）；`global.json` 加 `test.runner=Microsoft.Testing.Platform`；添加 `FsCheck.Xunit.v3`。
2. 搬确定性场景（风险最低）：S1–S20 每个闭包 → 一个 `[Fact]`；`(bool Ok, string Detail)` → `Assert.True(ok, detail)`。先保持一对一映射（或 `[Theory] + MemberData` 表驱动），确保零语义改动。
3. 搬随机不变量：`Random(42)` 的 2000 例、`Random(2026)` 的 3000 例**原样保留为"回归基准测试"**（同一 seed、同一断言），另**并行**新增 FsCheck `[Property]` 版本；两者并存观察一段时间，FsCheck 未发现新反例后再决定是否删除旧循环。
4. 基线对照：保留并守护 `=== 0 bugs / 2000 random + 0 bugs / 3000 capacity + 20 deterministic ===` 这条输出——在 xUnit 里加一个"基线守护"测试，调用旧 runner（进程调用，或把旧 runner 的报告逻辑抽成可调用的 `BaselineReport.Run()`）并断言输出字符串包含该基线。
5. CI 分档：PR 只跑 20 deterministic + 缩减版性质测试（如 `MaxTest=200`，固定 Replay）；nightly 跑 2000/3000 + 增大 `MaxTest`，固定种子保证可比。

**不该迁移**：

- `test/JarSystem.Test/Program.cs` 的 `--dump-contract` 契约快照模式：它本身就是"被守护的 CLI 契约 + 重构对照工具"，迁进 xUnit 会丢掉"可在重构前后对同一 CLI 做 diff"的能力；应继续作为独立 CLI 命令保留。
- `StrategyExperiment` 的既有报告路径与结论（`问题/问题十测试记录-重跑.txt`）：这是实验工件而非测试断言。
- 任何被 CI/脚本依赖的控制台文本契约（基线摘要行、退出码语义）。
