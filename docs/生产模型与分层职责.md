# 生产模型、运行时实例与分层职责

> 2026-11-03
> 本文回答一个现场误判：液体生产卡显示 0，为什么每回合仍会进入主台；以及生产卡背后到底有哪些真实实体。

## 1. 一次推进实际发生什么

`TickPipeline` 把一次推进固定为五个阶段：

1. **事件注入**：世界事件改资源或压入临时规则。
2. **修饰器更新**：区间到期的法令被移除。
3. **过程推进**：活动订单/迁徙至多前进一步。
4. **世界产出**：
   - `ProducerModule` 按每个形状的生产源速率产罐，先放入 `Warehouse`；
   - `LiquidProduction` 按每个液体品种的自产速率产液，也先放入 `Warehouse`。
5. **流入边界**：`Warehouse.FlowToMaster` 从中央仓库向当前主台搬运。

第 4 步和第 5 步是**两个不同机制**：

- 第 4 步增加库存；
- 第 5 步只改变库存位置，不产生新资源。

因此，“液体自产速率 = 0”和“液体进入主台”可以同时成立：流入搬运的是仓库已有库存。

仓库入口只有一个合法接收方：当前主台。主台切换的异步迁徙过程存续时入口暂停；从台只在
B 类订单期间接收主台选择性上调的资源，不参与仓库流入。

## 2. 当前实体与实例

### 配置/数据

- `WorldOptions`：一份世界参数快照。
- `FlowOptions`：每次流入的罐子上限、每种液体上限，以及液体自产速率。
- `ProducerOptions`：生产源名称与“形状 → 速率”表。
- 关卡 JSON：一份 `WorldOptions` + 回合/目标等关卡信封。

### 核心运行时

每个 `JarSystem` 世界拥有：

- 1 个 `ProducerModule`；
- `ProducerOptions.Count` 个 `Producer`；
- **每个词表形状 1 个** `ShapeProductionLine`；没有生产源的形状仍保留零速率投影，但当前不参与每 tick 求和；
- 1 个 `Warehouse`；
- 1 个 `LiquidProduction`，内部按液体品种保存速率和累加器；
- 1 个 `ProcessSystem` 与其过程日志/时钟；
- 1 个 `PresentationFeed`、1 个 `WorldBus`、1 个 `ModifierStack`、1 个 `JarPool`；
- 每个工作台一个 `Workshop`。

以当前第一关为例：

```text
词表形状线对象       8
其中正速率形状线     2（圆罐 1.0、方罐 0.8）
其中无生产源形状线   6（不参与产出计算）
Producer 实体         1
已占产能槽            2 / 3
液体自产通道          2（酒 0、蜜 0）
初始仓库库存          蜜 3、酒 0
每次推进流入上限      罐子 3、每种液体 2
```

第一回合的圆罐由生产者产出；方罐可能因累加器不足而到第二回合才出货。液体即使自产为 0，
只要仓库有库存，仍会按流入上限进入主台。

## 3. 页面表达

游戏页将生产区拆为：

- **形状线卡**：汇总真实 `generators[].rate` / `accumulated`；
- **生产源行**：显示每个 `(生产者, 形状)` 的实际速率；关卡初速不在快捷档位内时显示“当前值”；
- **产能槽摘要**：`used / limit` 来自内核，页面不自行数槽；
- **液体自产卡**：显示自产速率、累加器、仓库库存与单次流入上限；
- **生产 ≠ 流入说明**：明确“生产入库”和“仓库搬运”是两段链路；
- **空闲形状线摘要**：零生产源形状只汇总，不铺成可操作的空卡。

`production-view.js` 只负责这个只读投影；`play.js` 只负责连接、命令和页面编排。

## 4. 分层与职责

| 层 | 代表类型/文件 | 责任 |
|---|---|---|
| 配置/数据 | `WorldOptions`、关卡 JSON、`StateDto` | 可序列化输入与强类型读模型 |
| 领域 | `Jar`、`Workshop`、`Order`、`ProducerModule`、`LiquidProduction`、`Warehouse` | 资源、规则与状态迁移 |
| 应用/用例 | `JarSystem` + `JarSystem.Runtime`、`OrderService`、`ProductionService`、`WorkshopService` | 编排意图、校验、记录命令；门面按运行时职责拆分 |
| 过程/运行时 | `ProcessSystem`、`TickPipeline`、`WorldScheduler`、`WorldBus` | 逻辑时间、过程生命周期、跨 tick 事件 |
| 读模型 | `StateSerializer` | 把活世界投影成稳定 DTO，不承载业务规则；`producerStatus.slots/flow` 是显式读模型 |
| 宿主 | `JarSystemService`、`CommandDispatcher`、`GameManager` | 并发闸门、协议、文件 IO、引擎接入 |
| 表现 | HTML/CSS、`play.js`、`production-view.js`、Godot 卡片 | 只显示和转发命令 |

层级方向由 `ArchitectureTests` 机器检查；数据流固定为：

```text
配置 → 领域对象/服务 → 命令日志与逻辑 tick → StateDto → 宿主 → 表现
```

## 5. 什么不是“运行中的机制”

- `demo/_退役/` 是历史原型，不参与构建或运行。
- `MatchingSolver`、参考求解器和基准程序是替代实现/差分资产，不属于默认每 tick 链路。
- 没有生产源的 `ShapeProductionLine` 是状态投影占位，当前 `Tick` 已跳过其求和/累加。
- `JarSelector` 的非当前选择策略已改为按需实例化，默认 FIFO 时不会创建另外三个策略对象。
- 没有正速率生产源的形状线不进入 `Tick` 的求和/累加路径。
- Web 的两个后台循环是宿主生命周期设施：一个检查是否开始推进，一个检查自动分析开关；
  它们不是世界规则，也不进入核心回放。

## 6. 仍需独立处理的边界

- 液体名称仍在若干求解/执行路径中按 `Constants.LIQUIDS` 遍历；配置层目前明确拒绝改名/改序。
- Web 与 Godot 共用核心，但 Godot 尚未加载 Web 的 `config/world.json`、关卡目录和场景文件。
- `JarSystem` 仍是统一公开门面，但时间推进、产出配置和重置已从主文件拆到
  `JarSystem.Runtime.cs`；主文件回落到 1000 行以下，公开 API 保持不变。
