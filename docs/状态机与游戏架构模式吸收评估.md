# 状态机与游戏系统架构模式吸收评估

> 日期：2026-11-03
> 范围：`src/JarSystem.Core` 的领域、过程、调度、执行、投影，以及 Web/Godot 宿主。

## 1. 结论

系统大量使用状态机，但此前没有把所有“状态”当成同一个概念处理：

- **显式有限状态机**：过程生命周期、时间状态、订单生命周期。
- **显式阶段状态机**：订单执行会话的主台路径、贪心、转移、从台路径、从台贪心、完成。
- **属性型正交状态**：罐子的形状、液体空满、操作标记、回收标记、所在工作台。
- **派生状态**：世界阶段、关卡结局、可行性结论。
- **过程/命令记录状态**：`Command.Executed`、`OrderEvent.CurrentPhase`、日志序号。

本轮修复了订单状态机的断链：`Order.Status` 现在由 `OrderLifecycleState` 单一映射；
`OrderEvent.Status` 只读订单状态；异步启动会把订单从“待执行”迁到“执行中”。

## 2. 状态机总表

| 状态持有者 | 状态形式 | 状态集合 | 迁移入口 | 是否对外 |
|---|---|---|---|---|
| 订单 `Order` | 显式枚举 + 字符串投影 | Pending / Executing / Succeeded / Failed | `MarkExecuting` / `MarkSucceeded` / `MarkFailed` | `status` 字符串 |
| 过程 `ProcessInstance` | 显式 FSM | Created / Ready / Running / Blocked / Succeeded / Failed / Aborted | `MarkReady` / `Start` / `Block` / `Resume` / `Conclude` | `processes[].state` |
| 执行会话 `OrderExecutionSession` | 显式阶段机 | MasterPath / MasterGreedy / Transfer / SlavePath / SlaveGreedy / Done | `AdvanceOneUnit` 内部阶段迁移 | 通过过程进度/日志投影 |
| 时间 `WorldTime` | 显式 FSM | NotStarted / Running / Paused | `OnAdvanced` / `Pause` / `Resume` / `Reset` | 当前未直接进 state |
| 世界阶段 `JarSystem.Phase` | 派生状态 | Setup / Running / Settled | 无 setter；按结局和活动过程派生 | `phase` |
| 关卡结局 `LevelGoal` | 派生状态 | InProgress / Won / Lost | 纯函数判定 | `level.outcome` |
| 可行性分析 | 三值结果 | feasible / infeasible / undetermined | 求解器与预算结果 | `feasibilityResult` |
| 罐子内容 | 正交属性 | 空 / 满，液体名 | `PourIn` / `ClearLiquid` / `RestoreLiquid` | `jar.liquid` |
| 罐子形状 | 值状态 | 词表内的形状 | `Reshape` | `jar.shape` |
| 罐子操作锁 | 布尔状态 | Unmarked / Marked | `Mark` / `Unmark` / `ClearMarks` | `jar.isMarked` |
| 罐子生命周期 | 显式/组合生命周期 | Created / Warehouse / Workshop / Delivered / Discarded / Recycled | 生产、流入、交付、溢出、对象池 | 部分由资源列表/丢弃计数可见 |
| 命令 | 二态 | not executed / executed | `CommandExecutor.Execute` | 命令历史 |
| 执行阶段 `OrderEvent.CurrentPhase` | 显式阶段指示 | none / master / slave | `Start` / `AdvanceToSlavePhase` | 事件报告/执行段 |
| 修饰器 | 时间段状态 | outside / live / expired | tick `Expire`、作用域 Dispose | 行为结果 |
| 工作台位置职责 | 派生约束状态 | 主台 / 空闲工具位 / B 类占用中 | `SetSlaveIndex`、B 类开始/收尾 | `currentMaster` / `currentSlave` / 不变量 |

## 3. 罐子不是一个单一状态

把罐子压成一个枚举会丢失信息。正确的模型是正交状态：

```text
罐子
├─ 形状：圆罐 / 方罐 / …
├─ 内容：空 / 酒 / 蜜
├─ 操作锁：未标记 / 已标记
├─ 位置：仓库 / 主台 / 从台
└─ 对象生命周期：活跃 / 已交付 / 已丢弃 / 池中复用
```

其中：

- **空/满**决定能否倒液、能否用自身液体改形；
- **形状**决定需求匹配和可改形目标；
- **IsMarked** 是“当前执行阶段不可再次取用”的排他锁；
- **位置**决定资源归属和转移/回滚路径；
- **Recycled** 是对象池安全标记，不是玩家可见的罐子语义状态。

`IsMarked` 不是“曾经操作过”的永久历史。开始订单、切阶段、交付、失败都会清标记。
完整视图见 `UML/06_State_罐子操作.puml` 与 `UML/20_State_罐子完整生命周期.puml`。

从台不是普通的第二资源容器。它只在 B 类订单期间占用资源，退出时回到“空闲工具位”；
没有运行中的 B 类订单却仍有资源，属于 `SLAVE-RESIDUAL-WITHOUT-B-ORDER`。

## 4. 一次订单执行的并行状态轴

订单执行不是一条直线状态，而是四条同时存在的状态轴：

1. **订单状态**：委托是否待处理、被消费、成功或失败；
2. **过程状态**：运行、阻断、恢复、结束；
3. **会话阶段**：主台计划、贪心、跨台转移、从台计划；
4. **罐子操作锁**：本阶段哪些罐子已经被使用。

四条轴相互约束但不应互相复制：

- 订单 `Executing` 不代表过程一定 `Running`，过程可能 `Blocked`；
- 过程 `Succeeded` 之后，订单仍可能因交付检查失败而 `Failed`；
- 会话进入 `Transfer` 时，订单仍处于 `Executing`；
- 罐子 `Marked` 是阶段内状态，订单结束时会清除。

执行单位只由实现动作构成：`POUR_IN`、`POUR_OUT`、`RESHAPE`、`TRANSFER`。
`MATCH` 属于可行性匹配与交付预留，不推进过程；交付本身在所有实现动作完成后原子发生。
因此 A 类订单若开始时就已满足，过程零单位完成；B 类全部必要资源迁移是一个多目标单位，
迁移结束即可在同一单位完成原子交付。

详见 `UML/19_State_订单执行复合状态.puml`。

## 5. 已吸收的游戏/软件架构模式

| 模式 | 当前落点 | 作用 |
|---|---|---|
| Finite State Machine | 订单、过程、时间 | 限制合法迁移，避免任意字段赋值 |
| Hierarchical/Concurrent State idea | 订单执行四轴 | 将订单、过程、会话、罐子锁分开表达 |
| Command Pattern | `Command` / `CommandExecutor` | 原子操作执行、撤销、审计 |
| Memento / Snapshot | `WorkshopSnapshot`、`OrderEvent` | 换台回滚、阶段边界 |
| Event Sourcing / Command Log | `WorldCommand`、`SessionReplay` | 意图日志重建世界 |
| CQRS-like read model | `StateDto` / `StateSerializer` | 世界写模型与页面读模型分离 |
| Observer / Event Bus | `WorldBus`、过程观察者、表现帧 | 领域事实到过程与表现层的通知 |
| Strategy | `ISolver`、`IJarSelectionStrategy` | 可替换求解和罐子选择策略 |
| Decorator | `ModifierAwareSolver` | 临时规则叠加而不改基础求解器 |
| Ports and Adapters | 过程端口、`IWebSocketSink`、宿主接口 | 核心不依赖 Web/Godot |
| Composition Root / DI | `JarSystem`、`JarSystemService`、`Hosting` | 对象装配集中在边界 |
| Object Pool | `JarPool` | 高频短生命周期罐子的内存复用 |
| Data-driven content | `WorldOptions`、关卡、场景 JSON | 内容与规则代码分离 |
| Deterministic simulation | 逻辑 tick、定点速率、种子随机 | 回放、测试与跨宿主一致 |

## 6. 没有盲目吸入的模式

### ECS

当前世界对象少、身份和业务规则强。ECS 的优势在大量同构实体的数据局部性与并行更新；
本系统更接近“少量有身份的加工单元 + 复杂规则 + 可审计状态”，采用 ECS 会增加跨组件不变量成本。
若未来出现数千只罐子/生产槽，可考虑把生产累加器或表现粒子层局部 ECS 化，而不是重写领域层。

### Behavior Tree / StateTree

行为树适合角色 AI 的组合式行为选择。当前“订单执行”是由求解计划驱动的线性过程，
“失败/阻断/恢复”由过程 FSM 管理。引入行为树只会把一条可审计的计划路径变成隐含控制树。

### GOAP / HTN

现有求解器已经在资源变换空间搜索计划，是为“罐子与液体规则”定制的可验证求解器。
GOAP/HTN 更适用于开放世界 NPC 目标组合；把它们叠到当前求解器上会造成双重规划层。

### 完整 Redux/Actor 运行时

本项目由单宿主 Gate 保证确定性。直接引入全局 store 或 actor 并发会改变回放模型；
需要多会话时，更合适的是 world/session 隔离和 epoch，而不是把核心切成异步 actor。

## 7. 仍需补的状态设计与测试

1. 为订单四态建立穷举迁移测试，禁止 `MarkExecuting` 之外的跳过迁移。
2. 为 `OrderExecutionSession` 的阶段迁移增加显式图与非法迁移测试。
3. 将 `OrderEvent.CurrentPhase` 从字符串常量收敛为枚举投影。
4. 为罐子 `IsMarked` 增加“执行层不得重复取用”的集中守卫，避免未来新增路径忘记 `Mark()`。
5. 为 `WorldPhase` 增加更多派生状态测试，尤其“执行中同时回合耗尽”的组合。
6. 在状态投影中增加可行性结论的 `basedOnTick`，解决新鲜度不可见。

## 8. 验证与约束

- 订单契约字符串不变：`待执行 / 执行中 / 成功 / 失败`。
- 过程状态字符串不变：`created / ready / running / blocked / succeeded / failed / aborted`。
- `Order.Status` 与 `OrderEvent.Status` 现在共享唯一状态源。
- 不引入核心 FSM 库：当前状态少、语义强、需要审计与显式守卫，手写枚举与意图方法更可控，
  也符合核心零外部依赖边界。
- UML 状态图需能通过 PlantUML 渲染；已加入索引和验证说明。
