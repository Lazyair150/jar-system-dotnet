# World v2 — 阶段三：订单区域与通用订单委托

## 阶段定位

本阶段在阶段一的持续逻辑时间世界、阶段二的主从工作台岗位之上，建立新世界自己的订单区域。

本阶段需要明确：

- 订单委托是统一的容器对象，不因主动/被动或一次性/持续而产生不同订单类型；
- 订单区域提供装载订单的位置，并管理订单归属；
- 区域有两个相互独立的策略维度：主动/被动、一次性/持续；
- 订单委托自身拥有独立 CD；
- 订单区域中的被动订单按用户排列顺序表达自动调度优先级；
- 订单内容属于具体玩法/世界领域，通用订单区域不解释 A/B、罐子形状或液体。

本阶段**不实现求解器接入、资源预留、调度执行或真实订单执行过程**。这些属于后续阶段。

## 概念边界

### 订单委托不是订单内容本身

`OrderDemand` 是通用订单委托外壳，只负责：

- 独立 ID；
- 持有一个 `IOrderSpecification` 领域规格引用；
- 自己的 CD 时长与剩余时间；
- 判断自身 CD 是否结束。

它不解释规格中的业务字段，不拥有工作台资源，不保存求解方案，也不保存执行过程。

`IOrderSpecification` 是通用订单系统与具体领域内容之间的边界。当前罐子世界使用 `JarOrderSpecification`，由它负责：

- A/B 订单类型；
- 罐子需求列表；
- 形状、液体词表校验；
- 需求数量与顺序约束；
- 需求内容的不可变副本。

因此，未来其他玩法可以提供另一种规格实现，而不需要把新的业务字段塞进 `OrderDemand` 或 `OrderDemandArea`。

当前阶段仍然保留旧罐子玩法的 A/B 与 `Requirement` 规则，但它们已从通用订单委托移入 `JarOrderSpecification`。旧 `Order`、`OrderEvent`、`OrderService` 和旧执行链保持不变。

### 订单区域提供装载位置

订单区域持有多个统一的 `OrderDemand`。订单可以被装入、卸载，也可以在主动区和被动区之间移动。

卸载订单只改变区域归属：

- 不等于销毁订单对象；
- 不等于把订单标记为 Closed；
- 不回滚已经发生的资源消耗或世界变化。

当前模型不再给 `OrderDemand` 增加 Open/Closed 生命周期。区域是否登记该订单，才决定它是否属于当前需求集合。未来若需要“暂停”“撤销”“归档”等独立概念，应先定义它们的业务语义，不能把它们混入卸载操作。

## 区域的两个独立策略维度

### 维度一：主动 / 被动

这个维度决定**谁决定何时启动执行**：

- **被动区域**：需求满足执行条件后，允许系统自动安排执行。
- **主动区域**：即使需求满足执行条件，也等待用户明确选择具体订单后才允许启动。

主动/被动不改变订单规格，不改变求解规则，也不改变成功后的保留方式。

被动区域列表顺序就是用户设置的优先顺序；不另设 priority 字段。主动区域不使用这套自动优先级语义。

### 维度二：一次性 / 持续

这个维度决定**订单成功完成后，区域如何处理这张订单**：

- **一次性区域**：某张订单成功完成后，将这张订单从区域卸载。
- **持续区域**：某张订单成功完成后，仍将这张订单保留在区域中，以便未来再次参与求解和执行。

这里的一次性描述的是“单张成功订单的区域处理方式”，不是“区域只允许装入一张订单”或“区域完成一次后停止工作”。一次性区域仍可继续接收其他订单。

两个维度彼此独立，因此存在四种合法组合：

| 区域组合 | 执行启动策略 | 成功后的区域处理 |
|---|---|---|
| 被动 + 一次性 | 条件满足后自动安排 | 卸载成功订单 |
| 被动 + 持续 | 条件满足后自动安排 | 保留成功订单 |
| 主动 + 一次性 | 等待用户选择 | 卸载成功订单 |
| 主动 + 持续 | 等待用户选择 | 保留成功订单 |

`OrderDemandBoard` 创建时必须分别配置主动区与被动区的成功后处理策略，不使用隐含默认值。

`RecordSuccessfulFulfillment` 只负责按所属区域策略卸载或保留订单。它不负责验证执行过程是否真的成功，也不负责回滚资源；阶段五的执行过程是成功结果的可信报告方。

## 独立 CD

每张 `OrderDemand` 独立拥有：

- `CooldownDurationLogicalMilli`：该订单配置的 CD 时长；
- `CooldownRemainingLogicalMilli`：当前剩余 CD；
- `IsCoolingDown`：剩余时间是否大于零；
- `ReadyForSolve`：该订单自身的 CD 是否已经结束。

订单是否仍装载在订单区域，由 `OrderDemandBoard` 的归属关系决定；因此 `ReadyForSolve` 只表达订单自身 CD 条件，不等于订单一定登记在区域中。

CD 使用逻辑时间，不使用世界时间、宿主帧数或旧 tick。

推进规则：

```text
remaining = max(0, remaining - logicalDelta)
```

`OrderDemandBoard.AdvanceLogicalTime` 将同一逻辑时间增量分发给当前装载的订单。CD 到期后返回刚结束 CD 的订单 ID，阶段四据此触发重新求解。

CD 由明确的领域事件启动：
- 持续订单成功：订单保留在原区域，并启动该订单自己的 CD；
- 执行被工作台替换打断：订单保留在原区域，并启动该订单自己的 CD；
- 普通执行失败：不启动 CD，清理完成后按当前世界重新求解；
- 一次性订单成功：订单直接卸载，不再启动 CD。

CD 时长为 0 时不产生等待，持续订单成功后立即具备下一轮求解资格。

## 成功处理与持续订单的后续触发

本阶段已明确成功后的区域归属：

- 一次性区域：成功后卸载该订单；
- 持续区域：成功后保留该订单。

持续订单成功后保留原订单，并进入该订单配置的 CD。CD 期间求解簿状态为 NotReady；CD 到期事件将订单自动标记为 Dirty。CD 为 0 时直接 Dirty。这里不需要额外的上层 rearm 策略，也不依赖资源变化事件来唤醒订单。

## 与阶段二工作台替换的边界

阶段二的 `IOrderInterruptionPort` 契约要求：成功中断活动订单、让该订单进入自己的 CD，并按 B 类订单规则结算从台临时资源。

阶段三已经建立订单自身的 CD 状态和逻辑时间推进，但**尚无新世界执行过程可供中断**，所以本阶段不伪造一个适配器去调用旧 `OrderEvent.Fail()`。真实适配器必须等阶段五的新 Process 能被调度、停止并结算从台资源时实现。

## 与阶段四、五的边界

### 阶段四：共享快照与求解调度

- 建立一次共享世界快照；
- 对当前装载且 CD 结束的订单规格进行求解；
- 允许多个订单共享同一世界快照，把同一罐子作为候选资源；
- 用世界版本/Dirty 机制识别方案是否过期；
- 执行前验证并预留实际资源；
- 被动区域按用户排列顺序调度；
- 主动区域等待用户明确选择；
- 求解器根据 `IOrderSpecification` 的具体实现解释订单内容，而不是让通用订单区域理解罐子业务。

### 阶段五：执行过程

- 独立 Process 与执行步骤；
- 按逻辑时间推进执行；
- 执行开始时独占预留资源；
- 资源消耗不可默认回滚；
- 执行成功后向 `OrderDemandBoard` 报告成功，由区域策略决定卸载或保留；
- 执行被替换工作台打断时停止过程、进入该订单 CD，并按旧 B 类规则结算从台；
- 将完成/中断结果反馈给需求层与调度层。

## 当前实现边界

已实现：

- 统一的 `OrderDemand` 通用外壳；
- 通过 `IOrderSpecification` 隔离具体玩法订单内容；
- 当前罐子世界 `JarOrderSpecification`；
- 主动/被动与一次性/持续两个独立区域策略；
- 一次性成功后卸载、持续成功后保留；
- 跨区域 ID 唯一、区域移动、被动优先顺序；
- 每张订单独立 CD；
- CD 按 `ResourceWorldRuntime` 的逻辑时间推进。

尚未实现：

- 求解器读取 `IOrderSpecification`；
- 共享世界快照、世界版本与 Dirty；
- 资源预留、调度、执行；
- 真实成功/失败/中断事件；
- 工作台替换对新世界活动执行过程的中断适配器。

## 验收重点

1. 主动区与被动区持有相同的 `OrderDemand` 类型。
2. `OrderDemand` 不直接拥有 A/B、`Requirement`、形状或液体字段。
3. 主动/被动只决定自动启动策略。
4. 一次性/持续只决定成功后区域是否卸载订单。
5. 四种策略组合都可配置，且两个维度互不决定。
6. 一次性成功后订单从区域集合移除，但对象和规格本身不被销毁，也不回滚资源。
7. 持续成功后订单仍留在原区域。
8. 移除订单不等于关闭订单；订单对象没有额外的 Open/Closed 生命周期。
9. 每张订单的 CD 独立推进，CD 到期时准确归零。
10. 资源生产与订单 CD 使用同一份逻辑时间增量。
11. 不改变旧 `Order` / `OrderEvent` / `OrderService` / `OrderExecutor` 的旧世界行为与 JSON/协议契约。

## 仍需在阶段四/五前明确的规则

- 主动区是否允许多个用户选择请求同时排队；
- 主动区是否需要展示排序（不影响被动区自动优先级）；
- `IOrderSpecification` 的具体类型由哪个求解器/领域服务解释。
