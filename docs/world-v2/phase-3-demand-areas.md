# World v2 — 阶段三：需求区域与订单需求模型

## 阶段定位

本阶段在阶段一的持续逻辑时间世界、阶段二的主从工作台岗位之上，建立新世界自己的订单需求层。

本阶段只回答：

- 世界中有哪些需求；
- 需求属于主动区域还是被动区域；
- 需求是一次性还是持续性；
- 需求当前是否允许参与求解（开放且 CD 已结束）；
- 被动需求之间如何表达用户指定的优先顺序；
- 需求如何随逻辑时间推进自己的 CD。

本阶段**不实现求解器接入、资源预留、调度执行或真实订单执行过程**。这些分别属于阶段四、阶段五。

## 既有实现审查结论

旧系统已有 `Order`、`OrderEvent`、`OrderService`、`FeasibilityChecker`、`ISolver`、`OrderExecutionSession` 和 `OrderProcessAdvancer`。

它们不能直接充当新世界需求层：

1. 旧 `OrderLifecycleState` 只有 Pending / Executing / Succeeded / Failed，没有独立 CD。
2. 旧 `OrderEvent` 同时承担旧执行尝试、交付、失败、从台回流等职责。
3. 旧 `OrderService` 以旧 `JarSystem`、旧 `ProcessSystem` 和旧订单集合为入口。
4. 旧可行性结果是旧工作台快照上的缓存，不能直接视为新世界共享快照上的方案承诺。
5. ADR-0003 已规定旧订单生命周期必须只有一个状态源；不能在旧状态字符串旁边再堆一个互相同步的 CD 字段。

因此，新世界采用独立的 `OrderDemand` 需求模型。旧订单、求解器和执行器继续服务旧世界，不在本阶段强行改造或接线。

## 概念与状态归属

| 概念 | 拥有的状态 | 不负责 |
|---|---|---|
| `OrderDemand` | 需求 ID、A/B 类型、不可变需求列表、一次性/持续性、开放/关闭、自己的 CD | 求解、资源占用、执行步骤、工作台库存 |
| `OrderDemandArea` | 一个区域内的需求集合；区域类型决定自动/手动执行策略 | 求解算法、资源预留、执行过程 |
| `OrderDemandBoard` | 唯一的主动区域和被动区域；跨区域 ID 唯一性 | 罐子、液体、工作台资源 |
| `ResourceWorldRuntime` | 将世界时间换算成逻辑时间，并把逻辑时间分发给资源区、需求板 | 直接决定哪张订单执行 |

需求对象不因为拥有 CD、开放状态等多个状态就拆成多个 Manager。这些状态都属于同一张需求的生命周期。

## 主动区与被动区

两个区域持有相同类型的 `OrderDemand`，A/B 需求规则也完全相同。

唯一的策略差异：

- **被动区域**：满足执行条件后允许系统自动启动；多张订单同时满足条件时，按区域中的用户排列顺序决定优先级。区域集合的顺序就是优先顺序，不再另设一个容易漂移的 priority 字段。
- **主动区域**：持续参与后续求解，但不会仅因为可行就自动启动；启动必须来自用户对具体需求的主动选择。

区域策略不改变可行性规则，也不改变需求内容。不要为主动区和被动区复制两套订单、求解或生命周期实现。

被动区域支持在区域内部移动需求位置。主动区域不使用被动区域的自动优先级规则；其具体用户选择与执行请求由后续调度阶段接入。

## 一次性与持续性需求

需求的保留方式是独立于区域类型的另一个维度：

- **一次性需求**：成功交付后关闭，不再参与后续求解。
- **持续性需求**：成功交付后仍保持开放，未来世界资源变化时可以再次满足。
- 用户可以显式关闭仍开放的需求。
- 关闭是终态；本阶段不提供隐式重新打开操作。

因此可以存在“被动 + 一次性”“被动 + 持续”“主动 + 一次性”“主动 + 持续”四种组合。主动/被动不决定需求是否持续存在。

阶段三只定义需求关闭规则与显式完成入口。真实成功交付发生在阶段五；本阶段不伪造交付。

## 独立 CD

每张需求独立拥有：

- `CooldownDurationLogicalMilli`：该需求配置的 CD 时长；
- `CooldownRemainingLogicalMilli`：当前剩余 CD；
- `IsCoolingDown`：剩余时间是否大于零；
- `CanParticipateInSolve`：需求开放且 CD 已结束。

CD 使用逻辑时间，不使用世界时间、宿主帧数或旧 tick。

推进规则：

```text
remaining = max(0, remaining - logicalDelta)
```

`OrderDemandBoard.AdvanceLogicalTime` 将同一逻辑时间增量分发给所有开放需求。CD 到期后，需求自然重新满足“允许参与求解”的条件；阶段四负责在到期时触发重新求解。

CD 只能由显式领域操作进入，例如后续阶段的“执行被工作台替换打断”。**本阶段不擅自规定普通成功或普通失败是否进入 CD**；该规则此前尚未确定。一次性需求成功关闭与 CD 是不同的状态变化，不得把它们合并成一个枚举。

如果 CD 配置为 0，则该需求没有等待时长；不允许负时长。时间推进不得产生负剩余值，也不得影响其他需求的 CD。

## 与阶段二工作台替换的边界

阶段二的 `IOrderInterruptionPort` 契约要求：成功中断活动订单、让该订单进入自己的 CD，并按 B 类订单规则结算从台临时资源。

阶段三建立了需求自己的 CD 状态和逻辑时间推进，但**尚无新世界执行过程可供中断**，所以本阶段不伪造一个“中断适配器”来调用旧 `OrderEvent.Fail()`。真实适配器必须等阶段五的新 Process 能被调度、停止并结算从台资源时实现。

## 与阶段四、五的边界

### 阶段四负责

- 建立一次共享的世界快照；
- 每张开放且 CD 结束的需求独立求解；
- 同一罐子可以同时出现在多张需求的候选方案中；
- 以世界版本/Dirty 机制识别方案是否过期；
- 执行前验证并预留实际资源；
- 被动区域按用户排列顺序调度，主动区域等待用户明确选择。

本阶段不存储求解结果，不把候选方案当成资源预留。

### 阶段五负责

- 独立 Process 与执行步骤；
- 按逻辑时间推进执行；
- 执行开始时独占预留资源；
- 资源消耗不可默认回滚；
- 成功交付、一次性需求关闭、持续需求保留；
- 执行被替换工作台打断时停止过程、进入该需求 CD，并按旧 B 类规则结算从台；
- 将完成/中断结果反馈给需求层与调度层。

## 验收条件

1. 同一需求不能同时登记在两个区域；需求 ID 在整张需求板内唯一。
2. 主动区和被动区持有同一种需求模型，A/B 需求内容校验规则一致。
3. 被动区域位置变更会改变其优先顺序；主动区不套用该自动优先级。
4. 一次性需求成功完成后关闭；持续性需求成功完成后保持开放。
5. 关闭需求不能参与求解；CD 未结束的开放需求也不能参与求解。
6. 每张需求的 CD 独立推进；一个需求进入/结束 CD 不影响其他需求。
7. CD 按逻辑时间推进，暂停/零逻辑时间不减少 CD；跨越 CD 到期点时剩余时间准确归零。
8. 负 CD 时长、负时间推进、重复登记、非法跨区移动等输入必须被拒绝且不产生部分修改。
9. 需求板接入 `ResourceWorldRuntime` 后，资源生产与需求 CD 使用同一份逻辑时间增量。
10. 不改变旧 `Order` / `OrderEvent` / `OrderService` / `OrderExecutor` 的旧世界行为与 JSON/协议契约。
11. 本阶段不产生求解方案、不预留资源、不启动执行过程，也不把旧订单 FAILED 状态映射为 CD。

## 当前未决且不得擅自决定的规则

- 普通成功或普通失败后是否进入 CD。
- 持续性需求成功后是否立即重新求解，还是由世界变化/调度事件触发。
- 主动需求是否允许同时存在多个用户选择请求（执行互斥将在阶段四/五定义）。
- 主动区内部是否需要展示排序；它不影响被动区的执行优先级。
