# 4.10b-9c2：将选定准备操作纳入有序程序

> 状态：显式准备操作分配已纳入符号程序，并可交给 9c 资源模拟器；尚未自动枚举所有准备操作组合，也尚未绑定真实 Jar 库存。准备 Jar 必须与最终需求 Jar 身份不同。

## 为什么单步候选还不够

规则候选 Profile 已经包含 `PreparatoryOperations`，目前主要是通用 `PREPARE_POUR_OUT`。但此前的直接候选投影只接受每条需求的候选，刻意拒绝把 `RequirementIndex = -1` 的准备操作伪装成需求步骤。因此，准备操作虽然已被目录发现，却还没有进入订单程序。

本切片增加 `WorldOrderPreparatoryProgramBuilder`，显式接收：

- 一组每需求恰好一个的直接候选解；
- 若干 `WorldOrderPreparatoryOperationAssignment`，指定岗位、抽象 JarKey 和准备候选；
- A/B 类及主从岗位身份。

每个准备分配必须来自目录中的 `PREPARE_POUR_OUT` 候选，且每个抽象 Jar 在本切片最多分配一次准备操作。**准备 Jar 不得同时作为最终需求 Jar**：成功准备操作会设置订单级 Mark，不能再由同一 Jar 执行最终需求操作。

## Jar 与岗位时序

- 所有订单 Jar 在开始时均属于主台；从台不能凭空创建初始 Jar。
- 主台准备操作先于主台需求操作和唯一 handoff。
- handoff 一次性将从台需求所需 Jar，以及指定在从台执行准备操作的 Jar，批量迁移到从台。
- 从台准备操作只能在 handoff 之后执行。
- 若某需求的 Jar 先被准备操作处理，准备输出的形状/液体必须与该需求候选的输入事实完全一致。
- Jar 的身份保持不变，状态版本逐步增加；每次状态版本只能被消费一次。
- 不允许 Jar 已经进入从台阶段后再回到主台执行准备操作。

准备操作可以单独产生游离液体，也可以直接准备某条需求使用的 Jar。对于从台需求，既支持主台先 PourOut 再把空 Jar 与液体一起通过唯一 handoff 迁移，也支持先迁移满 Jar、再由从台 PourOut 供给从台后续操作。

## 资源模拟连接

生成的程序沿用 9c 的资源模拟器：

- Master 与 Slave 仍使用完全独立的 staging 账户。
- 每个 PourOut 的产液在执行岗位的实际容量/拒收规则下接收或丢弃。
- 后续步骤只能消耗此前真正接收的余额。
- 主台产液若要供从台使用，必须在唯一 handoff 节点提供固定交接向量；从台准备操作产液则可直接供给更晚的从台步骤。
- B 类 handoff 仍然且只能执行一次，不会因为有多个准备操作而重复。

## 本切片的边界

这是“显式选定的准备操作 → 有序程序 → 顺序资源模拟”，不是完整自动搜索。调用方仍须选择准备操作和 JarKey；本切片不从实际库存自动挑选可执行的 Jar，也不枚举不同准备操作集合、不同 Jar 绑定或全部合法操作顺序。

下一步应把可用 Jar 库存作为独立绑定输入，枚举有限的准备操作/需求 Jar 组合，并在每个候选程序上计算所需的一次性交接液体向量。交接向量必须同时满足 Master 在 handoff 时刻的实际余额、Slave 的 staging 容量和拒收规则；不能把两个岗位的液体账户合并。
