# World v2 阶段四 4.3：方案持有与失效状态

## 目标

在 4.2 的规格求解适配器之上，补齐两个缺口：

1. 可行结论必须持有完整、不可变的求解计划，而不只是步骤数量。
2. 每张订单需要明确的求解状态，且需求板变化和世界快照版本变化不能让旧方案继续被当作当前方案使用。

本阶段不启动执行、不预留或消耗资源，也不实现主动/被动执行优先级。

## 求解计划

`WorldOrderSolvePlan` 是旧求解器可变路径对象的深拷贝投影：

- A 类：保存主台单阶段路径。
- B 类：分别保存主台路径、从台路径、转移罐子 ID、转移液体账目。
- 每一步复制需求值、操作值、操作前后罐子值、操作后液体账目。
- 所有集合和字典均为只读副本；不保留 `SolverStep`、`JarState`、`Workshop` 或真实 `Jar` 的可变引用。
- 计划本身不重复保存世界版本；它必须通过外层 `WorldOrderSolveResult.WorldVersion` 绑定到求解输入版本。

只有 `Feasible` 结果允许携带计划；没有计划的可行结果在构造时即被拒绝。若底层求解器声称可行却没有提供路径，适配器返回 `Undetermined`，不制造空计划。

计划是求解输出，不是执行许可。执行前仍需核对订单仍登记、结果版本仍匹配当前世界，并完成资源预留。

## 每张订单的求解状态

`WorldOrderSolveBook` 为需求板中的订单维护一条记录：

| 状态 | 含义 |
|---|---|
| `Dirty` | 没有可直接使用的当前结论，需要重新求解 |
| `Current` | 持有针对某个世界版本的求解结论 |
| `NotReady` | 订单仍处于 CD，不能求解 |
| `Detached` | 订单已不在需求板中，旧计划被清除 |
| `AwaitingRearm` | 持续订单刚完成；等待上层策略决定是否及何时再次参与求解 |

`Current` 不等于可执行。读取结果时还会核对需求板归属、CD 和当前 `WorldSnapshot.Version`。版本不匹配时立即丢弃结果并转为 `Dirty`。

## 自动失效规则

需求板发布不包含玩法细节的结构变化通知：

- 新订单加入 → `Dirty`。
- 订单从主动区移到被动区或反向移动 → `Dirty`。
- 订单被卸载（手动删除或一次性成功）→ `Detached`，清除计划。
- 订单 CD 到期 → `Dirty`。
- 被动区顺序变化 → 不使求解结论失效；它改变的是未来调度顺序，不改变同一世界快照下的求解输入。
- 持续订单成功后仍保留 → `AwaitingRearm`，清除旧计划，不自动重新求解。

世界变化使用快照内容版本判定，而不是根据操作名称猜测。调用方在读取或求解时提供最新快照：若版本不同，旧结论即被失效。这样不需要每帧求解，也不要求每个资源写入点都手工通知求解簿。

## 持续订单边界

目前没有决定持续订单成功后是立即重新求解、等待资源变化、等待 CD，还是等待用户操作。

因此：
- 成功后进入 `AwaitingRearm`；
- 普通世界变化和全局 Dirty 不会自动唤醒它；
- 只有上层策略明确调用 `MarkDirty(demandId, reason)` 才重新参与求解。

这保留了策略决策点，不会把持续订单做成成功后立即无限重复的循环。

## 主动/被动边界

求解簿不决定执行启动：
- 主动/被动使用相同求解规则和同一结果类型；
- 被动顺序变化通过需求板通知暴露给未来调度器，但不污染求解缓存；
- 主动与被动之间的执行优先级仍未定义。

## 测试范围

新增测试覆盖：
- 可行 A/B 结果携带完整计划；
- 求解路径和转移账目被深拷贝，原对象后续修改不影响计划；
- 计划集合/字典不可修改；
- 新增、移出、跨区移动、被动顺序变化的失效差异；
- 世界版本变化使旧结论不可读取；
- CD 到期触发 Dirty；
- 一次性订单成功后 Detached；
- 持续订单成功后 AwaitingRearm，只有显式策略调用才能重新 Dirty；
- 全局失效不绕过持续订单的 AwaitingRearm。

## 尚未实现

- 自动扫描 Dirty 订单的统一调度器；
- 被动订单按列表顺序自动选择；
- 主动订单的显式选择入口；
- 主动/被动之间的优先级策略；
- 执行开始前的原子版本确认与资源预留；
- 执行期间资源独占、执行中断与完成报告。

这些属于后续阶段，不由求解簿擅自决定。
