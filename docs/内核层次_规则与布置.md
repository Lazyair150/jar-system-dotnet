# 内核层次审查：哪些是「规则」，哪些是「布置」，哪些只是「实现细节」

> 触发：`User said (m00804)` —— 「关于卡槽上限、初始工作台配置以及自动生产资源……这都是偏向于实际的
> 布置设计，就像原本的规则是底层逻辑，而布置的工作台是什么样，液体生产速率怎么样，是否按照回合制
> 生产……这类应该独立出内核的固定吧？有什么纠缠让它不可以独立出来？还是说大量的模块过于依赖于
> 这些初始设定？比如可有可无的 20 上限之类？需要全面审查。」
>
> 本文给出**结论先行**的答案，并把每条判定的依据落到文件与行号，便于复核与反驳。

## 0. 一句话结论

**布置（工作台长相、生产速率、初始库存、液体流入量）已经全部是数据，不是常量**——它们住在
`WorldOptions` / `config/world.json`，`Constants` 里的 `20` / `30` 只是**缺省值**，任何工作台都可以在
装配期覆盖。真正「写死在内核、且不该写死的」只有两处：**仓库容量 200** 与**卡槽上限（缺失）**。
另有两条**必须**继续写死在内核（`MAX_PRODUCER_RATE`、`MAX_ORDER_REQUIREMENTS`），理由见 §4。

## 1. 三分法的定义

| 层 | 定义 | 判据（问一句话） | 该住哪里 |
|---|---|---|---|
| **规则** | 世界的物理与因果：什么操作合法、代价是什么、失败了会不会回滚 | 「换个关卡，这条还成立吗？」**成立** ⇒ 规则 | 内核，编译期固定；参数化也只能由内核执行校验 |
| **布置** | 这一次的配置：几台工作台、各自标记/禁令/容量、产线产什么多少、开局给什么 | 「换个关卡，这条会变吗？」**会变** ⇒ 布置 | 装配期数据（`WorldOptions` / `world.json`），运行期经命令改 |
| **实现细节** | 缓冲上限、搜索预算、日志容量 | 「玩家能感觉到吗？」**不能** ⇒ 实现细节 | 可留在内核，但应可注入/可覆盖，不许外溢成玩法约束 |

### 2.2 真缺口：该是「布置」却写死或缺失的

| # | 缺口 | 证据 | 后果 |
|---|---|---|---|
| G1 | **仓库容量 200 写死** | `Config/Constants.cs:20-21` `WAREHOUSE_MAX_JARS=200` / `WAREHOUSE_MAX_LIQUIDS=200`；`WorldOptions` **没有** warehouse 字段（`config/world.json` 里 `warehouse` 也是 `null`） | 「仓库多大」是纯玩法布置，却只能改代码 |
| G2 | **卡槽上限根本不存在** | 内核里生产者是 `ProducerModule` 的 `Dictionary<string, ShapeProductionLine>`（`Production/ProducerModule.cs:128/152`），没有「只能有 N 条产线」的概念；`MAX_LINES=3` 只存在于 `demo/puzzle_data.js` | 「布置产线卡」的**上限**无处安放；页面自己限 3 会被别的客户端绕过 |
| G3 | **运行期换整套工作台能力无命令** | `Domain/Workshop.cs:100` `ReplaceCapability(WorkshopCapability)` 已存在，但 21 条命令里没有对应 case | 只能在装配期决定 base/add/ban；运行期只能改容量 |
| G4 | **订单排序无命令** | `Order.Priority` 字段在，但无 `moveOrder` 类命令 | 执行顺序只能靠创建顺序 |

## 3. 两个「看起来像纠缠、其实不是」的地方

**① 求解器里的 `MaxJars = 20` / `MaxLiquids = 30`（`Abstractions/SolverContracts.cs:54-55`）**
这不是硬编码的世界容量，而是 `WorkshopInfo` 的**默认值**；真正喂给求解器时由
`Orders/Feasibility/FeasibilityContext.cs:51-52` 从**工作台快照**投影：

```csharp
MaxJars = snap.MaxJars,
MaxLiquids = snap.MaxLiquids
```

⇒ 求解器看到的就是真实工作台的容量，**没有第二份真相**。这条不构成「模块依赖初始设定」。

**② 回合制/节拍**
内核只有 tick，没有「回合」。回合是**宿主的批量语义**：`manualTick`（一批推进）+
过程 `TicksPerStep`（一步跨几刻）。`TickIntervalMs=2000` 属于 Web 宿主，不在核心。
⇒ 「是否按回合制生产」不需要改造内核，它已经是可调参数（`FlowOptions` 决定每 tick 多少，
`TicksPerStep` 决定过程每步多慢，宿主决定一回合推几次 tick）。

## 4. 两条「必须写死在内核」的（不要挪出去）

| 常量 | 为什么必须住内核 |
|---|---|
| `MAX_PRODUCER_RATE = 100`（`Config/Constants.cs:26`） | 代码注释已写明：这是**游戏规则**不是输入校验。只写在 Web 层的话，别的宿主（Godot/脚本）可以提交 1e9，把产出循环变成 OOM（实测 20 万/tick 即造 20 万个罐子）。 |
| `MAX_ORDER_REQUIREMENTS = 10`（`Config/Constants.cs:22`） | `规则.txt:29-30` 明写它是「用于约束可行性分析的搜索规模」——`PartitionSearch` 是 2^N 划分搜索，需求数直接决定判定成本。它是**判定可行性的护栏**，不是布置。 |

两者都可以「参数化」，但参数**必须由内核执行校验**；一旦交给界面，就只有界面遵守。

## 6. 「可有可无的 20 上限」到底可不可有

可无 —— 它只是默认值，不是规则；真正决定玩法的是 `config/world.json` 里每台工作台的
`maxJars` / `maxLiquids`（现在 4 台都显式给了，绕过了 20/30 缺省）。所以这里的答案不是"删掉 20"，
而是**把缺省值降级成"没有显式配置时的兜底"并写进文档**（现状已是如此，只是没人知道）。
