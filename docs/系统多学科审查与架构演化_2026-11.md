# 系统多学科审查与架构演化

> 日期：2026-11-03
> 基准：当前未提交工作树；完整门禁 `VERDICT=OK` + `QUALITY-OK`。
> 证据优先级：源码与测试 > `CONSTRAINTS.md` > 交接报告 > 历史设计文档。

## 1. 结论

当前系统不是“没有架构”，也不是“每个界面卡都对应一套后台逻辑”。它已经形成了可验证的
事件溯源核心：配置装配世界，命令改变世界，逻辑 tick 推进世界，`StateDto` 投影世界，Web/Godot
只负责输入输出。真正的历史问题主要是：

1. **语义没有完整投影**：后台存在的生产源、产线、库存和流入，在页面上被压缩成不完整的卡片，
   导致玩家建立了错误心智模型。
2. **局部实现与声明不一致**：生产源可能只进入状态而未挂到真实产线；未知液体曾被静默忽略。
3. **运行时和外围资产混在一起被误认为臃肿**：归档原型、替代求解器、测试基准与默认运行链路
   的职责不同。
4. **主从位置职责曾未进入领域模型**：从台被错误地当作第二仓库，允许已有资源并只按转入账目
   回滚，导致工具罐倒出的游离液体残留。
5. **少数边界仍是显式技术债**：液体名硬编码、事件历史弱类型、Godot 内容装配差异、缺少
   world epoch 的表现帧。

本轮已经修复前两类中可安全闭环的问题，并把后两类写成了有验收条件的演化路线。

## 2. 审查方法

- 对每个概念同时检查：领域实体、写入入口、推进阶段、状态投影、前端消费、回放/测试。
- 使用 `ArchitectureTests` 检查核心命名空间只向下依赖。
- 使用 `CONSTRAINTS.md` 检查契约、回放、可移植性和质量地板。
- 使用浏览器冒烟检查真实 DOM、交互、换关和 WebSocket 通信。
- 只把有源码、测试或运行证据的问题列为缺陷；抽象偏好列为设计建议。

## 3. 哲学与认识论

### 3.1 世界事实与界面解释必须分开

系统采用三层本体：

1. **意图**：玩家下发的命令；
2. **世界事实**：资源、订单、过程、命令日志、逻辑 tick；
3. **解释投影**：`StateDto`、帧、生产卡、日志措辞。

旧生产卡把“液体自产为 0”和“仓库向主台搬运库存”合并成一个视觉结论，这是认识论错误：
它让玩家把“没有新生产”误读成“资源不应移动”。修复后，事实与解释各自有明确字段。

### 3.2 因果链必须可观察

一次推进的因果链是：

```text
逻辑 tick
  → 形状线 / 液体产能
  → 中央仓库库存
  → 仓库到主台搬运
  → 工作台状态变化
```

生产增加库存；流入只改变库存位置。模型必须保留这个差异，否则界面会诱导玩家修改错误参数。

### 3.3 确定性优先于便利性

世界变化必须能从“初始配置 + 种子 + 命令日志”重建。由此推导出：

- 墙钟只用于事件记录，不参与判定；
- 不引入核心自有线程；
- 浮点产能通过千分之一定点累加；
- 过程和命令日志保持可重放；
- 页面不能自行计算业务结论。

## 4. 结构学与依赖关系

核心采用从数据到组合根的层序，机器规则要求依赖只向下：

```text
Config
  → Domain
  → Abstractions
  → Rules / Production / Solver / Commands
  → Orders / Process
  → Services / Sessions / Executor / World
  → Bootstrap
```

这不是“层越多越好”，而是将变化原因分开：

- 词表、容量、内容变化在 Config；
- 资源不变量在 Domain；
- 求解算法变化在 Solver；
- 时间与过程生命周期在 Process；
- 宿主协议与并发在 Web/Godot；
- 页面只消费投影并发送命令。

`JarSystem` 是统一门面而不是业务真相；本轮将时间、tick、产出配置和重置拆到
`JarSystem.Runtime.cs`，主文件从 1116 行降到 935 行。

## 5. 面向对象与职责分配

| 组件 | 主要责任 | 输入 | 输出 | 禁止事项 |
|---|---|---|---|---|
| `WorldOptions` | 数据化世界内容 | JSON | 配置快照 | 决定运行时行为 |
| `JarSystem` | 公开用例门面与组合根 | 意图调用 | 状态变化/结果 | 承载页面措辞 |
| `ProducerModule` | 形状生产源与产线 | 速率、tick | 新罐入仓库 | 直接操作工作台 |
| `LiquidProduction` | 液体速率与累加 | 速率、tick | 新液入仓库 | 读取订单/工作台 |
| `Warehouse` | 库存与流入 | 新资源、主台 | 搬运结果 | 生成新资源 |
| `ProcessSystem` | 过程状态机与时间管线 | tick、工作体 | 过程日志/状态 | 直接渲染 UI |
| `StateSerializer` | 只读 DTO 投影 | 活世界 | `StateDto` | 修改世界 |
| `CommandDispatcher` | 协议适配与输入分派 | WebSocket 报文 | 用例调用/回包 | 复制领域规则 |
| `production-view.js` | 生产/流入表现 | `producerStatus` | HTML | 网络、命令、业务推导 |

面向对象上的关键改进是**让声明与实体一致**：状态里显示某生产源已开工，就必须真的挂到
`ShapeProductionLine`；显示流速为 0，就不能暗示不会发生仓库搬运。

### 剩余结构张力

- `JarSystem` 仍是较宽的统一门面，但公开 API 稳定比内部“拆散入口”更重要；后续应按用例组合，
  而不是为了行数继续拆 partial。
- `Workshop` 同时持有资源与能力规则，规模仍较大；若未来出现独立编辑器，可拆出资源账本。
- `StateDto` 与领域对象存在字段映射重复，这是防腐层成本，不是无意重复。

## 6. 交互、信息流与沟通

信息流固定为：

```text
HTTP/WS 输入
  → 协议校验
  → 串行 Gate
  → JarSystem 用例
  → 世界变化 + 命令/过程日志
  → StateSerializer
  → 广播 StateDto
  → 页面重建显示
```

本轮补强：

- 多客户端世界变化广播；
- 换关时先广播 `world` 再广播 `state`；
- 后台 tick/自动分析在拿锁后重新读取当前世界；
- 场景事件源与 WorldBus 组合，避免启用场景后总线失效；
- 生产卡显示槽位、真实速率、累加器、仓库库存与流入上限；
- 浏览器冒烟修复异步清理，应用断言成功后退出码为 0。

交互准则：**命令与状态由内核负责，页面只负责用户可理解的组织与反馈**。页面失败时必须显示
内核原因，不能把拒绝伪装成成功。

## 6.1 状态机与状态轴

系统在多个层级使用状态机：

- 订单生命周期：待执行 → 执行中 → 成功 / 失败；
- 过程生命周期：Created → Ready → Running ↔ Blocked → 终态；
- 执行会话：主台路径 / 贪心 / 转移 / 从台路径 / 从台贪心 / 完成；
- 世界时间：未开始 / 流动 / 暂停；
- 世界阶段与关卡结局：派生状态；
- 罐子：内容空满、操作标记、所在位置和对象池生命周期是**正交状态轴**。
- 工作台位置职责：主台接收仓库流入；从台是 B 类订单临时工具位，开始前为空、结束后排空。

本轮把订单执行中的状态断链修复为单一来源：`Order.Lifecycle` 是权威枚举，
`Order.Status` 是 JSON 契约投影，`OrderEvent.Status` 只读取它。

完整清单、模式吸收评估与未采用模式见
`docs/状态机与游戏架构模式吸收评估.md`；
状态图见 `UML/19_State_订单执行复合状态.puml` 与
`UML/20_State_罐子完整生命周期.puml`。

本轮同时收敛了从台生命周期：`SetSlaveIndex` / `SetSlave` 拒绝有资源的候选工作台，
B 类可行性分析只从空从台出发；执行结束后由 `SlaveRollback` 排空从台全部剩余罐子和游离液体。
因此“必要转移后仍剩罐子”的合法来源只剩工具罐，且它必须在终态回到主台。

## 7. 游戏设计与心理学

### 7.1 心智模型

玩家需要区分：

- 产线在生产什么；
- 仓库已有多少；
- 每回合会搬多少；
- 工作台实际接收了多少。

这四件事同时可见后，“为什么还能进液体”不再需要猜。生产卡现在显示“自产 0、仓库库存 X、
流入上限 Y”，比一句“产率为 0”更符合因果直觉。

### 7.2 控制感与可预测性

- 非快捷档位的初速用“当前值”标识，避免出现“没有任何按钮亮着却已开工”。
- 槽位显示 `used/limit`，让“2 条开工”有明确边界。
- 零生产源形状只做摘要，减少视觉噪声。
- 流过仓库与生产使用不同措辞，防止玩家误以为所有增长都来自速度卡。

### 7.3 认知负荷

- 形状线、液体卡、订单卡、执行中段各有稳定职责。
- 剩余为零的形状线不再生成 6 张空卡。
- 错误与成功状态都用文本，不仅依赖颜色。
- 动态提示使用 `aria-live="polite"`；生产说明使用 `role="note"`。

### 7.4 失败心理学

系统保留“失败要付代价”“已完成步骤不回滚”的规则。界面应展示代价和原因，不应通过自动回滚
抹平玩家的决策后果。胜利状态不可因删除历史订单而回退，避免“赢了又变没赢”的失信体验。
“从台残留”也不是隐含玩法：正常终态必须排空，异常残留由世界不变量显式报告。

## 8. 简化与规模判断

默认源码（排除 `bin/obj`）约 17.5k 行，其中：

- `JarSystem.cs` 935 行，`JarSystem.Runtime.cs` 149 行；
- `play.js` 676 行，新增 `production-view.js` 113 行；
- 源码包含三个页面控制器、两个宿主、15 个核心命名空间和完整测试。

“源码多”不等于“运行时臃肿”：

- `demo/_退役` 是归档，不编译；
- `MatchingSolver`、参考求解器和基准工程不是默认链路；
- 8 条形状线对象保留用于稳定投影，但无正速率时不参与 tick；
- 罐子选择策略按需实例化；
- 两个 `BackgroundService` 是宿主调度设施，不进入核心回放。

## 9. 安全与信任边界

当前系统的安全定位是**本机单用户开发/游玩壳**，不是公网多租户服务。

已有控制：

- 默认绑定回环地址；
- Host 白名单与 Origin 检查；
- WebSocket 最大帧和最大连接数；
- 场景请求体 1 MiB 上限；
- 场景文件原子写入；
- 外部 JSON 未知键拒绝（关卡和场景路径需继续审查）；
- 输出 HTML 转义；
- 核心无网络、文件或框架依赖；
- 命令日志与回放用于审计。

仍需注意：

- 本地回环不是身份认证；同机恶意进程仍可访问；
- 当前页面使用内联事件处理器，未启用严格 CSP；
- 没有公网部署所需的认证、授权、速率限制与共享会话存储；
- 表现帧仍是无载荷 fire-and-forget，跨 world 的极端乱序需要 epoch；
- 存档、场景、关卡均应按不可信输入继续做大小、深度和引用完整性限制。

## 10. 可扩展性

已存在的扩展点：

- `ITickHandler` / `WorldScheduler`：增加时间驱动阶段；
- `IWorldEventSource` / 场景事件：增加世界事件；
- `IRuleModifier`：增加临时规则；
- `ISolver` / `IWorkBudgetedSolver`：替换可行性算法；
- `IProcessAdvancer`：增加新过程类型；
- `IPresentationSink`：增加新表现宿主；
- World JSON：内容化工作台、生产者、订单模板和关卡；
- `producerStatus`：增加稳定读模型，而不是让页面反向猜规则。

限制扩展的地方：

- 液体名仍在若干求解/执行路径中硬编码；
- 事件历史的弱类型值联合仍阻止完全 schema 收紧；
- Godot 尚未接 Web 的配置文件、关卡与场景内容；
- 帧与快照缺少 world generation 标识。

## 11. 演化路线

### P0 已完成：正确性与可观测性

- 生产、自产、流入分离；
- 生产源与真实产线一致；
- 换关/多客户端/场景总线/回放修复；
- 生产卡重做；
- 完整门禁与浏览器冒烟。

### P1 契约收敛

- 将液体词表贯穿所有求解与执行路径；
- 把 `eventHistory` 收紧为封闭事件联合；
- 为可行性结果增加逻辑 tick 新鲜度；
- 目标：移除 `loose=1` 和液体名硬编码，重新建立契约基线。

### P2 宿主对齐

- Godot 加载与 Web 相同的世界/关卡/场景入口；
- 抽取共享的关卡装配器；
- 将浏览器冒烟纳入正式 CI 或明确标注为非门禁。

### P3 多会话与表现时序

- 为快照和帧增加 `worldEpoch`；
- 支持多世界/会话隔离；
- 让表现帧具备可丢弃、可重连的明确一致性语义。

### P4 内容与运营

- 关卡编辑、场景热重载、平衡数据面板；
- 遥测只记录匿名玩法事件，不记录个人信息；
- 形成可回归的关卡可解性与难度指标。

## 13. 最终判断

架构方向是清楚的，不需要推倒重建；需要继续做的是**把边界变成可观察事实、把事实变成稳定
契约、把契约变成机器门**。当前最大风险不是类数量，而是同一概念在后台、状态和页面各有一套
不完整解释。生产/流入修复消除了这一类风险的典型实例，后续应沿用同样方法处理液体词表、
事件联合和 world epoch。
