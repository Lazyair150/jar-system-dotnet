## 3 唯一的真歧义：满罐改形自耗算不算"使用液体"

`ReshapeFull` 现在是"罐里有液体就自耗它"，这跟工作台液池无关。两种读法：

- **读法 A（我倾向）**：自耗的是**罐内**液体，不经过工作台液体槽 ⇒ 不算"使用液体" ⇒ 禁液满罐照样能改形。
  好处：与"槽"的比喻一致（槽里的是可取的，罐里的是自带燃料）；坏处：与今天的实现相反，且"禁酒"变得比今天宽松。
- **读法 B**：改形是一次"使用" ⇒ 禁液满罐不能改形（= 今天的行为）。
  好处：与今天兼容；坏处：禁令又渗回"操作合法性"，与"只限制取用"的初衷不一致。

**这一条必须你定**，因为它是玩法语义，不是实现细节。我给的默认是 A，理由是它让"禁令"只有一种含义（不能取用），而 B 会让禁令同时管两件不同的事。

## 5 为什么 2b 不能省

今天的 `SOLVER-OK (compared=4003, agree=4003, undetermined=0)` 之所以干净，是因为"池里出现的液体一律可用"这个假设与"禁液存不进"这条规则**互相支撑**。步骤2 一旦放开存储，这个假设就变成**假前提**：池里可以有不能用的液体。
于是"容量是否够"这类下界会把禁液算成可用资源 ⇒ 误判可行 ⇒ 玩家看到"可行"，执行时却失败。
**这类错误的形态与上次 `IsBanned` 挡在 MATCH 之前（105 例错杀）正好相反**：那次是错杀（可行判成不可行），这次可能变成**放行**（不可行判成可行）。放行更难被发现，因为报错发生在执行时。

### 7.1 两处预期之外的发现

**① 规则表的 `PourOut` 少了禁令这一问（差分对拍当场抓到）。**
`RulebookAgreesWithExecutionOnEveryCombination` 报：
`玄武台 形状=圆罐 罐内=酒 已操作=False 账目=[] 操作=pour_out 规则表=True 执行=False`。
原因：`CanStore` 以前顺手承担了"禁液不能倒出"的职责（它当时既问禁令又问容量）。
语义拆开后，规则表就少了一问。修法**不是**把禁令塞回 `CanStore`（那正是这次要拆的那两件事），
而是在 `PourOut` 分支显式两问：`Check(liquid)` + `CanStore(liquid, 1, have)`。
教训：把一条规则拆成两条时，凡"借用"过它的地方都会露出来 —— 这正是差分对拍存在的意义。

**② 契约快照动了 3 行，但回放字节**一字未变**。**

```
- state.workshops[0].liquids.酒 = 0
+ state.workshops[0].liquids.酒 = 2
- state.warehouse.liquids.酒 = 23
+ state.warehouse.liquids.酒 = 21
- state.producerStatus.warehouse.liquids.酒 = 23
+ state.producerStatus.warehouse.liquids.酒 = 21
```

三行是同一件事：玄武台禁酒，但酒现在能流进去（仓库里那 2 份搬到台上了）。
行数仍是 226，schema（11 类型 / loose=1）与 `contract.d.ts`（degraded=0）都没动。
`REPLAY-OK (commands=33, stateBytes=3146, logBytes=8797, journalBytes=725)` **逐字节未变** ——
因为回放脚本那份世界从来不把酒送进禁酒的工作台。这两条合起来说明：
**改的是"被禁液体能不能存在"，不是"世界状态的结构"**。

### 7.2 仍未做的 2b（以及为什么不能省）

求解器现在仍假设"池里出现的液体一律可用"。这在改动前是**真的**（禁液进不来），
改动后是**假的**（禁液能进池子、但取不出）。所以：

- `StateSpaceSolver` 的候选生成不会误用禁液（它按 `_banned` 生成操作），这一层是安全的；
- `SolverPrecheck` 的容量/预算类下界若把池内液体总量当可用资源，就会**误判可行**（放行）。
  这类错误的形态与上次 105 例"错杀"相反，且更难发现（报错发生在执行时）。
- 所以 2b 要做两件事：①求解器接 `LiquidRules` 纯规则层；②`SolverPrecheck` 把"禁用中的液体"
  单独计（不参与预算），并**先写一条红测试**证明旧下界会放行。

## 8 2b 的实测结论：**误判可行没有发生**，但"什么是活性液体"确实需要重新定义

动手前我在 §7.2 写下担心（用户随后也指了出来）：液池里存着 2 份禁液，
求解器会不会把它当成 2 份可用液体、从而误判可行。查完代码 + 写完测试之后，
结论分两半，**两半都要记下来**。

### 8.1 三个实现都没误判，原因是"决定性那一行"各自挡着

`SolverPrecheck` 在结构上只有两种结局：**证明不可行**、或**委托给搜索**。
它不会自己断言"可行" —— 所以"误判可行"不可能来自它；它的错误只可能是"错杀"，
而那个方向被 `test/SolverBench` 的健全性检查盯着。

真正能断言可行的是搜索侧。实测三处都在挡禁令：

```
Solver/StateSpaceSolver.cs:285   if (!st.IsBanned(liquid) && …IsBaseMarked(shape))        // POUR_IN 候选
Solver/StateSpaceSolver.cs:340   if (st.IsBanned(st.Jars[i].Liquid!)) return false;       // 成本支付
Solver/StateSpaceSolver.cs:360   if (liq != null && st.IsBanned(liq)) return "需求 … 被禁止";  // 终局校验
Solver/MatchingSolver.cs:242     if (IsBanned(l) && consPin[l] > 0) return false;         // 平衡式里禁液不许被消耗
Solver/MatchingSolver.cs:436     if (!cap.IsBanned(l) && pool[l] > 0) return true;        // 付钱时再筛一次
Solver/MatchingSolver.cs:426     if (cap.IsBanned(jar.Liquid)) return false;              // 从罐里取液也不许
```

即使 `MatchingSolver` 的平衡式用**原始库存**给 `surplus` 凑数（`Balance()` 里 `start = liquids[l]` 没过滤），
它后面也要过 `BuildPath` 的付款与终局校验，通不过就整体回退给精确搜索 —— 方向是安全的（只是多做一次无用功）。

### 8.2 但输入口径确实含糊，所以现在把它钉成一处

`ISolver.Solve(..., Dictionary<string,int> liquids, ...)` 的注释一直写着"液池里有多少"。
语义变更之后这句话**不再等于"能取用多少"**：那格子里可以有 5 份取不出来的酒。
用户的原话是"求解器需要重新认定什么是活性液体"。于是新增

```
src/JarSystem.Core/Solver/SolverInput.cs
    public static Dictionary<string,int> UsableLiquids(Dictionary<string,int> liquids, WorkshopCapability capability)
        // 被禁液体一律清零；键保留、值清零（那格子里确实有东西，只是取不出来）
```

三个 `Solve` 入口各接一行，于是"求解器看到的液体 = 能取用的液体"只有**一处**定义，
而不是每个实现各自记得过滤 —— 后者不会在任何世界状态里显形，只会某天以"某个实现忘了"的形式出事。
它**不做**禁令判定本身（那是 `WorkshopCapability.IsBanned` 的事），也不猜容量（容量本来就是输入）。

### 8.3 测试与负向验证

`test/JarSystem.Tests/SolverLiquidSoundnessTests.cs`（4 → 6 条，其中 5 条 × 3 实现）：

| 用例 | 期望 | 钉的是什么 |
|---|---|---|
| 池里 2 份禁酒 + 需求「圆罐:酒」 | 不可行 | 禁液不是供应 |
| 池里只有禁酒 + 需求「三角罐」（空罐改形） | 不可行 | 禁液不能当成本 |
| 罐内禁酒 + 需求「方罐」（满罐自耗） | 不可行 | 读法 B：自耗也算使用 |
| **池里 5 份禁酒 + 两份「圆罐:蜜」** | 不可行 | **数量型**：库存不许被当供应 |
| 同样三件事换成蜜（自由台） | 可行 | 反向对照：不是"恒不可行" |
| `SolverInput.UsableLiquids({酒:2, 蜜:1}, 禁酒)` | `{酒:0, 蜜:1}`，键数仍 2 | 口径定义本身 |

负向验证（这道门有牙）：
- 去掉 `StateSpaceSolver.cs:285` 的禁令判断 ⇒ `AStoredButBannedLiquidIsNeverASupply` 红，
  消息 `StateSpaceSolver 把「用池里的禁酒灌满圆罐」判成了可行 —— 禁液被当成了资源`；
- 把 `UsableLiquids` 的过滤去掉（原样返回）⇒ `UsableLiquidCountsDropTheBannedOnes` 红。

**两条要注意的教训**：
1. 改 `SolverPrecheck.CanObtainLiquid` 的禁令过滤**不会**让任何测试变红 —— 那行只影响
   "有没有成本液体"的粗判，不是决定性那行。**负向验证必须打在决定性行**，否则得到
   "看起来有牙其实没牙"的假信号。
2. 数量型用例在"没有 `SolverInput`"时也是绿的（因为各实现内部再筛一次）。也就是说：
   **它是定义测试，不是缺陷复现测试**。这两者都要，但要分清 ——
   否则会误以为"改坏了会红"而其实只是"改坏了某项内部过滤才红"。

### 8.4 因此仍然不把求解器接到 `LiquidRules` 的账目侧

`LiquidRules` 的第二半（库存账目）描述的是**活的工作台此刻有多少**；求解器刻意不认账目
（液体是输入值，换个世界就是另一次调用）。求解器需要的只是**规则侧**的禁令判断，
唯一来源就是 `WorkshopCapability.IsBanned`（`LiquidRules.IsBanned` 也委托它）。
现在多出来的 `SolverInput` 只负责"输入里哪些算资源"，与 `LiquidRules` 职责不重叠：
前者在**入口**把口径定死，后者在**运行中**回答"这次取用行不行"。
