## 一、逐题批改

### Q1（判定：半对）—— 你答的是"为什么要有组件"的上层理由，缺"这一行代码"的机械理由

- 你说"战斗是一个 system，由 health/hit/hurt 组件组成"——方向对，这是组件化的设计动机之一。
- 但在这个项目里，还有更朴素、可验证的理由你没看：
  - `player_base.gd` 只管移动/动画（`_physics_process`、`rotate_player`），它调用组件只用了两句：`init_health`（第 16 行）和 `take_damage`（第 40 行）。扣多少、何时死、发什么信号，Player **一概不知道**（都在 `health_component.gd` 里）。
  - 如果血写进 Player：Player 脚本会同时管移动+血量+将来的一切 → 越滚越大，改一处怕坏三处。组件 = **每个脚本只管一件事**（单一职责），需要"会受伤"的实体就把 HealthComponent 挂上去。
- 顺便纠正一个词：`player_base.tscn` 里的 HealthComponent 是 Player 的**子节点**（组合），不是 Player 的**子类**（继承）。组合与继承的区别见 Q3 批改。

### Q2（判定：错）—— Resource 与"继承/数据库"无关，它是**数据文件**

- 事实：`player_bunny.tres` 内容只有数据：`max_hp = 7.0`、`move_speed = 250`、`id = "Bunny"`。`player_data.gd`（脚本）只负责声明"这份数据长什么样"。
- 4 个角色 = 4 个 .tres + **同一个** `player_base.gd` 和 `player_base.tscn`。看 `player_bunny.tscn` 第 44 行：它**实例化了 player_base.tscn**，然后只做两件事：把 `data` 指向 bunny.tres、换贴图。
- 所以正确答案是：**Resource = 把"会变的东西"（数值、贴图、描述）从代码里拿出来，变成可独立编辑的文件**（数据驱动）。写死在脚本里会失去什么？
  - 调平衡（兔子太快？）= 改代码 + 重新编译 + 怕改坏别的；
  - 加第 5 个角色 = 复制脚本或给脚本加一堆 if——而资源方案 = 新建一个 .tres 填数字，代码一行不动。
- 你说的"修改 base 联动子类"是把 .tres 当成了类——.tres 没有类、没有继承，它就是一份 JSON 式的数据。真正的复用靠的是 **场景实例化**（bunny 场景引用 base 场景），不是类继承。

### Q3（判定：半对）—— 顺序直觉对了一半，术语和"为什么必须"没答

- 谁调用 `init_health`：`player_base.gd` 第 16 行，位置在 **`_ready()`** 里。`_ready` 是节点进入场景树时 **Godot 自动调用一次** 的回调。
- 你说的"先执行子类后执行父类"应纠正为：**子节点的 `_ready` 先于父节点执行**。这里不是继承，是 player 这个父节点在调它**子节点** HealthComponent 的方法。
- "为什么必须先于第一次受伤"你没答，答案是：`health_component.gd` 里 `current_health` 没赋初值 = **0**；而 `take_damage` 第一行是 `if current_health > 0` —— 若没 init，第一次受伤会被 **if 直接吞掉**：不减血、不发信号、血条不动、也死不了。这叫做**初始化前置条件**：一个变量在被使用前必须先被设置，谁负责设置、什么时候设置，读代码时要一眼能看到。

### Q4（判定：空 —— 但这是最有价值的一题）

你写"不知道怎么才能知道答案"——答案就是下面的**方法课**。方法学会了，这类题你 5 分钟能解。请先看第二节的完整示范，再去做练习 2 的 Part 2。

### Q5（判定：半对偏上）—— 链条画对了，但两处事实错 + 动机只说对一半

**你画对的部分（很好）：** `health_component` 受伤发 `on_unit_damaged` → `player_base` 收到并**转发**到 `EventBus.on_player_health_update` → `arena.gd` 第 10 行 connect → 第 21-22 行更新 `health_bar.value`。方向完全正确。

**两处事实错：**
1. "删除该方法后角色不会扣血"——**错**。扣血发生在 `player_base.gd` 第 40-41 行：`_input` 里按下 `ui_accept` 直接调用 `health_component.take_damage(1)`。删掉第 44 行（只是"转发通知"）后，**扣血照常**，死亡也照常，只有**血条 UI 不再刷新**。区别"改状态"和"通知别人状态变了"是两条独立的线——这是本课最重要的一个概念。
2. "绑定实际是在 player 的 `_ready` 中执行"——**不准确**。打开 `player_base.tscn` 第 26-28 行：信号连接写死在场景文件里（`[connection signal="on_unit_damaged" from="HealthComponent" to="." ...]`），Godot 在实例化场景时自动注册，你不需要写任何 connect 代码。

**动机部分：** 你说"组件被卸载时写死的引用会 null"——这是信号解耦的**真实动机之一**，很好。完整的理由是：信号让**发送方不知道接收方是谁、有几个、什么时候来**。arena 想听就 connect，不想听就不 connect；以后加第二处血条（比如小地图旁），只要它自己 connect EventBus，**player 和 health 一行都不用改**。如果直接调用，player 就得认识 UI 节点，UI 一换 player 就崩。

## 二、方法课：Q4 是这样被解出来的（这是本练习真正要教的东西）

### 读代码 4 步协议（以后所有"这玩意是怎么工作的"都用它）

1. **找入口**：从"用户能看到的动作"开始（点卡片、按空格、开枪……）。
2. **追写入**：全局搜索 `Ctrl+Shift+F` 搜那个函数/变量，把所有"写入点"和"读取点"列出来。
3. **逐跳前进**：每找到一个调用点，就打开那个文件那一行，问三个问题——这行改了谁的什么状态？谁可能调用我所在的函数？我调用了谁？然后跳到下一跳，直到终点（你观察到的现象）。
4. **用断点验证**：在关键行打断点（F5 运行、F10 单步），看变量面板。**运行时的真相 > 脑内推演。**

### Q4 完整示范（你在脑子里跟着走一遍）

问题：武器 `current_weapon` 是谁给的？`Global.selected_weapon` 谁写的？

1. 入口 = 用户在选人界面**点了一张武器卡**。
2. 搜 `selected_weapon` 的写入点 → `character_selection.gd` 第 57 行：`Global.selected_weapon = data`。（同文件第 50 行也写了 `Global.selected_player`。）
3. 为什么能跨场景访问？因为 Global 是 **Autoload 单例**（`project.godot` 里注册），它从游戏开始活到结束，任何场景都能读写它——这就是"选人界面的选择要带到战斗场景"的机制。
4. 切场景进入 arena → `arena.gd` 的 `_ready`（第 9 行）→ 第 14-17 行 `load_game_selection()`：`Global.get_player().instantiate()` 生成玩家并 `add_child`，**然后第 17 行 `player.weapon_controller.equip_weapon()`**——找到了 `equip_weapon` 的调用者！
5. 打开 `weapon_controller.gd:13-18` 的 `equip_weapon()`，逐行看：
   - `Global.get_weapon()`（`global.gd:42-43`）= 用 `selected_weapon.weapon_name` 去 `all_weapons` 字典（第 21-31 行）查对应的 **PackedScene**（注意：字典里存的是"场景模板"，不是武器本身）；
   - `.instantiate()` = 把模板变成真实节点；
   - `current_weapon = weapon` = 把新武器引用存进 controller 的成员变量（这样 `_process` 每帧才能用它 `look_at` 鼠标）；
   - `current_weapon.data = Global.selected_weapon` = 把选中的**数据**塞进武器，武器才知道自己的伤害/射速。
6. 终点现象：武器节点成为 controller 的子节点，出现在玩家手上，跟着鼠标转。

**答案汇总：** `current_weapon` 由 `equip_weapon()` 自己赋值；`equip_weapon` 的调用者是 `arena.gd:17`；`Global.selected_weapon` 的写入者是 `character_selection.gd:57`。

**核心认知：** 程序里"一个东西为什么会变成这样"，答案永远是一条**写入/读取 + 调用/被调用**的链。读代码不是从头读，是**从现象出发反着追**。
