# 框架与封装评估（jar-system-dotnet → Godot）

> 结论先行：**当前项目没有使用任何游戏框架**；对这个项目，**不需要也没必要**引入通用"游戏框架"；
> 真正该做的是**先把封裝（访问级别）收敛**，再按需引入最小工具（DI / 状态机 / 测试）。
> 你提到的 GodotGameFramework（GGF / GF Framework 系）**不适合**本项目的 C# 核心，原因见第 4 节。

---

## 1. 事实核对：现在用了什么框架

| 层 | 现状 | 框架依赖 |
|---|---|---|
| `src/JarSystem.Core` | 纯 C# 类库（`dotnet build` 可独立编译） | **无**（`JarSystem.Core.csproj` 无任何 `PackageReference`） |
| `src/JarSystem.Web` | ASP.NET Core 极简 API + 原生 WebSocket | 仅 ASP.NET Core 内建 |
| `test/JarSystem.Test` | 自写控制台随机测试框架 | 无测试框架（手写断言） |
| `test/StrategyExperiment` | 自写实验工程 | 无 |

也就是说：**它是"手写领域库 + 手写测试 + 薄 Web 壳"**，没有 MVC/ECS/DI/框架容器。
`Constants / Rules / ShapeRules / Solver / Executor / Command` 这套结构是**项目自造的分层**，不是任何现成框架。

## 2. 你观察到的"变量全是 public"——这个判断是对的

### 2.1 数据（`src/JarSystem.Core` 内 `{ get; set; }` 命中 144 处）

真正该收敛的（领域对象与门面，可直接被外部任意改写）：

| 文件 | 暴露内容 | 问题 |
|---|---|---|
| `Domain/Jar.cs` | `Id / Shape / Liquid / IsMarked` 全 public set | 外部可随意改罐子状态，绕过 `PourIn/Reshape/Mark` 语义 |
| `Domain/Workshop.cs` | `Name / BaseMarks / AdditionalMarks / Ban / MaxJars / MaxLiquids / Jars / LiquidStorage` 全 public set，且是 `List/`Dictionary` 本体 | 外部可绕过 `AddJar/AddLiquid/IsBanned` 直接改集合，容量与禁令校验被跳过 |
| `JarSystem.cs`（门面） | `ProducerModule / Workshops / Orders / Checker / Executor / EventHistory / LiquidProductionRate / FlowSettings / AutoCheckEnabled / CurrentMaster / CurrentSlave` 全 public set | 门面等于没有边界，任何调用方都能替换求解器/执行器或篡改状态 |
| `Production/ProducerModule.cs` | `Warehouse / LiquidWarehouse` 集合本体 public | 绕过仓库上限与丢弃计数 |
| `Orders/OrderEvent.cs` | 快照、转移集合、执行日志全 public set | 事件内部记账可被外部改写 |

可以接受的（DTO / 序列化载体，本来就是数据袋）：
`Orders/Order.cs` 里的 `FeasibilityResultData / SolverStep / DirectMatch / OperationNeed / JarState / Requirement`、
`Solver/StateSpaceSolver.cs` 里的统计与结果 DTO、`WorkshopSwitchEvent.OperationRecord`、`Command` 结果对象。
这些全 public 只是"不够整洁"，不构成逻辑风险——**但它们和领域对象混在同一个可见级别里，是问题被放大的原因**。

### 2.2 为什么"AI 编程"没提醒

三个真实原因，不必自责：

1. **生成式代码的默认风格**：把一切写成 public 的 DTO 是 LLM 最省事的写法，它不主动做"封装审查"。
2. **没有封装要求写进任务**：整个开发过程的验收标准是"测试 0 bug / 编译 0 警告"，而 public setter **不影响这两项**，
   所以任何一轮 review 都容易漏过——包括我第一轮给你梳理项目时也没点出这一条，这是我的疏漏。
3. **它真的埋了一个坑**：你自己的《Godot移植设计对话记录.md》7.5 里，`JarBalanceService.Rebuild()` 的设计就是
   "**推入核心公开 setter**"——这正是封装缺失的直接后果：本来是配置，现在变成了"外部直接改内部状态"。

### 2.3 收敛方案（建议在 Godot 移植之前做，1–2 天）

原则：**能读不能改；要改必须走方法；配置走一条入口。**

```csharp
// Domain/Jar.cs —— 已经是好样板：字段私有 + 行为方法
public int? Id { get; private set; }
public string Shape { get; private set; }
public string? Liquid { get; private set; }
public bool IsMarked { get; private set; }
// 保留 PourIn / Reshape / ClearLiquid / Mark / Clone（已存在）

// Domain/Workshop.cs —— 集合与键值只读暴露
private readonly List<Jar> _jars = new();
private readonly Dictionary<string, int> _liquids = new();
public IReadOnlyList<Jar> Jars => _jars;
public IReadOnlyDictionary<string, int> LiquidStorage => _liquids;
public IReadOnlyList<string> BaseMarks { get; }      // 构造后不变
public int MaxJars { get; private set; }             // 只能通过 SetCapacity 改
public void SetCapacity(int maxJars, int maxLiquids) // 溢出丢弃 + 计数都在这里

// JarSystem.cs（门面）—— 依赖组件只读，配置走显式 API
public ProducerModule ProducerModule { get; }        // 不再是 set
public IReadOnlyList<Workshop> Workshops => _workshops;
public IReadOnlyList<Order> Orders => _orders;
public int? CurrentMaster { get; private set; }      // 只能通过 SetMaster
// 配置入口保留且唯一：
public void UpdateProducerRate(...); UpdateLiquidProductionRate(...);
public void UpdateWorkshopCapacity(...); SetAutoCheck(...); SetFlow(int jars, int liquids);
// 未来 Godot 的 JarBalanceService 就变成 _core.ApplyBalance(cfg)，而不是逐条打 setter

// Solver / Executor / FeasibilityChecker 的内部类型：internal 化
```

安全网：现有 **2000 随机 + 3000 容量压力 + 19 确定性**测试就是这次重构的回归依据——
先做封装收敛，再跑测试绿灯，说明"只是收口，没改行为"。

## 3. Godot 里可用的 C# 逻辑层方案（候选评估）

| 方案 | 类型 | 能否用于 Godot C# | 对本项目的价值 | 建议 |
|---|---|---|---|---|
| **不加框架，手工组装**（JarDriver 里 `new` 出少数几个服务） | — | 可以 | 你的组件只有 4~6 个，手写组合根最省心 | ⭐ **起点推荐** |
| [Chickensoft.AutoInject](https://github.com/chickensoft-games/AutoInject) | Godot 节点 DI（Source Generator，免反射） | 可以（专为 Godot C# 设计） | 解决"Godot 用 new 实例化节点、无法构造函数注入"的痛点；需要时再引入 | ⭐ 进阶推荐 |
| [Chickensoft.GoDotTest](https://packages.nuget.org/packages/Chickensoft.GoDotTest/1.5.2) | 在 Godot 内跑测试 | 可以 | 给 Godot 侧（JarDriver/UI 绑定）加测试；核心仍用现有测试工程 | 可选 |
| [Chickensoft.LogicBlocks](https://packages.nuget.org/packages/Chickensoft.LogicBlocks) | 逻辑/状态块（纯 .NET） | 可以 | 若想把 `OrderEvent.CurrentPhase`（字符串阶段）升级成正式状态机 | 可选（非必需） |
| [Chickensoft.Serialization](https://github.com/chickensoft-games) | 序列化 | 可以 | 存档/读档（核心范围外，你迟早要补） | 可选 |
| [GodotSharpDI](https://github.com/Supheria/GodotSharpDI) | 以场景树为 Scope 的 DI（Service/Host/User/Scope 四角色） | 可以（社区新方案） | 生命周期跟随场景树，适合关卡切换；生态较新 | 观望 |
| [Godot.DependencyInjection.Services](https://packages.nuget.org/packages/Godot.DependencyInjection.Services/atom.xml) / [godot-addons-dependency-injection](https://github.com/Nico1395/godot-addons-dependency-injection) | 轻量 DI 封装 | 可以 | 同样是"可选替代品" | 观望 |
| `Microsoft.Extensions.DependencyInjection` | 通用 DI 容器 | 技术上可以 | **与 Godot 场景树生命周期不匹配**（Scope 要手工 CreateScope/Dispose，易泄漏）——社区实战帖见 [Godot 论坛](https://forum.godotengine.org/t/my-journey-wrestling-with-dependency-injection-in-godot-c-projects/132379) | 不推荐单用 |
| `Stateless` 等纯 .NET 状态机 | 状态机 | 可以 | 同上，可替代 LogicBlocks | 可选 |
| ECS（Arch / DefaultEcs / Friflo.Engine.ECS 等） | 数据导向 | 可以（有 [性能对比讨论](https://forum.godotengine.org/t/new-c-ecs-benchmark-covering-many-common-uses-cases/71866)） | **不适合**：你的系统是"少量实体 + 全局搜索/回滚/规则校验"，ECS 的收益场景（海量同构实体）不成立 | ❌ 不用 |
| 「GameFramework」类通用框架（Ellpeck/GameFramework 属 FNA/MonoGame 系；Unity 生态的同名框架更不适用） | 整机框架 | **不能**用于 Godot | 会把你从已验证的 .NET 库上拽走 | ❌ 不用 |

### 关于"逻辑框架"的关键认知

**你的 `JarSystem.Core` 本身就是那个逻辑框架**：Facade + 领域对象 + 命令模式 + 事件快照回滚 + 求解器。
再套一层通用框架，通常只会带来：概念重复（两套生命周期）、边界模糊（谁持有状态）、
以及把已验证的测试覆盖换成未验证的新约定。**缺的不是框架，是"组合根 + 封装边界"这两件小事。**

## 4. GodotGameFramework（GGF / GF Framework）行不行

**结论：对你这个项目，基本不行。**依据如下：

1. **语言不匹配（关键）**：GGF 这一类 Godot 框架是 **GDScript 生态的 addon**
   （`addons/gf` + 脚本模板 + GUT 测试；见 [GF Framework 资产页](https://godotengine.org/asset-library/asset/5102)、
   [中文文档](https://gf-framework.readthedocs.io/zh-cn/latest/)、
   [GGF 实战教程系列](https://www.bilibili.com/video/BV1dgMo63Eec/)）。
   而你的核心是 **C# 类库**。官方《跨语言脚本》只覆盖 GDScript ↔ C++（GDExtension），
   **C# 与 GDScript 之间没有官方支持的互相调用**（[中文文档](https://docs.godotengine.org/zh-cn/4.4/tutorials/scripting/cross_language_scripting.html)）。
   想把 C# 核心塞进 GDScript 框架，等于要么重写核心，要么做 GDExtension 桥——两条路都比直接写 Godot C# 更难。
2. **定位错位**：这类框架解决的是"大项目场景/UI/音频/存档的组织"，
   而你已经有：分层的领域库、固定结构的 `GetState()`、写好的 UI 结构设计（《Godot迁移指南》2.4）。
   框架能帮的那部分你已经有替代品。
3. **成本收益倒挂**：引入框架要先学它的四层概念（GFModel/GFSystem/GFController/GFUtility 之类）+ 
   编辑器工作流，而你现在最该投入的是"跑通 M0–M3"。
4. 若你确实想用它的某些模块（音频、语言切换、存档图），**它们是表现层能力**，
   用 Godot 官方 API 或小工具库同样能做，且不与你的架构冲突。

> 附带提醒：名字相近的东西很多——`Ellpeck/GameFramework`（FNA/MonoGame 系）、Unity 生态的 GameFramework/ET 等，
> 都与 Godot 无关。选之前先确认"目标引擎 = Godot"且"脚本语言 = C#"。

---

## 5. 建议顺序（把"要不要框架"这件事排到后面）

1. **封装收敛**（1–2 天）：按 2.3 改造 `Jar / Workshop / JarSystem / ProducerModule / OrderEvent`；
   跑 2000+3000+19 测试保持全绿。**这一步让后面的 Godot 层有清晰边界，性价比最高。**
2. **M0–M2**（见《Godot学习路线与里程碑.md》）：Godot 项目 + 引用核心 + `JarDriver` 手写组合根。
3. **需要时再引工具**：Godot 侧写测试 → GoDotTest；节点依赖变多 → AutoInject；想存档 → 序列化库。
4. **不要**在第一版就上 DI 容器 + 状态机 + 框架全家桶：那是"感觉在进步、实际在拖慢"的经典陷阱。
