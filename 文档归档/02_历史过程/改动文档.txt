## 阶段 1 — 路径可执行性（问题 1、2、3）

- 日期：2026-08-01
- 内容：
  1. `SolverOperation` 新增 `FullReshape` 标志：求解器生成「满罐改形」时置位，`MakeSummary` 输出 `reshapeMode: full/empty`。
  2. `SolverStep` 新增 `AfterLiquids`：求解器每一步直接记录操作后的液体状态，可行性分析不再手工推算液体账目。
  3. `JarState` 新增 `Id`；`MakeSummary` 输出 `jarId / jarShape / jarLiquid`，路径步骤携带罐子身份与预期状态。
  4. 执行器新增 `ApplySolverStep`：按 jarId（首选）或 jarIndex 定位罐子；执行前校验真实罐子与步骤预期状态一致；RESHAPE 按 `reshapeMode` 区分空罐/满罐改形。A 类路径与 B 类主台路径统一走该逻辑。
  5. B 类执行：`slave_only / combined_under_slave / two_phase_simulation / partition` 等求解器方案下，主台不再先跑贪心操作，避免改变路径依赖的初始状态；无可行性结果时才走旧贪心回退。
- 涉及文件：`Order.cs`、`StateSpaceSolver.cs`、`FeasibilityChecker.cs`、`IndependentExecutor.cs`。
- 验证：旧测试套件 11 bugs / 2000 → **0 bugs / 2000**（此阶段尚未改测试，NOTE 不计）。

## 阶段 2 — 精确可行性（问题 4）

- 日期：2026-08-01
- 内容：
  1. `CheckTypeB` 重写为「按需求子集划分的精确搜索」：需求按出现顺序编号（满罐优先排序），枚举 2^N 个主台/从台划分。
  2. 每个划分：主台子集在主台规则下精确求解 → 取真实终态（`AfterLiquids`）与从台合并 → 从台子集在从台规则下精确求解；任一划分可行即订单可行。
  3. 可行时保存两阶段路径：`MasterPath`（主台阶段步骤）+ `SolverPath`（从台阶段步骤），执行器按 Id 忠实执行，不再依赖启发式降级。
  4. 删除旧的启发式 `TwoPhaseSimulation`（含逐需求补全循环、`alreadyDone` 重复需求跳过逻辑）与死代码 `BuildMergedWorkshopInfo`；`combined_under_slave` 被「全部需求划分给从台」的子集自然覆盖，`CheckMethod` 现为 `slave_only / partition`。
- 涉及文件：`FeasibilityChecker.cs`。
- 验证：0 bugs / 2000（旧测试口径），性能无回退（约 3 秒）。

### 2. 问题 21 重跑：策略实验多种子统计验证

- 新建独立实验工程 `test/StrategyExperiment`（已加入 `JarSystem.slnx`），复现 711 抽象结构模式。
- 与原记录的方法差异（已写入报告）：
  1. 每模式 3 个独立种子（1001/2002/3003）× 30 单/种子 = 90 单/策略/模式（原 1 种子 × 60 单）；
  2. 指标 = 实际执行成功率（不调用可行性分析，策略只影响执行器选择）；

  | 策略 | 成功率 | 严格最优运行流 | 每模式最优 |
  |------|--------|---------------|-----------|
  | FIFO | 44.96% | 1330 | 520 |
  | LIFO | 40.26% | 585 | 170 |
  | RareShapeFirst | 27.13% | 3 | 0 |
  | Random | 23.30% | 0 | 0 |

  FIFO vs LIFO / RareShapeFirst / Random 配对符号检验 p 值均 < 0.001。
- 结论修正：在执行器贪心路径口径下 **FIFO 显著最优**；原记录「差异很小（0.1–0.3pp）」的表述被多种子重跑推翻。

## 第四轮（2026-08-01）— 容量纳入可行性资源管理 + 跨阶段罐子保留

### 背景（用户场景）

主：罐 5/7、液 8/8；从：罐 0/3、液 0/5；主从禁液一致。问题：可行性分析是否把
「容量导致的转移不足」纳入路径筛选（即容量是否属于资源管理的一部分）。

### 验证结论（修前）

1. 路径已区分主台/从台阶段（MasterPath 转移前、SolverPath 转移后），但**只区分需求归属，不区分罐子归属**：
   从台阶段可再次匹配/消耗主台已制造的交付罐 → 重复需求场景存在「可行性=真、执行失败」的假阳性。
2. 容量**未纳入转移边界**：求解器只约束阶段内液体存储上限（POUR_OUT 守卫 MaxLiquids），
   罐子容量、转移边界的罐子/液体容量均未检查 → 用户场景（从台 0/3 收不下主台 5 罐）会被误判可行。
3. 执行端液体转移是「全量或全不」，与可行性假设的合并状态不一致。

### 修复内容

1. `WorkshopInfo` 增加 `MaxJars`；`BuildWorkshopInfo` 填充。
2. `CheckTypeB` 增加**容量边界 1**：B 类全量转移要求 `主台罐子数 + 从台罐子数 ≤ 从台 MaxJars`，
   否则直接不可行（CheckMethod="capacity"，blockage 说明需要多少个罐位）。
3. `CheckTypeB` 划分循环增加**主台交付罐保留**：主台子集需求在终态中匹配的罐子 Id 记为交付罐，
   从台求解池排除它们（防止跨阶段重复使用同一罐子）；删除因此不再需要的 `MergeLiquids`。
4. `CheckTypeB` 增加**容量边界 2**：从台阶段液体池按 `slave.MaxLiquids` 截断
   （溢出液体留在主台），与执行语义一致。
5. 执行端液体转移改为**容量感知的部分填充**（`IndependentExecutor.ExecuteTypeB`、
   `OrderEvent.RollbackSlaveToMaster`、`ProducerModule.FlowToMaster` 三处），
   与可行性截断一致；回滚部分填充后剩余才回流中央仓库。

### 新增用例

- S15：重复需求跨阶段罐子保留（可行性=可执行，修前为假阳性）；
- S16：用户容量场景——从台罐位不足 → 可行性 false + 执行失败；
- S17：从台液体截断与执行一致（日志出现 transfer_liquid_failed）。

### 验证（第四轮后）

- 测试：**0 bugs / 2000 随机 + 17 确定性全部 PASS**；全解决方案 0 警告 0 错误。

## 第五轮（2026-08-01）— B 类选择性转移 + 罐子价值优先级细化

### 用户确认的三点

1. B 类订单转移改为**选择性转移**：只转移「交付罐 + 从台阶段计划使用的工具罐」，其余留在主台；
2. 液体只转移**从台阶段实际需要的量**（2b）；
3. 切换事件罐子价值优先级细化：**附加标记空罐的价值低于「基础+附加之外的空罐」**
   （因为后者新主台无法通过任何方式获得）；异液满罐（液体被新台禁）始终最低。

### 实施内容

- 求解器：`JarState.MasterOrigin` 标记主台来源；`SolverState.TransferBudget/TransferUsed` 转移预算
  （从台阶段最多可使用的主台罐子数，未使用的主台罐子留在主台）；`Solve` 增加预算参数。
- 可行性：移除第四轮「全量转移容量边界 1」（已被选择性转移取代）；
  划分循环按「从台罐位 − 从台原有罐子 − 交付罐数」计算预算，不足则划分不可行；
  从台求解池 = 主台终态（扣除交付罐，标记 MasterOrigin）+ 从台原有罐子；
  可行时输出 `TransferJarIds`（交付罐 + 从台路径实际使用的主台罐子）与
  `TransferLiquids`（沿路径净消耗峰值超出从台自身存储的部分）；slave_only 转移清单为空。
- 执行器：按 `TransferJarIds` 选择性转移（无可行性结果时回退全量），液体按 `TransferLiquids` 只转需要的量。
- 切换事件：`JarValue` 细化为 0 同液满罐 > 1 同形基础罐 > 2 基础+附加之外空罐 > 3 附加标记空罐 > 4 异液满罐。

### 用例

- S16 改为选择性正例：主 5/7 罐、从 0/3 罐，订单只需 1 罐 → 可行，4 罐留主台；
- S17 改 2b：液体只转需要的 1 酒，蜜×4 留在主台；
- S18 增加附加标记层级：保留 0/1/2 价值罐，丢弃 3/4 价值罐；
- S19 工具罐转移并回流：主台无游离酒但有 满罐(圆罐,酒) + 空方罐，从台基础[方罐]附加[三角罐]，
  订单 空三角罐 → 两罐都转移，倒出酒支付改形，交付三角罐，空圆罐回流主台。

### 用户场景推演结论（经用户纠正：主台禁酒、从台禁蜜）

- 主台禁酒 → 主台自己**无法倒出**圆罐中的酒（倒出=存储，被禁），所以工具罐必须转移；
  从台禁蜜、酒可用 → 在从台倒出酒并支付改形（方罐→三角罐）→ 交付三角罐 → 空圆罐回流主台。
- 该场景在选择性转移规则下**可行**，S19 已用正确禁令验证：
  「并非所有必要转移的资源都是最终订单需要的」——工具罐转移并在订单结束后回流主台。
- 之前「从台禁酒则不可行」的推演结论仅针对说反的那一版设定（从台禁酒时倒出/成本均被禁令拦截）。

### 验证（第五轮后）

- 测试：**0 bugs / 2000 随机 + 19 确定性全部 PASS**；全解决方案 0 警告 0 错误；
  无残留后台进程（此前执行中断未造成影响）。

## 第六轮（2026-08-01）— 全面系统审计

### 修复：B 类主台路径出错仍可能返回成功

- 发现：`ExecuteTypeB` 中 MasterPath（求解器主台路径）任一步失败时，错误被累计到 `errs`，
  但只要最终 `IsSatisfiedBy` 通过仍返回成功——此时主台状态已偏离可行性模拟，转移清单与从台路径不可靠。
- 修复：主台路径有错误即返回失败「主台路径执行失败，状态与可行性分析不一致」，
  不再带错误继续/静默成功（贪心路径的信息性错误不受影响）。

### 新增：容量压力测试（3000 场景）

- `GenCap`：主从台罐位 1-4、液位 1-3（每种液体）、从台也分配资源，
  专打选择性转移预算、转移清单、容量截断与回滚路径；与主随机套件相同的四类断言
  （双向一致、罐子守恒、液体非负、无崩溃）。
- 结果：**0 bugs / 3000**。

### 其他核验（审计结论）

- 选择性转移：预算 = 从台罐位 − 从台原有罐子 − 交付罐数；求解器按预算筛选；
  转移清单 = 交付罐 + 从台路径使用的主台罐子；执行器按 Id 清单转移、未交付罐子回滚回主台 —— 一致。
- 液体 2b：`TransferLiquids` 按从台路径净消耗峰值计算，执行端只转该量 —— 一致。
- 切换事件：JarValue 五级价值排序 + 快照回滚 + Case2 剩余禁液丢弃不回仓库 —— 一致。
- Web 链路：`transferJarIds / transferLiquids` 已序列化进 GetState/feasibilityResult，冒烟通过。
- 构建：全解决方案 0 警告 0 错误。

## 第八轮（2026-08-01）— 前端容量编辑被打断修复

### 问题

- 现象：编辑工作台容量时，几秒后输入框自动复原。
- 根因：服务端 `startTick` 每 2 秒广播 `state`，`updateUI() → renderWorkshops()` 重建全部卡片
  （`c.innerHTML = ...map(...)`），正在编辑的输入框被静态显示覆盖。

### 修复（app.js）

- 新增 `editingCapacityIndex` 与 `capacityDraft` 两个前端状态：
  - 进入编辑态时记录草稿值并重绘；
  - `renderWorkshops` 对正在编辑的卡片渲染输入表单（值来自草稿），其余卡片照常；
  - 输入框 `oninput` 实时写回草稿（`updateCapacityDraft`），tick 重绘不再丢失输入；
  - 确认（✔）时读取草稿提交 `updateWorkshopCapacity` 并退出编辑态。
- 验证：`node --check` 语法通过；后续 state 广播会保留编辑表单与已输入内容。
