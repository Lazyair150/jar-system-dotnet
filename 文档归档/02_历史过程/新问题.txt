• 我已通读设计文档、全部核心源码、前端、测试和历次问题记录，并实际运行了测试（当前结果是 11/2000 个 bug + 1 个反向不一
  致，文档里写的 18/2000 已过时）。下面是我对这套设计的理解和发现的问题。

  ## 我的理解

  这是一个"规则驱动的资源调度解谜"内核：中央仓库持续产出罐子和液体，玩家选主从工作台、接订单，系统先做可行性分析（DFS 状
  态空间求解 + 两阶段模拟），再按路径执行；执行失败会回滚资源。后来加的 WorkshopSwitchEvent 把"切换主台"从纯丢弃变成了有
  策略的资源重组。分层（Core 零依赖 / Web 薄胶水 / 前端 SPA）、快照隔离、命令模式、一罐一操作、就简原则这些设计是扎实
  的，作为可移植的游戏子系统没有问题。

  但"可行性分析 → 路径 → 实际执行"这条主链并没有真正闭环，这是整套设计里最核心的问题。下面按重要性排。

  ## 一、核心问题：可行性分析与实际执行不一致

  1. 求解器路径里有不可执行的步骤。
  求解器会生成"满罐改形"（RESHAPE 满罐，用罐内液体自耗）。但执行器处理 RESHAPE 时一律调用 ReshapeEmpty（src/
  JarSystem.Core/Executor/IndependentExecutor.cs 里 A 类路径和 B 类主台路径都是如此），满罐必然返回"必须为空罐"→ 该步失
  败 → 静默降级到贪心。也就是说：路径弹窗展示的方案，实际执行时并没有照做。这正是你历史问题里反复出现的"路径说可行/这样
  做，实际不按路径走"的根源之一。

  2. B 类订单转移后，求解器路径的罐子索引会错位。

  - slave_only 路径的索引基于"转移前的从台罐子列表"，但转移后 slave.Jars 前面插入了所有主台罐子，索引整体偏移 → 操作会 落
    在错误的罐子上；

  - combined_under_slave 路径顺序恰好一致，但主台会先执行贪心操作改变罐子状态，再转移，路径依赖的初始状态已经不存在。

  降级机制（路径失败就重跑贪心）掩盖了问题，让结果"大多数时候正确"，但路径与执行的绑定关系是虚假的。

  3. 两阶段模拟的液体账目漏掉 POUR_OUT 回补。
  阶段 1 的残留液体是从初始库存"只减操作消耗"算出来的，POUR_OUT 倒出的液体没有加回去（src/JarSystem.Core/Orders/
  FeasibilityChecker.cs 的 TwoPhaseSimulation）。含倒出步骤的可行订单会被低估液体、误判不可行。

  4. 两阶段模拟本身是启发式，不是完备证明。
  阶段 1 是"按需求顺序 DFS + 逐个补全"的贪心最大化，不保证主台贡献最优；阶段 2 只是"在这个状态下再解一次"。所以 1% 级别
  的可行性/执行不一致是结构性的，不是修一个边角能根除的。当前 11 个 bug 全部是 B 类报"从台资源不足"，印证了这一点。

  5. 测试只验证了半边。
  测试把"可行但执行失败"计为 bug，但"不可行却执行成功"只输出 NOTE 不计数（test/JarSystem.Test/Program.cs）——所以 99.1%
  这个数字只代表"不会假阳性"，不代表不会假阴性。而且所有随机场景的资源全放在主台、从台永远为空，B 类从台路径、切换事件、
  容量上限、ID 碰撞、回滚正确性都没有被测试覆盖。

  ## 二、工作台切换事件

  6. 旧主台只有液体、没有罐子时，切换事件根本不触发。 SetMaster 的触发条件是 old.Jars.Count > 0，所以只有游离液体时资源
  原地滞留，既不转移也不丢弃，连日志都没有。前端也不会收到 workshopSwitched 动画。

  7. Case 1 与设计文本不符。 设计说"从非基础形状满罐倒出液体"应适用于所有装满未禁液体的罐子，但实现只倒出"当前已有游离库
  存的那种液体"的满罐。如果游离液体为 0，满罐液体完全不被利用。

  8. Case 2 会把旧台所有游离液体无条件清空，包括新主台本来能用的（例如旧台无禁、新台只禁蜜，酒应该能带走却被丢弃）。设计
  文本写"残留液体丢弃（新台无法使用）"，实现比这个更激进。

  9. 可以把当前从台设为主，造成主从同台。 核心层没有"主从不得相同"的不变量，前端也允许对从台卡片点"设为主"（只隐藏了当前
  主台的按钮）。切换后 CurrentSlave 不变，主从指向同一工作台，状态自相矛盾，B 类订单会向自己转移资源。

  10. 切换事件没有快照和回滚。 它直接改真实工作台状态，中途失败没有恢复点；容量满丢弃罐子有日志，但 Case 2 的液体清零基
  本没有日志。作为"类似订单的事件"，生命周期管理比 OrderEvent 弱一档。

  ## 三、状态与 ID 管理

  11. 罐子 ID 是每工作台自增的，跨台转移后会撞号。 B 类回滚用 TransferredJarIds / SlaveOriginalJarIds 两个 HashSet<int>
  判定罐子归属，一旦两个工作台各自生成过同号罐子，回滚会把错误罐子留在从台或错误归还。应该用全局唯一 ID，或直接按对象引
  用/实例 ID 判定。

  12. 订单在核心用 Id、前端用数组 index，删单后 index 错位。 前端缓存的 selectedOrderIndex、可行性结果都会指到错误订单
  上。

  13. A 类订单被无谓地耦合了从台。 设计上 A 类"主台完成、无转移"，但 CheckFeasibility 和 ExecuteOrder 都强制要求
  CurrentSlave 非空，UI 同样。选不出从台就连 A 类都不能执行。

  14. B 类转移失败时流程混乱。 批量转移失败会回滚已转移的罐子，但阶段停在 master 后第三阶段照常执行：solver 路径绕过阶段
  检查直接改从台，ExecOnWs 的命令则全部被"当前不在从台阶段"拒绝，最后报一个笼统的"从台资源不足"。

  15. 液体回流名不副实。 B 类交付后剩余资源回滚回主台，主台容量不足时液体直接消失，日志却写 return_to_warehouse（实际没
  回仓库）；转移阶段往从台加液体也忽略了 AddLiquid 的容量返回值。规则矩阵里"容量溢出回流 ✅"与真实行为不符。

  ## 四、规则实现重复与数据不一致

  16. 形状转换规则有三份实现，已经漂移。 Workshop.GetPossibleTransforms、WorkshopInfo.GetPossibleTransforms、
  RuleEngine.GetPossibleTransforms 是互相独立的拷贝，其中 RuleEngine 只支持"基础→基础"，改形成本还写死为"酒"（实际可以 用
  蜜）。RuleEngine/WorkshopService 目前是死代码，一旦被未来功能调用就会与主流程产生两套规则。应单一来源。

  17. 禁令数据两种写法并存。 模板用 ["酒"]，青龙台用 ["禁蜜"]，随机生成又用裸液体。IsBanned 兼容两种写法，但序列化展示和
  任何直接比较 ban 的代码都会踩坑。

  18. "空罐在前"只是订单构造校验，实际执行按满罐优先排序。 规则文档、UI 提示说"空罐必须在满罐之前"，但求解器和执行器都把
  满罐需求排前面执行，容易让玩家误以为执行顺序就是列表顺序。

  ## 五、前后端断链（功能存在但实际不工作）

  - 容量编辑是死的：前端发 updateWorkshopCapacity，但 src/JarSystem.Web/Program.cs 的 WebSocket 命令表里没有这个 case →
    点击编辑静默无效。

  - B 类转移动画从不触发：服务端 orderExecuted 只传 {success, reason, operations}，前端却在等 data.transferOccurred ===
    true → 永远为 false。（切换事件的动画正常，因为它走 workshopSwitched。）

  - 主从卡片高亮样式不生效：CSS 定义的是 .workshop-card.master/.slave，JS 生成的是 role-master/role-slave →
    卡片上的红/蓝高亮不存在（Canvas 里的高亮是正常的）。

  ## 六、游戏性 / 平衡性层面

  19. 满罐需求存在隐藏限制：只能由"现成满罐"或"现成空罐+倒液"满足。 因为一罐一操作，"改形+倒液"两步制造满罐在规则上不可
  行，改形操作只能服务于空罐需求。这不是 bug，但它是当前规则组合的隐含结论，文档没有说明；作为游戏设计，你要确认这是想要
  的深度（比如满罐需求很依赖仓库恰好送来对应形状的空罐），否则玩家会觉得"有液体、有罐子却做不出满罐"很憋屈。

  20. 中央仓库无上限。 罐子和液体随时间无限堆积，长跑会膨胀；且 FlowToMaster 固定从队首取罐，生产者速率不均会让某些形状
  长期滞留仓库。

  21. 策略对比结论统计上很弱。 "FIFO 最优（38.2%）"来自每模式 60 个订单的一次运行，四种策略平均成功率只差 0.1–0.3 个百 分
  点，这个差距大概率在噪声范围内。作为设计证据，它支撑"策略影响很小"，但撑不起"FIFO 是最优策略"的结论。

  22. Web 层是单例 + 多客户端共享状态，自动检测 timer 和多个 WebSocket 连接可以并发触发 Tick/执行/切换，存在竞态。作为单
  人游戏移植内核没问题，但这个 Web 壳不适合多人。

  ## 建议的修复顺序

  1. 先把"路径可执行性"补上：执行器区分空罐/满罐改形；转移后对路径索引做重映射（按罐子 ID 而不是位置）；两阶段液体账目补
     POUR_OUT 回补。

  2. 测试补反向一致性（不可行但成功也算 bug）、从台资源、切换事件、容量边界、回滚和 ID 碰撞。
  3. 修三处前后端断链（updateWorkshopCapacity、transferOccurred、CSS class），都是小改动。
  4. 确立状态不变量：主从不得同台、切换时处理从台角色、A 类不要求从台。
  5. 全局唯一罐子 ID + 单一规则来源（去掉 RuleEngine 或让它委托给 Workshop）。

  总的来说：骨架是好的，方向（可行性前瞻、产线重组、资源博弈）也成立；目前最需要解决的不是加功能，而是把"分析结果 = 可执
  行方案"这条承诺做实，再把测试从"只测半边"补成"双向一致"。
