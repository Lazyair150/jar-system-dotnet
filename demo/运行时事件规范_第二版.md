# 运行时事件规范（第二版 · 定案）

> **状态**：规范性文件。第一版见 `运行时事件规范_第一版.md`（保留为历史）。
> **适用对象**：`src/JarSystem.Core` 里一切"会改变世界"或"会被世界看见"的动作。
> **强制力**：新增事件、改造既有事件、给世界加一条可观察通道，都必须先满足本文件的条文，并且能被一条测试或一处代码位置指认。**条文与实现对不上时，以条文为准去改实现，或以证据修订条文——不允许"代码已经这样了，所以规范就这么写"。**
>
> 用词：**必须**（must，违反即缺陷）／**不得**（must not）／**应当**（should，偏离要写明理由）。

---

## 0. 这份文件回答什么

它不描述"系统现在长什么样"（那是代码和 `README` 的事）。它只回答一个工程问题：

> **新加一个事件时，作者凭什么知道该把它做成哪一类，而不是自己猜？**

猜错的代价不是抽象的。本仓库真实出现过：换台是「全成或全退」，订单是「失败代价不退」，两者看起来都像"执行一串操作"，但失败语义相反；配置类命令既不回滚也不进 `eventHistory`，于是它看起来像"偷工减料的换台"。**三种写法并存而没有一条写下来的判据**，就是这份文件存在的原因。

## 1. 三条时间轴（先把"时间"分清，否则后面的条文没法读）

| 轴 | 定义 | 谁能推进 | 用途 |
|---|---|---|---|
| **逻辑 tick** | `Process.Scheduler.LogicalClock.Tick`，单调递增的整数 | 只有 `TickPipeline.AdvanceOneTick()`；外部只能经 `JarSystem.Tick(count)` 或宿主 `manualTick` 请求 | **一切判定与计时的唯一依据** |
| **调用边界** | 一次公开方法调用（`JarSystem.Xxx(...)`） | 调用方 | 决定"哪些阶段在一个调用里做完" |
| **墙钟** | `DateTime.Now` | 操作系统 | **只允许出现在两处**：命令日志的 `WorldCommand.Time`、事件历史的 `timestamp`。不得参与任何判定 |

**R-TIME-1**：任何判定**不得**读取墙钟。违反后果：`REPLAY-OK` 逐字节一致性立即失效。
**R-TIME-2**：逻辑 tick 只能由显式推进命令增长。宿主卡顿后**不补算**（`TickBackgroundService.ReportIfStalled` 的注释原文：「不补算是刻意的：补算等于凭空推进世界 ⇒ 改玩法语义」）。
**R-TIME-3**：一条 tick 内部的阶段顺序**必须**固定，且**必须**可枚举。实现：`Process.Scheduler.WorldScheduler`，阶段表 `TickPhase { Events=0, Modifiers=1, Processes=2, Production=3, Flow=4 }`。
**R-TIME-4**：同一阶段内按 `Order` 升序执行；**同阶段同 `Order` 必须报错**（点名两个处理器），不得靠注册顺序默默决胜。实现：`WorldScheduler.Register`。
**R-TIME-5**：一个 tick 的第一个处理器执行后**封盘**（`IsSealed`），此后注册即被拒绝——阶段顺序是结构，不是运行时配置。

### 1.1 一个 tick 里实际发生什么

```
JarSystem.Tick(count)
  for i in 1..count:
     AdvanceOneTick(tick = clock.Tick + 1)
        Scheduler.RunTick(tick)：只跑前四阶段
           ① Events      —— 执行世界事件源在本 tick 排定的事件（反应器排的后续变化在这一步落地）
           ② Modifiers   —— 过期清理（ModifierStack.Expire(tick)）
           ③ Processes   —— 推进所有活跃过程（这是唯一会阻塞/宽限/完成的地方）
           ④ Production  —— 生产者产出 → 仓库
     Time.OnAdvanced()
  RunCallBoundary(tick)     // ⑤ Flow：仓库 → 工作台。**整批调用只做一次**
```

**R-TIME-6**：`Flow` 阶段**必须**放在调用边界而不是每个 tick 里。理由：一次 `Tick(n)` 是"过了 n 个 tick 的一次请求"，流入是"请求边界上的结算"，否则 `Tick(4)` 与四次 `Tick(1)` 会产生不同的世界——那是回放不出来的分歧。

## 2. 三个判定维度

新增一个事件，按顺序回答这三问，答案的组合**唯一确定**它属于哪一类。这三问不是风格偏好，每一问都直接对应一套实现约束。

### 2.1 原子性（失败时世界怎么办）

| 取值 | 含义 | 实现约束 |
|---|---|---|
| **全退**（atomic） | 任何一步失败，世界回到调用前，逐字段相同 | 必须有前后快照 + 恢复路径；恢复必须幂等 |
| **代价不退**（irreversible） | 已发生的操作保留，只有"跨工作台的转移"回滚 | 必须能说清"哪一部分是已付出的代价" |
| **无失败**（infallible） | 这类动作不定义失败 | 不得声称回滚；也不得被当成"缩水的原子事务" |

**R-ATOM-1**：选「全退」的事件，其回滚**必须**能覆盖该事件可能改动的**全部**字段。反例（已修）：`RestoreFromSnapshot` 曾经只还原罐子与液体，而 `CreateSnapshot` 存了容量与能力参数 ⇒ "快照—还原"不对称，切换过程中若改过容量，回滚后会留一个与快照不一致的工作台。
**R-ATOM-2**：选「代价不退」的事件，**必须**在条文里写明"代价是什么"，并且这个代价**必须**是玩家主动投入的稀缺资源（本系统里是罐/液）。否则它就是"没有代价的失败"，与「无失败」无法区分。
**R-ATOM-3**：取消是一条**独立的失败路径**，不因为它"不是异常"就可以不处理。反例（已修）：`ProcessSystem.Cancel` 走 `advancer.MarkFailed → OnFinished → run.Abort`，而 `SwitchProcessAdvancer.OnFinished` 当时只处理成功分支 ⇒ 取消后留下"改了一半的工作台"。现在 `OnFinished` 在 `!Succeeded` 时调 `Rollback()`。

### 2.2 时间性（在一个调用里做完，还是跨 tick）

| 取值 | 含义 | 实现约束 |
|---|---|---|
| **瞬时**（instant） | 一次调用内跑完，期间世界不可被观察 | 不得产生中间态；不得被取消 |
| **过程**（process） | 按 tick 一格一格做，有中间态 | **必须**走 `ProcessSystem`：五态 + `graceTicks` + 可取消 + 进过程日志 |
| **即时配置**（config） | 改的是"世界的参数"，不是"世界的内容" | 立即生效；不发明过程 |

**R-TIME-7**：需要中间态、需要被反对、需要时间成本 —— **三者占其一就必须用过程**。
**R-TIME-8**：过程**必须**声明 `graceTicks`。宽限期是"被阻断后还能等多久"，它的存在让 `blocked → resumed` 成为一个有意义的状态转移，而不是立即失败。

### 2.3 可观察性（谁能看见它）

四个通道，**保证不同、不得混用**：

| 通道 | 保证什么 | 不保证什么 | 实现落点 |
|---|---|---|---|
| **命令日志** `_commandLog` | 回放的**唯一输入**：每个意图一条 `WorldCommand`，`Seq = 世界修订号` | 不表达"事件"，只表达"请求" | `JarSystem.Record(...)`（本类唯一写入口） |
| **事件历史** `eventHistory` | 对外的**世界事件流**，保留窗口 `MaxEventHistory = 10`（`JarSystem.MaxEventHistory`，`StateSerializer` 引用同一常量） | 不是审计日志（会被裁剪）；不是回放源；**没有统一的 schema**（见 R-OBS-6） | `JarSystem.AddEvent(...)`（唯一写入口，全仓 4 处调用） |
| **过程日志** `processJournal` | 过程的**append-only** 逐条记录，可裁剪不可修改，容量 `DefaultCapacity = 4096` | 不覆盖非过程事件 | `Process.Journal.ProcessJournal` |
| **世界信号** `WorldBus` | **同一 tick 内的推送**，给观察者/反应器用；`WorldChanged` / `ProcessChanged` / `TimePaused` / `TimeResumed` | 不是存储，不持久化，不参与回放 | `Core/World/WorldBus`（既是观察者枢纽，也是管线第 ① 步的 `IWorldEventSource`） |

**R-OBS-1**：任何"改世界"的意图**必须**经 `Record(...)` 落一条命令日志。这是回放的充要条件，不得绕过。
**R-OBS-2**：进 `eventHistory` 的事件**必须**同时已经进命令日志；反之不成立（命令日志更细）。
**R-OBS-3**：观察者**不得**抛异常、**不得**反向调用 `JarSystem`（`IProcessObserver` 的注释原文即此约定）。理由：观察者出错不能影响世界推进；反向调用等于在"改到一半"的世界里读状态。
**R-OBS-4**：信号**必须**携带 `Tick` 与 `Revision`。没有轮次的世界观是不可回溯的。
**R-OBS-5**：注册观察者/反应器**不得**改变世界的任何一步。硬证据：`WorldBusTests.Subscribers_DoNotChangeWorldOutcome` —— 两个同种子同命令序列的世界，一个挂订阅者+反应器一个不挂，状态快照必须逐字相同（比对前把 `FeasibilityResultData.Timestamp` 这种墙钟耗时抹成 `<volatile>`）。
**R-OBS-6**：`eventHistory` 的每一条**必须**能被消费方**自我识别**（有明确的 `type` 字段）。

**已整改（2026-08 批次，D4）**：本条曾是已知缺陷——全仓 4 处 `AddEvent` 产出过**两种形状**，订单事件没有 `type`，消费方只能靠"看它有没有 `order` 键"来猜。现在：
- 换台事件收成**唯一发射点** `JarSystem.AddWorkshopSwitchEvent(...)`（原先 `JarSystem.CommitSwitch` 与 `Services/MasterSwitchCoordinator` 各拼一份同样的字典）；
- 订单事件补 `["type"] = "order_event"`；
- 配置事件经 `JarSystem.AddConfigEvent(kind, fields)`，三种配置各有自己的字段。

守卫：`test/JarSystem.Tests/WorldEventShapeTests.cs` 的 `EveryEventHasTypeField` 断言**任何**条目都有非空 `type`。

## 3. 五类事件的定案

| # | 事件 | 原子性 | 时间性 | 可观察性 | 过程种类 |
|---|---|---|---|---|---|
| E1 | 换台（同步轨）`setMaster` | 全退（快照回滚） | 瞬时 | `eventHistory` + 命令日志 | — |
| E2 | 换台（异步轨 / **工作台迁徙**）`startSwitch` | 每阶段全退 + 取消也回滚 | 过程 | `eventHistory`（仅成功提交时，经 `CommitSwitch`）+ `processJournal` + 命令日志 | `ProcessKinds.WorkshopMigration = "workshop_migration"` |
| E3 | 订单执行（同步轨）`executeOrder` | **代价不退** | 瞬时 | `eventHistory`（订单形状，无 `type`）+ `processJournal` + 命令日志 | — |
| E4 | 订单执行（异步轨）`startOrder` | **代价不退** | 过程 | 同 E3 | `ProcessKinds.OrderExecution = "order_execution"` |
| E5 | 配置（产线速率 / 液率 / 流入参数） | 无失败 | 即时配置 | `eventHistory`（`flow_settings` / `producer_rate` / `liquid_rate`）+ 命令日志（D1 已定案） | — |

### 3.1 E1 / E2 是同一份搬运逻辑的两条轨

**R-EVT-1**：不得出现两份搬运实现。`WorkshopSwitchEvent.Execute()` 就是 `Begin → RunReshape → RunTransfer` 的组合，异步轨只是把这三步按 tick 拆开调用。

### 3.2 E3 / E4 的代价，以及为什么 E2 不照抄

**R-EVT-2**：订单失败**不回滚**已发生的操作（已改形保持新形状、已消耗成本液体不返还、已倒液体留在工作台），只有「跨工作台转移」回滚。依据 `规则.txt:33-37`：「试探一个订单本身有成本，这是 puzzle 的一部分，**不要**当缺陷修掉」。
**R-EVT-3**：迁徙**不得**套用 E3 的失败语义。迁徙没有已付出去的代价——它改的只是资源摆在哪，退回去不构成惩罚。因此 E2 的每个阶段**仍然整体回滚**。把订单的失败惩罚硬加到迁徙上，等于让玩家为"换个台"付费。
**R-EVT-4**：E2 **不是订单**：没有委托方、没有交付物、不产生 `orderEvent`。它是**使用者主动发起的资源重组**。

### 3.3 E5 为什么这么轻

**R-EVT-5**：配置类改的是"世界的参数"，不是"世界的内容"。它们不定义失败，因此没有回滚可言。**但这一点必须写下来**——否则它看起来像"漏了回滚的换台"。

## 4. 过程语义（E2 / E4 共用同一套）

**R-PROC-1**：状态机固定为 `Created → Ready → Running → {Succeeded | Failed | Aborted}`，`Running ↔ Blocked` 由 `graceTicks` 兜底（超时未恢复 ⇒ `Failed`）。
**R-PROC-2**：状态变化对外**只有五个原因**：`started` / `progressed` / `blocked` / `resumed` / `finished`（`ProcessObserverReasons`）。新增原因属于契约变更。
**R-PROC-3**：过程状态变化**必须**经唯一的通知出口。反例（已修）：`ProcessSystem.AdvanceUnit` 曾直接调 `Observer?.OnChanged(...)`，**绕过** `Begin` 传入的 `notify` 回调 ⇒ `progressed` 从不上总线。现在只有一个私有 `Notify(...)`。
**R-PROC-4**：过程的**副作用**（改罐子、搬液体、交付）属于"世界内容"，应当尽量集中在"推进"这一个动作里；`OnTick` 的处理器**不得**自己去改过程状态。

## 5. 时间冻结

**R-FREEZE-1**：冻结（`WorldTimeState.Paused`）期间 `JarSystem.Tick` **必须完全无效**：不推进时钟、不跑任何阶段、**不写命令日志**，直接返回 0。
理由不是为了省事，而是**回放安全**：冻结期日志里没有任何条目，因此同一份命令日志在"停过"与"没停过"两个世界里产生同一个结果。
**R-FREEZE-2**：冻结与解冻**必须**发出世界信号（`WorldSignalKind.TimePaused` / `TimeResumed`）。这是"依赖时间的逻辑"唯一能区分「世界在走」与「世界停了」的途径。
**R-FREEZE-3**：`ElapsedSince(tick)` 对负数或未来 tick **必须**抛 `ArgumentOutOfRangeException`，不得静默返回 0 或负数。

## 6. 事件级联（一个操作引发一连串世界变化）

**R-CASCADE-1**：级联**必须**通过管线的第 ① 阶段落地，不得在信号分发期间直接改世界。理由：分发时世界还处在"改到一半"的状态，此刻读到的任何东西都不可靠。
**R-CASCADE-2**：`WorldBus.DrainForTick(tick)` **必须先取走再清空**。效果执行期间新排定的效果落到**下一批** ⇒ **级联严格一 tick 一跳**，不得在同 tick 内自激。这是回放可复现的必要条件。
**R-CASCADE-3**：级联**必须**有界（`MaxEffectsPerTick = 256`、`MaxSignalsPerDispatch = 1024`），超限**必须**显式计数丢弃，不得静默增长。
**R-CASCADE-4**：事件不让别的模块"做事"，只让别的模块"**缓存失效**"。第一个真实反应器 `FeasibilityInvalidationReactor` 做的就是这件事：世界资源一变，待定订单的可行性缓存作废。
**R-CASCADE-5**：基于缓存失效的重算**不得**按"世界修订号"判等。反例（已修）：`JarSystem.Tick` 每 tick 都无条件 `Record(WorldOps.Tick)` ⇒ 修订号几乎每 tick 都变，"按修订号复用"永不命中。正确做法是按**内容指纹**（`OrderService.WorldSignature()`：主从台选择 + 每台标记/禁令 + 罐子集合含 Id + 每台液池）。

## 7. 互斥规则

**R-MUTEX-1**：迁徙进行中**不得**执行订单；订单执行中**不得**开始迁徙。双向拒绝。
依据：迁徙更新的是**工作台配置**，而任何订单执行都以工作台为前提。
**R-MUTEX-2**：**不得**实现"阻断订单 → 迁徙 → 恢复订单"。恢复时手里的计划仍然基于旧配置，那正是缓存失效要防的那类错误。宁可让玩家自己决定先后。
**R-MUTEX-3**：同步轨（`executeOrder` / `setMaster`）**不**加互斥——它们在一个调用内跑完，不存在交错的可能。

## 8. 回收语义（与事件治理的边界）

**R-POOL-1**：对象回收**不得**改变任何可观察状态。`Rent` 出来的对象必须与 `new` 逐字段等价。
**R-POOL-2**：归还一个对象 = 断言"世界上再没有第二处引用它"。这个断言**必须**由结构保证，而不是由注释保证：被回收后再读写**必须**抛异常。实现：`Jar.IsRecycled` + `JarPool.Return` 对重复归还返回 `false`。
**R-POOL-3**：只有能证明"已经彻底离开世界"的位置才允许归还。仍被引用的地方（审计记录、事件历史、快照）**一律不还**。
**R-POOL-4**：回收**不得**进入任何可观察通道——它不产生事件、不进日志、不发信号。它是资源生命周期，不是世界变化。

## 9. 新增事件的检查清单（照着做，不要凭感觉）

1. **它会失败吗？** 会 ⇒ 选「全退」或「代价不退」；不会 ⇒ 「无失败」。
2. **选「全退」**：回滚是否覆盖它可能改的**全部**字段？有没有"取消"这条独立失败路径没处理？
3. **选「代价不退」**：代价是什么？它是不是玩家主动投入的稀缺资源？如果答不上来，说明它不是 E3 这一类。
4. **需要中间态 / 需要被反对 / 需要时间成本**，占其一 ⇒ 必须走 `ProcessSystem`，并声明 `graceTicks`。
5. **它会改世界吗？** 会 ⇒ 必须经 `Record(...)` 落命令日志。
6. **要进 `eventHistory` 吗？** 进 ⇒ 确认它已在命令日志里，并接受 `MaxEventHistory = 10` 的裁剪。
7. **要发世界信号吗？** 发 ⇒ 必须带 `Tick` + `Revision`，且不得在信号里改世界。
8. **会不会和其他事件争同一块世界？** 会 ⇒ 定互斥规则，双向拒绝，并写测试。
9. **它改了世界的参数还是内容？** 参数 ⇒ 即时配置；内容 ⇒ 走前 1~4 步。
10. **写一条"观察者不改变世界"的测试**：两个同种子同命令序列的世界，一个挂订阅者一个不挂，状态必须逐字相同。

## 10. 待定项

**D1｜配置类命令是否补 `eventHistory`。**（**已定案：补。** 实现见 §3 E5 与 D4 整改）
现状：`UpdateProducerRate` / `SetLiquidProductionRate` / `SetFlowSettings` 只写命令日志。
问题：它们不会失败，但世界事件里查不到"产线速率被改过"。
**约束**：这一项一旦动，`eventHistory` 的形状就变，`REPLAY-OK` 的 `stateBytes` 随之变。按 `CONSTRAINTS.md` 的 I4，契约快照 + schema + `contract.d.ts` + 协议清单 + 回放资产**必须在同一次有意的改动里一起移动**。因此它**不得**与无关改动混批。
**倾向**：补。理由是"配置也是世界的一部分，玩家复盘时应当能看见自己改过速率"；代价是契约五件套要一起动。

**D2｜`WorldBus` 的观察者是否允许跨 tick 持有信号。**（**已定案：禁止转存。**）
现状：`WorldSignal` 是 `readonly struct`（零分配），没有生命周期约束。

**规则**：信号只在分发期间有效。需要延后使用只许复制 `Tick` / `Revision` 两个整数，并在使用前与当前值比一次；**不要**持有整个信号。

**理由（实测，不是论述）**：`test/JarSystem.Tests/RuntimeRetentionTests.CapturedSignalRevisionIsStaleByTheTimeTheEffectRuns` 把陷阱做成可教学的刻画——
反应器在 tick 1 收到信号（`Tick=T1`）并排一条效果，效果在 tick 2 的第 ① 步执行，此时 `Time.Tick = T1+1`。**信号描述的是过去那个 tick 的世界**。
一个容易搞错的细节：`Revision` 在这条路径上**不会**变大——`Record` 在 `Tick` 末尾才递增编号，所以跨 tick 持有真正丢的是**时间位置**（Tick），不是编号。这条测试断言的是 `TickAtEffectRun > CapturedTick`。
守卫位置：`src/JarSystem.Core/World/IWorldObserver.cs` 的接口文档写明这条纪律（`readonly struct` 存一份永远编译通过，只能靠条文 + 测试守）。
将来若确实需要"可延后的信号流"，应**另开一个通道**（带自己的生命周期与容量），不要复用 `WorldSignal`。

**D4｜`eventHistory` 的形状统一（R-OBS-6 的整改）。**（**已定案并完成。**）
现状：两种形状并存，订单事件没有类型字段（详见 R-OBS-6）。
约束：这是**契约变更**——`event_history` 的结构进 `state.schema.json` 与 `state_keys.baseline.txt`，形状一改，`REPLAY-OK` 的 `stateBytes` 随之变。必须与 D1 一起、作为**一次**有意的改动来做，五件套同时移动。
倾向：给订单事件补 `["type"] = "order_event"`，并考虑把两条换台轨的 `AddEvent` 收成一处。

**D3｜过程日志的裁剪策略。**（**已定案：保持有界 + 显式可查缺口。**）
现状：`ProcessJournal.DefaultCapacity = 4096`，append-only；满时**成批丢弃最旧的一半**（摊销 O(1)），`seq` 全局单调。

**规则**：一整局的可回溯性由命令日志（`_commandLog`，刻意无界）承担；过程日志只做**近端诊断**，允许裁剪，但必须让消费方能发现缺口。

**为此新增三个只读成员**（`src/JarSystem.Core/Process/Journal/ProcessJournal.cs`）：`FirstSeq`（保留条目里的最小序号）、`LastSeq`、`IsTruncated`（`DroppedEntries > 0`）。恒等式：`FirstSeq == DroppedEntries + 1`（有保留时）、`DroppedEntries == 累计追加 − 保留条数`。

**消费方的硬纪律**：`IsTruncated == true` 时，"没有记录"必须读成"没有**保留的**记录"，不能读成"没发生过"。

守卫：`RuntimeRetentionTests.TrimmingKeepsSequenceContinuousAndReportsTheGap`（capacity=8 灌 40 条，断言三条恒等式 + 保留条目首尾相接无洞）、`JournalWithinCapacityIsNotTruncated`（容量内不裁剪、`Clear()` 一并归零）。
