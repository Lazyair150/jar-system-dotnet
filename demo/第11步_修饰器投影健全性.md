# 第 11 步：修饰器投影的健全性（用规则表抓出的第四例同类错误）

## 一、这一轮在追什么

规则表（第 10 步）落地后，有一个"其它操作程序"仍然按**类型**而不是按**规则**判断：
`src/JarSystem.Core/Rules/ModifierAwareSolver.cs`。它把修饰器"折进求解器输入"时，用的是一个
`switch (m)` —— 按修饰器的**种类与字段**猜"这条规则等价于什么"。

这正是用户在最初提的那个问题的另一半：如果规则可以被查询，那么需要规则的程序就不该自己猜。
而"猜"在修饰器这里有一个现成的破口。

## 二、被抓住的错误

原来这一条：

```csharp
case SuppressModifier s when !string.IsNullOrEmpty(s.Liquid)
    && s.Operation is null or "POUR_IN" or "POUR_OUT" or "RESHAPE":
    if (!banned.Contains(s.Liquid)) banned.Add(s.Liquid);   // 折成"这种液体被禁"
    break;
```

它假设「抑制某种液体的**某一种**操作」等价于「这种液体被禁」。这个假设在**该台 Ban 列表里没有这种液体**时多禁了一半
（前置条件必须写明：一旦这种液体本来就被该台禁止，那三行全都不可行，折叠反而是精确的）：

| （前提：该台 Ban 里没有酒，规则只抑制「灌入酒」） | 真执行（`Workshop`） | 投影后的求解器 |
|---|---|---|
| 空罐用酒灌入 | 被抑制 ✅ | 被禁 ✅（一致） |
| 满罐改形，自耗罐内的酒 | **合法** | 被禁 ❌（多禁） |
| 空罐改形，用酒作成本 | **合法** | 被禁 ❌（多禁） |

于是出现了最坏的一种结果：**真执行做得到，而"自动检验"说不可行**。
这与史上那 105 例错杀是同一个形状——把一条不完整的推理当成完备的，然后据此否定。

### 禁令与抑制是两条不同的通道（这一节的由来）

我初稿把上面那张表写成无条件的，用户指出**若该台禁止酒，装了酒的罐子即使形状对也不能改形、也不能倒出**。
核实后用户是对的，而且这恰好解释了为什么 `Operation is null` 那条分支折叠成"被禁"是**精确**的：

| | 禁令 `WorkshopCapability.Ban`（基础法则） | 抑制 `SuppressModifier`（修饰器） |
|---|---|---|
| 谁在读它 | `Workshop.IsBanned` → `_rules.IsBanned` → `_capability.IsBanned`（`RuleContext.cs:48`） | `_rules.SuppressionReason(op, shape, liquid)`（`ModifierStack.cs:80-100`） |
| 看修饰器栈吗 | **完全不看** | 就是它 |
| 覆盖范围 | 倒入、存储、空罐改形成本、倒出、满罐改形自耗 —— **整种液体的所有用法** | 只覆盖它点名的那个 `Operation`（`:89` 的操作过滤） |
| 折进求解器的正确方式 | 折成"被禁"（等价） | **不可折**，如实回"未判定" |

四处禁令落点（都在 `src/JarSystem.Core/Domain/Workshop.cs`）：`PourIn:279`、`PourOut:290`、
`ReshapeEmpty` 经 `TryPayReshapeCost` → `HasUsableLiquid:162`（以及 `AddLiquid:174`）、
`ReshapeFull:313`（`if (IsBanned(l!)) { j.PourIn(l!); return (false, "工作台禁" + l); }`）。

守这条差别的测试是 `BanBlocksEveryUseOfThatLiquidWhileSuppressionBlocksOnlyTheNamedOperation`：
同一只 `三角罐:酒`，`Ban=[]` 时改形与倒出都成功，`Ban=[酒]` 时两者都失败。

## 三、先写失败的测试（不是先写修复）

`test/JarSystem.Tests/ModifierProjectionTests.cs` 三条：

1. `PourInOnlySuppressionStillAllowsFullReshapeUsingThatLiquid`
   —— 建一个真的 `Workshop`（带抑制栈），把 `三角罐:酒` 改成 `方罐`，断言**执行成功**。
   这一条是**地面真值**：它不依赖求解器，直接问执行器。
2. `SolverNeverCallsAnInexpressibleRuleInfeasible`
   —— 同样的场景交给求解器，要求它**不许说不可行**：要么精确表达，要么如实回"未判定"。
   修复前它返回 `Feasible=false, BudgetExceeded=false`（即"确定不可行"），测试红。
3. `WholeLiquidSuppressionIsProjectedExactly`
   —— 反向：`Operation` 为 null（整种液体不可用）时折成"被禁"确实是精确的，
   原有的能力必须保住，不能因为修 bug 把它一起退化成"未判定"。

## 四、修复

把那条 case 拆成两条，判据从"操作是这几个之一"改成"操作**不限**"：

- `s.Operation is null` ⇒ 折成"被禁"（精确，理由写进注释：禁令恰好同时覆盖倒入、存储、
  作为空罐改形的成本、倒出、以及满罐改形的自耗）。
- 其它 ⇒ `_inconclusive = "当前规则含求解器无法表达的限制：" + m.Name + "（只抑制液体 … 的 … 操作，而求解器只有「整种液体被禁」这一种投影）"`，
  返回 `Feasible=false` 但**置** `BudgetExceeded`。

关键点：**"未判定"与"不可行"必须是两个答案**。前者说"我不知道"，后者说"世界做不到"——
用前者冒充后者，就会让玩家看到一张明明能做的订单被判红。
