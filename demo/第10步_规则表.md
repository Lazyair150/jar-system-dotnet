# 第 10 步：工作台规则表（把"两边都知道规则"变成可执行断言）

## 一、动手前的问题

「是否有这样的设计：工作台提供操作接口，其它程序用接口去操作罐子资源？」

查完代码，答案是**一半**：

**有的那一半（执行层）** —— `src/JarSystem.Core/Domain/Workshop.cs` 对外只有四个操作，
全部返回 `(成功, 原因)`，规则关在里面而不是散在调用方：

| 行 | 签名 |
| --- | --- |
| `:274` | `PourIn(Jar j, string l)` |
| `:285` | `PourOut(Jar j)` → `(bool, string?, string? Liquid)` |
| `:296` | `ReshapeEmpty(Jar j, string to, string cost)` |
| `:306` | `ReshapeFull(Jar j, string to)` |

而且 `Domain/Jar.cs` 里改罐子的方法**全是 `internal`**（`Mark`/`Unmark`/`PourIn`/`ClearLiquid`/
`RestoreLiquid`/`Reshape`），跨程序集改不了 —— 结构上钉死了「`Workshop` 是唯一执行者」。

**缺的那一半（能力清单层）** —— `Domain/WorkshopCapability.cs` 只有五个成员：
`IsBaseMarked`/`IsAdditionalMarked`/`IsBanned`/`GetPossibleTransforms`/`CanTransform`。
它能回答"这个形状能不能变成那个"，**不能回答"我现在能对这只罐子做哪几件事"**。

后果是"哪些操作可用"这份枚举被各写一遍：内核求解器在 `Solver/StateSpaceSolver.cs:270/285/301/313/340`
自己拼，原型 JS 的 `tryOp` 另写一份。**过去三次同类错误都是这个形状**：

1. 前置检查把 `IsBanned` 挡在 MATCH 之前（105 例错杀）；
2. 原型 `tryOp` 漏了 `IsBaseMarked`，于是"附加标记形状装液体"凭空可行；
3. 更早那次把"液体要么在池子里、要么在这只罐子里"当成完备推理。

## 二、这一版做了什么

新增 `src/JarSystem.Core/Domain/WorkshopRulebook.cs`（Domain 层，与规则同一处）：

```csharp
public enum WorkshopOperationKind { PourIn, PourOut, ReshapeEmpty, ReshapeFull }
public readonly struct WorkshopOperation      // 只描述意图：Kinds + 目标形状/液体/成本液体
public readonly struct JarFacts               // 形状 + 罐内液体 + 是否已被操作
public static class WorkshopRulebook
{
    public static bool IsAllowed(RuleContext rules, int maxLiquids, in JarFacts jar,
                                 in WorkshopOperation op, IReadOnlyDictionary<string,int> liquids);
    public static List<WorkshopOperation> Available(RuleContext rules, int maxLiquids,
                                                    in JarFacts jar, IReadOnlyDictionary<string,int> liquids);
}
```

它**不执行任何操作**，也**不持有罐子对象**：只把 `Workshop` 里那几道判定按同样顺序重述一遍，
输入是纯事实。判定走 `RuleContext`，所以抑制类与授予类修饰器自动生效，空栈时与改造前逐项相同。

## 三、为什么它不去"强制"求解器调用它

这是这次设计里唯一需要交代清楚的取舍。

`Solver/StateSpaceSolver.cs` 的 `GenOps` 在**几十万节点的热路径**上被调用。让它每节点构造一次
`WorkshopOperation` 描述符，等于把分配压进搜索预算 —— 而它本来就只需要三个判定
（`IsBanned`/`IsBaseMarked`/`CanTransform`）加库存与转移预算，**它自己知道规则**。

所以：**执行器与求解器都不必调这张表**。用户的原话就是这个意思——"只要知道规则就行"。

那这张表存在的意义是另一件事：把"两边都知道同一套规则"从**口头约定**变成**可执行断言**。
一旦有一条测试对每个 `(罐子, 工作台, 候选操作)` 断言
「`WorkshopRulebook.IsAllowed` 与 `Workshop.xxx` 的执行结果一致」，
任何一方单独改规则都会被立刻抓住。

## 四、对拍测试（`test/JarSystem.Tests/WorkshopRulebookTests.cs`，4 条）

| 测试 | 守住什么 |
| --- | --- |
| `RulebookAgreesWithExecutionOnEveryCombination` | 三套工作台（玄武/朱雀/无禁令）× 8 形状 × 空/酒/蜜 × 已操作/未操作 × 5 种液体账目 × 27 个候选操作 = **23,328 次**，逐个断言规则表判定 == 真执行结果 |
| `AvailableListsExactlyTheAllowedSet` | 枚举入口与判定入口自洽：列出来的恰好是判定为真的那批，不多不少 |
| `PourOutIsBlockedExactlyWhenThatLiquidStorageIsFull` | 容量是**每种液体各自**的（酒满不影响蜜）——写成总数会悄悄改掉液池语义 |
| `SuppressedOperationIsRefusedByBothRulebookAndExecution` | 抑制类修饰器让规则表与执行**同时**翻转；且只抑制灌入时不波及改形 |

关键设计：候选操作宇宙**不预筛**（`Universe()` 里 27 个候选一律跑），因为预筛会掩盖
"规则少了某道门"这类错误——那正是要抓的东西。

## 六、还没做的一件事（明确记下）

原型 JS（`demo/_退役/puzzle_engine.js` 的 `tryOp`）仍然是**第三份枚举**，本次没动它。
它离内核最远、也最容易漂移（上次那个 bug 就出在这里）。若要收口，做法是在
`_test_engine.js` 里加一段：对随机池子逐个 `tryOp` 候选，与"按同一套规则推断的合法集"比对。
这件事没做，理由是它属于原型线的收尾，而原型当前正等下一步的玩法推进。
