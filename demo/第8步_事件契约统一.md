# 第 8 步：事件契约统一（D1 + D4 合并为一次有意的契约变更）

> 这一步动的是**契约**（`eventHistory` 的结构），所以它的第一条要求不是"写对代码"，而是
> **"证明这次动基线是合规的，而且只动一次"**。本文按这个顺序写。

## 0. 为什么要合并成一次

原本有两件独立的事：

- **D1**：`UpdateProducerRate` / `SetLiquidProductionRate` / `SetFlowSettings` 只写命令日志，不进 `eventHistory`。
- **D4**：`eventHistory` 里并存两种形状 —— 换台有 `type`，订单事件**没有** `type`（消费方只能靠"看它有没有 `order` 键"来猜）。

如果只做 D1，就是往一个本来就没有统一 schema 的通道里塞**第三种**形状。那会让 D4 从"两种形状"变成"三种形状"，问题更糟。所以两件合并，一次改到位。

## 1. 为什么这次可以动基线（`CONSTRAINTS.md` I4 的逐条对照）

I4 的原文要求是：契约变更必须让**契约快照、schema、`contract.d.ts`、协议清单、回放资产**在同一次有意的改动里一起移动。

| schema `_contract/state.schema.json` | **未变** | `git status` 无该文件；门禁 `schema total loose=1`、11 types 全部 OK（`eventHistory` 本来就是 `Dictionary<string, object?>` 的松散项，加键不改类型） |

**为什么这是合规的而不是"静默重基线"**：

1. 改动是**有意的**——本文就是那次改动的书面记录，且在同一次改动内完成；
2. 没有**削弱**任何检查：`stateBytes` 数字仍然被逐字节比对，只是期望值随这次有意的形状变更一起移动；
3. **`logBytes=8797` 与 `journalBytes=725` 完全未变** —— 命令日志与过程日志一个字节都没动，说明这次改的只是"世界事件流的形状"，不是"世界本身的行为"。这是"改动范围确实只有那么大"的直接证据；
4. `SOLVER-OK (compared=4003, agree=4003, feasible=583, undetermined=0, targeted=3)`、`MODDIFF-OK (scenarios=400, checks=1600)` 与改前**逐字相同** —— 求解器与修饰器语义完全没被波及。

## 2. 改了什么（三处）

### 2.1 换台事件：两处拼字典 → 一个发射点

改前有**两个地方各拼一份同样的字典**：`JarSystem.CommitSwitch`（异步轨）与 `Services/MasterSwitchCoordinator.cs:57`（同步轨）。形状一旦有人只改一边就会分叉。

现在统一为 `JarSystem.AddWorkshopSwitchEvent(from, to, caseType, operations)`，两条轨都调它。**形状逐字不变**（所以 `state_keys` 的换台部分没有变化）。

### 2.2 订单事件：补 `type`

`Services/OrderService.cs:270` 与 `:285` 两处字典各加一行 `["type"] = "order_event"`。这是 `stateBytes` 变化的唯一来源。

### 2.3 配置命令：补可识别的事件

`JarSystem.AddConfigEvent(kind, fields)`，三个调用点：

| 命令 | `type` | 字段 |
|---|---|---|
| `SetFlowSettings` | `flow_settings` | `jarCount`、`liquidAmount` |
| `UpdateProducerRate` | `producer_rate` | `producer`、`shape`、`rate` |
| `UpdateLiquidProductionRate` | `liquid_rate` | `liquid`、`rate` |

三条都带 `timestamp`（**意图时间**，`Now.ToString("o")`，与既有事件一致；回放时由 `Record` 的时序复现）。

**事件发在门面（也 `Record` 的那一层），不发在 `Core`**：`ProductionService.UpdateLiquidProductionRate` 的注释明写「走 Core（不写日志）—— 会话日志由门面的 UpdateLiquidProductionRate 记一条即可」。若在 Core 里发事件，任何直接调 Service 的路径就会产出"没有对应命令日志的事件"，违反 R-OBS-2。

## 3. 过程中发现并修掉的一个潜在运行时崩溃

第一版 `AddConfigEvent` 的签名是 `(kind, subjectKey, subject, value)`，而 `flow_settings` 的调用写成了：

```csharp
AddConfigEvent("flow_settings", "value", jarCount + "/" + liquidAmount, $"{jarCount}罐+{liquidAmount}液");
```

字典初始化里 `["value"]` 出现**两次** ⇒ 运行时 `ArgumentException: 已添加了具有相同键的项`。

**它没有被门禁抓到**——因为契约快照的固定场景根本不调用 `setFlowSettings`。这正是"必须在测试里真的走一遍这条路径"的理由。现在的签名叫 `(kind, fields)`，字段由调用方给（三种配置的字段本来就不同，硬塞成一个 `value` 只会让消费方继续猜）。

## 4. 新测试（`test/JarSystem.Tests/WorldEventShapeTests.cs`，3 条）

| 测试 | 守什么 |
|---|---|
| `EveryEventHasTypeField` | R-OBS-6：**任何**进 `eventHistory` 的条目都必须带非空 `type`。它同时走过三条配置命脉（流入/液率/产率），所以上面那个重复键 bug 会被它抓到 |
| `ConfigCommandsEmitTypedEvents` | §3 E5：三类配置各发一条可识别事件，且字段值随命令走 |
| `SwitchEventShapeIsIdenticalOnBothTracks` | 换台事件只有一个发射点：两条轨产出的**键集合**必须相同、值必须相同（`timestamp` 除外） |

写第三条时踩到一个真实的语义细节：**旧主台没有资源时 `SetMaster` 只改指针、根本不发事件**（`MasterSwitchCoordinator` 的 `hasResources` 判据）。所以测试必须先 `SetMaster(0)` 钉住主台再 `Tick(20)` 产出资源，否则 `Single()` 找不到事件 —— 这是判据本身的正确行为，不是缺陷。
