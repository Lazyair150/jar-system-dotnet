# 原型修复：装液必须落在「基础标记」的形状上

## 一句话

`puzzle_engine.js` 的 `tryOp` 少了一道门 —— 原系统 `Workshop.PourIn` 要求**罐子的形状是该台的基础标记**，原型允许往附加标记的形状里倒液。补上之后，四个关卡订单变成不可完成，因为它们原来靠这条不存在的路。

## 一、怎么发现的（不是靠读代码，是靠自检）

`_test_engine.js` 里有一段「下界正确性抽查」，名义上验证「`grow` 说能长到 N ⇒ 把它的 steps 真的执行一遍，看是否全部成立」。它一直在报

```
抽查 120 次，重演不一致 55 次
```

我原本以为这是引擎的问题，读下去发现**是这段自检本身坏的**：

1. `function reqLiquidOf(od, st) { return null; }` —— 一个**恒返回 null 的桩**。于是每一条重演步骤都被当成「空罐需求」，装配液的那一步必然对不上。
2. `var def = BENCHES[Math.floor(Math.random() * BENCHES.length)]` —— 随机挑一台当规则来源，与罐子实际所在的台无关。
3. `sim` 是从 `jars` 拷的 `{shape, liquid}`，**丢了 `home`**，而 `home` 决定用哪套能力规则。
4. 用 `st.op.to` 当"目标形状"、把需求改成 `{shape, liquid: null}`，等于自己构造了一个假需求。

四条叠起来 ⇒ 报出来的 45% 是假警报。而一个"永远报错所以没人看"的检查比没有检查更糟。

## 二、重写后的检查

- 池子里的罐子带 `home`（来自该关真实存在的工作台），`def` 取主台。
- 每条 step **按 5 种 op 的规则逐条独立复核**（`match` / `pourout` / `pourin` / `reshape` / `reshapefull`），用 `ENG.canTransform` / `isBanned` / `isBaseMarked`，并强制「一罐一操作」。
- 复核通过后**自己**推进模拟状态（不调用引擎的 `applyOp`，避免循环论证）。
- 最后**独立地**数一数终态满足了几条需求，要求 `≥ grow 报的 height`。

重写后立刻报出 **120 次里 2 次非法步骤**：

```
! pourin 无钱/非基础  jar=三角罐 base=圆罐,方罐
```

`三角罐` 在玄武台是**附加标记**，按原系统根本倒不进液体。于是找到了 `tryOp` 里那缺失的一行。

## 三、修的那一行

```js
// puzzle_engine.js tryOp()，需求 =「装着 wantLiquid 的罐」
if (jar.liquid === null) {
  if (!isBaseMarked(d, jar.shape)) return null;   // ← 新加：原系统 Workshop.PourIn 的第三道门
  if ((liquid[wantLiquid] || 0) >= 1) return { op: 'pourin', liquid: wantLiquid };
  return null;
}
```

原系统 `Workshop.PourIn` 的三道门是：未标记 / 形状是基础标记 / 液体未被禁。原型此前只有二、三两道。少一道的后果不是报错，而是**凭空多出一条路** —— 所有"附加标记形状装液体"的订单都能白做。

## 四、连带修掉的四个关卡订单

补上门之后，四个订单变成不可完成（每个都是「某形状(空) + 同形状:液体」，而那个形状在该关任何一台里都**不能灌**）：

| 位置 | 原订单 | 改为 | 依据 |
|---|---|---|---|
| L2 #1 | 三角罐(空) + 三角罐:蜜 | 三角罐(空) + **圆罐:蜜** | 玄武台基础含圆罐、不忌蜜 |
| L3 #1 | 扁罐(空) + 扁罐:酒 | 扁罐(空) + **长罐:酒** | 青龙台基础含长罐、不忌酒（白虎台忌酒 ⇒ 正是"禁令逼你换台"） |
| L3 #2 | 三角罐(空) + 三角罐:蜜 | 三角罐(空) + **三角罐:酒** | 青龙台基础含三角罐、不忌酒 |
| L4 #4 | 尖罐(空) + 尖罐:蜜 | 尖罐(空) + **扁罐:蜜** | 白虎台基础含扁罐、不忌蜜；尖罐由扁罐改形而来（base→additional 允许） |

判断一个"装满某液体的形状需求"能否成立，判据是：**∃ 一台，`shape ∈ base` 且 `liquid ∉ ban`**。只看"有没有台把形状算基础标记"会漏掉禁令那一半——我第一次扫描就是这么漏掉的。

## 五、修完之后的自检结果

| 脚本 | 结果 |
|---|---|
| `_test_engine.js` | 下界抽查 OK：120 次，**非法步骤 0，承诺未兑现 0** |
| `_test_levels.js` | L2 WIN@2 3/3、L4 WIN@11 4/4、**L3 2/3**（贪心自动打手差一口气，未证明不可解） |
| `_test_battle.js` | 锁死判定误判 0 次 |
| `_smoke_ui.js` / `_smoke_battle_ui.js` | 全过 |

L3 的 2/3 是**没有证明可解**，不是"证明不可解"——它需要三只三角罐 + 一只长罐挤在六个罐位里，贪心打手在上面差一步。这属于自动化打手的局限，需要人玩或更强的规划器才能判定。

## 六、顺带得到的教训

1. **自检脚本也会腐坏**，而且腐坏得比产品代码更隐蔽——它出问题时的表现是"报一个没人细看的数字"。凡是报数字的检查，必须能指着一条具体失败解释它是怎么失败的（所以重写版把失败的 op、罐子、台、产地都打出来）。
2. **原型的规则必须与内核逐条对齐**，否则两个世界会漂移。这次是"原型比内核宽松"，漂移方向是让人以为某关能过。
3. 一个"能让玩家白拿一步"的规则缺漏，比一个崩溃更危险：崩溃会立刻被修，白拿会被当成设计。
