**可替换性**（这是"换算法不改调用方"的标准做法，既有的 `ISolver` 抽象就是接缝）：

```csharp
new FeasibilityChecker()                                   // 新版（默认）
new FeasibilityChecker(new StateSpaceSolver())             // 换回裸实现
new FeasibilityChecker(new PrecheckedStateSpaceSolver())   // 显式指定
```

三行都是合法宿主编译期选择，调用方一行不用改。两套实现同时存在，可互相对拍。

## 二、为什么是"前置检查"而不是"改搜索"

原求解器的最坏情形是**不可行的 B 类订单**：它必须把整棵搜索树走空才会回答"不可行"，
`StateSpaceSolver.cs:212-214` 自己写明「20 罐 / 8 需求一次求解就超过 240 秒」。
而"不可行"常常能用**多项式时间**证明 —— 把这部分提到搜索之前，就得到
"不可行的题秒回、可行的题才进搜索"的形状。

两条健全判据（**只放宽、不错杀**）：

1. **一罐一操作容量**：`需求数 ≤ 非主台罐数 + min(主台罐数, 转移预算)`。
2. **需求↔罐子二分图完美匹配**（Kuhn）：一个可行解必然给每个需求分配一个**互不相同**的罐子，
   不存在这样的分配 ⇒ 必然无解。服务关系放宽判定（宁可高估）。

其中最锋利的一条来自操作集本身：**满罐需求只能由"形状已经是该形状"的罐子承担** ——
因为改形与灌液是两次操作，而一罐一操作。这条比任何搜索剪枝都强。

## 三、实测数据（`dotnet run --project test/SolverBench/SolverBench.csproj -c Release`）

同一批 900 个场景分别喂给裸 `StateSpaceSolver` 与 `PrecheckedStateSpaceSolver`：

| 指标 | 旧（裸实现） | 新（前置检查） |
|---|---|---|
| 场景数 | 900 | 900 |
| 结论可比较 / 一致 | 898 / 898 | 898 / 898 |
| **判定不一致** | — | **0** |
| **健全性违反**（旧可行→新不可行） | — | **0** |
| **未判定（预算耗尽）** | **2** | **0** |
| 搜索总节点 | 1,076,419 | 10,744（**−99.0%**） |
| 总耗时 | 2,619 ms | 9 ms（**62.56×**） |

场景构成：`random` 400 / `capacity` 400 / `adversarial` 60 / `exploding` 40
（exploding 专造"形状可达但液体稀缺"的对抗样本，用来逼出预算耗尽）。

## 五、诚实边界（它没解决什么）

- **指数本身没有被根除**。这是 NP 难问题，前置检查只是把"不可行"这一半从指数
  拉到多项式；**可行的重活仍然靠原搜索**。
- **真正的时间黑洞是 `EmptyOps` 的改形扇出**（每个可用成本液体 × 每个可改形空罐），
  前置检查对它**没有帮助**——恰恰相反，扇出最大的场景通常就是匹配能通过的那些。
- 想真正压住扇出，要动的是 `ni = idx` 那条"倒液体不推进下标"的规则（把液体预算从
  搜索里提出来当可数的资源），那需要**重写搜索语义**并重新论证等价性，风险远高于本次改动。
  本次刻意没有碰它。
- 基准里的 2 个"救回"样本说明前置检查确实能在真实预算耗尽点上给出确定答案，
  但样本量小，**不足以宣称"解决了 240 秒问题"**。
