# 第 7 步：罐子对象池

## 0. 先纠正我上一轮的错

我上一轮说"池化不安全"，理由是"求解器对象必须在结束时完全失效"。**这条理由是假的**：

- `src/JarSystem.Core/Solver/StateSpaceSolver.cs` **一处都没用过 `Jar` 类型**，它操作的是 `List<JarState>`；
- `JarState` 是**无身份的纯值**（`Descriptor(JarState j)` 的注释原文写着「不含 Id」），定位用的是 `j.JarIndex` 这个 int 下标；
- 我说的"71 秒 → 890 秒"是**跨调用复用 `_failedStates` 搜索缓存**的负优化，跟对象池是两件事，我把它们混成了一件。

你指出的判据是对的：**求解器要是需要记住罐子的地址，那它就不是在按数学求解了。** 它确实没有。

## 1. 池化的唯一危险，以及怎么让它炸出来

罐子是这个世界里唯一**持续产出又持续消失**的实体（生产者每 tick 造、仓库溢出丢、换台装不下丢），也是唯一带身份（`int? Id`）的领域对象。

危险只有一条：**归还一只罐子 = 断言"世界上再没有第二处引用它"。** 这个断言一旦错，两处代码就持有了同一只罐子互相覆盖，而且**不报错**。

所以本实现不去"小心一点"，而是把它变成**当场炸**：

- `Jar.IsRecycled`：归还后置位，此后**每一次读写都抛 `InvalidOperationException`**（`Id`/`Shape`/`Liquid`/`IsMarked` 的 getter、`GetDescription`、`IsEmpty/IsFull`、`DeepClone`、以及全部 internal 变更方法）。
- `JarPool.Return` 对**重复归还**返回 `false`（说明有两个地方都在还同一只）。
- 池按**词表引用**匹配（`HasVocabulary`）：不同词表的罐子不复用，否则改形校验会用错词表。

由此得到一条可以逐字照做的规矩，写在 `JarPool` 的类注释里：
> 只有能证明"已经彻底离开世界"的位置才允许 `Return`；仍被引用的地方（交付记录 `OrderEvent._deliveredJars`、事件历史、快照）**一律不还**。

## 2. 允许归还的位置（只有两处，都是"丢弃"）

| 位置 | 为什么安全 |
|---|---|
| `Production/Warehouse.StoreJars` 溢出分支 | `规则.txt` 规定溢出**直接丢弃并计数、不回流** ⇒ 丢弃即离开世界 |
| `Orders/Switching/ResourceTransferrer` 的 `discard_jar` | 换台时新主台容量已满，罐子被丢掉且不回流中央仓库 |

而 `ResourceTransferrer` 里那句 `log.Add("discard_jar", $"丢弃 {jar.GetDescription()}…")` **必须先于** `Return` —— 归还后再 `GetDescription()` 就会抛，这正是回收标记要拦的那类误用。

**明确不还的地方**：`OrderEvent.Deliver` 移除罐子后仍把引用留在 `_deliveredJars`（审计与回滚依据）；`Workshop.CreateSnapshot()` / `RestoreFromSnapshot` 克隆出的罐子会逃逸到调用方。这些都不进池。

## 3. 接入点

- `JarSystem.JarPool`：世界级、每个世界一份（不跨世界共享，避免泄漏）。
- `ProducerModule(..., JarPool? pool = null)` → 转交 `ShapeProductionLine`（真正造罐子的地方）与 `Warehouse`。
- `WorkshopSwitchEvent(old, next, JarPool? pool = null)` → 转交 `ResourceTransferrer`；两条轨（`JarSystem.BeginSwitch` 与 `Services/MasterSwitchCoordinator`）都带上池。
- `pool == null` 时全部退化为直接 `new Jar(...)` ⇒ **池是可选的**，不影响任何既有调用方。

## 4. 实测

一轮 120 tick 的世界（同种子 `randomSeed: 7` + `SequentialIdGenerator`）：

```
POOLSTATS rented=360 returned=160 created=208 idle=8 discarded=160
ALLOC   new=56.0 B/jar    pooled=0.001 B/jar
```

- 借出 **360** 只，实际新建 **208** 只 ⇒ **42% 的罐子分配被复用消掉**。
- 单只成本：`new Jar(...)` **56 B**，池化后 **≈0 B**（`Rent`+`Return` 全程零分配）。

**诚实的量级评估**：这个工作负载下省下的是 `152 × 56 B ≈ 8.5 KB / 120 tick`，绝对量很小 —— 罐子不是热点。所以池化的价值不在"提速"，而在：

1. 它是**唯一带身份的实体**，回收语义一旦立起来，后续任何"高频生死 + 带身份"的对象都能照同一套规矩接入；
2. 它把"回收后仍被引用"这类错误从**静默串味**变成了**当场抛异常**，这是净收益；
3. 换来的是 `Rent` 与 `new` **逐字段等价**（`Id` 仍由工作台在入台时分配），所以确定性不受影响。

其中一条测试就是直接证明这件事的：`PoolingDoesNotChangeWorldState` 跑两遍同种子同命令的世界（一遍池化、一遍不池化），比对整份状态 JSON 必须逐字相同。

## 6. 踩到的一个坑（值得记）

`ProducerModule` 的构造函数里，生产线的创建在池赋值**之前**：

```csharp
foreach (var s in _vocabulary.Shapes)
    _generators[s] = new ShapeProductionLine(s, _vocabulary, _intensity, _pool);  // _pool 此刻还是 null
_pool = pool;
```

第一次实测是 `rented=0 returned=160 created=0` —— **池完全没参与生产**，而 160 次归还是从 `Warehouse` 溢出那条路进来的。看起来"池在工作"，其实只工作了一半。把 `_pool = pool;` 提到循环之前才对。
