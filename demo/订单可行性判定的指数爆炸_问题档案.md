# 订单可行性判定的指数爆炸：问题档案

> 一份可以冷启动接手的问题说明。
> 记录：难题是什么、长在代码的哪里、为什么必然爆炸、门禁为什么限制了解法空间、
> 已经做了什么、以及真正的瓶颈仍然在哪里。

---

## 0. 一句话

陶罐系统判定「一张订单能不能做完」用的是**指数搜索**；B 类订单要在这之上再套一层
**2^N 划分搜索**。两者相乘，最坏情形下**一次可行性检查可以跑几分钟**，
而在那几分钟里整个系统（推进、命令、自动检测）全部停摆。

这不是性能调优问题，是**算法复杂度选错了位置**的问题：
不可行的题必须走空整棵搜索树才敢回答"不可行"。

---

## 1. 上下文：这是个什么东西

**陶罐系统**（`D:\codex\jar-system-dotnet`）是一个规则驱动的资源调度解谜系统。
核心玩法是：工作台有若干形状标记（基础标记 / 附加标记）与液体禁令，
玩家用液体往罐子里倒、把空罐改形成别的形状，凑齐订单要求的一组罐子。

- 形状共 8 种，液体恰好 2 种（酒、蜜）—— 见 `src/JarSystem.Core/Config/Constants.cs`
- 「一罐一操作」是硬规则：每只罐子在一次订单执行中最多被操作一次
- 改形 → 附加标记是死胡同，出口是退回基础标记
- 系统**零随机**，回放必须逐字节一致（这是硬资产，见第 4 节）

订单分两类：

| 类 | 流程 |
|---|---|
| **A 类** | 主台独立完成，不跨台 |
| **B 类** | 主台预处理 → 选择性转移 → 从台继续 → 从台交付 |

B 类的存在是爆炸的**直接原因**：只有在「知道主台阶段结束后还剩什么」的前提下，
才能判断从台阶段能不能接上。而"主台阶段怎么划分需求"有 2^N 种可能。

## 3. 为什么必然爆炸：机制分析

### 3.1 分支因子从哪里来

`StateSpaceSolver.GenOps`（`:323`）为每条**需求**生成候选操作：

- 满罐需求 → `FullOps`（`:345`）：只有 `MATCH` 与 `POUR_IN`，**两者都不改形状**
- 空罐需求 → `EmptyOps`（`:356`）：`MATCH` + **空罐改形** + **满罐改形**
- 无论哪种，都**无条件追加**所有可倒空的满罐的 `POUR_OUT`

作者自己在 `:212-214` 留了注释，这段话是整个问题的核心：

> EmptyOps 会为「每个可用成本液体 × 每个可改形空罐」各生成一个 RESHAPE 候选
> ⇒ **分支因子 ≈ 罐子数 × 液体数、深度 = 需求数**，
> 于是 **20 罐 / 8 需求的一次求解就超过 240 秒**。

### 3.2 深度从哪里来

`Bt(reqs, idx, st, path)`（`:197`）按需求下标 `idx` 递归推进。
全仓**只有一处**允许 `idx` 不前进（`:249-257`）：

```csharp
if (op.Type == "POUR_OUT")
{
    shapeMatch = jBefore.Shape == reqs[idx].Shape;
    isEmptyReq = reqs[idx].Liquid == null;
    ni = (shapeMatch && isEmptyReq) ? idx + 1 : idx;   // ← 倒液体可以原地不动
}
```

`POUR_OUT` 是唯一「不直接满足当前需求」的操作（它只做
`TakeLiquid + MarkJar + AddLiquid`，**形状不变**），本质是**液体预算准备**。
因为它可以原地循环，搜索里就多了一条不受深度约束的路径。

### 3.3 让它更糟的两个乘数

1. **`PartitionSearch` 把 2^N 次求解串起来**（`:96`、`:108`）。
   B 类不可行的订单要对**全部 2^N 个划分各做一次主台 + 从台求解**
   （`:92-94` 有注释）。已有的单调性剪枝（`:86-95`：已证不可行的主台子集，其超集直接跳过）
   只是在减少调用**次数**，不改变单次调用的成本。
2. **预算耗尽只能报「未判定」**（第 4 节），所以"跑不完"不会变成"跑得完"，
   它只是把代价换成了一个**不可用的答案**。

### 3.4 为什么"加缓存"这条路已经试过并且失败了

`StateSpaceSolver.cs:173-176` 有一段实测记录：

> 跨调用复用 `_failedStates` 是**负优化** —— 40 万条长键堆满内存、触顶整体清空、
> 剪枝知识反复归零，实测把 C 类 8 需求从 **71 秒**拖成 **>890 秒**。
> 正确做法是**减少求解调用次数**，而不是让单次求解背全局缓存。

同一份文件 `:299-309` 还记录了另一次失败的微优化：
「角色投影」（把罐子描述符按角色而非身份归一）试过并**回退** ——
节点数一样（104,496），耗时反而慢 10%。

> **结论：这个问题的解不在常数优化里，也不在缓存里，只在结构里。**

## 4. 门禁：它约束了解法空间

改这个求解器不是"改个函数"就行，它背后有一条差分校验：

```
SOLVER-OK (compared=4003, agree=4003, feasible=583, undetermined=0, targeted=3)
```

由 `test/JarSystem.Test/Program.cs:1380 CheckSolverDifferential()` 产生：
4000 个随机/容量场景，**生产求解器 vs `ReferenceSolver`（独立 BFS 完整搜索）**逐个比判定。

`ReferenceSolver`（`test/JarSystem.Test/ReferenceSolver.cs`）是刻意"另一套写法"：
BFS 而非 DFS、状态键精确逐下标而非多重集、只记「已访问」而非「已证无解」、
不做同构合并、不设生产预算。它的注释明写：

> 操作集合、推进规则（POUR_OUT 只有在"倒空且形状等于当前空罐需求"时才推进下标）、
> 转移预算的判定，都与生产实现保持一致 —— **差分才有意义**。

### 这三条约束决定了什么能改、什么不能改

| 约束 | 出处 | 含义 |
|---|---|---|
| **只比判定，不比路径** | `Program.cs:1591-1594` 的 `a.Feasible == b.Feasible` | 改搜索结构**允许**，路径变了不算失败 |
| `undetermined` 必须保持 0 | 同上：`if (a.Undetermined \|\| b.Undetermined) { undetermined++; return; }` | **不能靠"多报未判定"来降时间** |
| 回放逐字节一致 | `REPLAY-OK (commands=33, stateBytes=3125, logBytes=8797, journalBytes=725)` | 求解路径若进状态，改搜索就会动回放字节 |

还有 `CONSTRAINTS.md` 的通用纪律：

> - 禁止删除或弱化断言、确定性用例、契约键、协议消息、回放检查
> - `Bug fixes require a regression test that fails before the fix`
> - `Structural changes must remove branches or concepts, not merely relocate them`
> - 本文件不得在同一次改动里被放宽（**Exceptions: None**）

以及一条来自 `IWorkBudgetedSolver.cs` 注释的**语义铁律**：

> 预算耗尽只能得出「**未判定**」，绝不能当成「不可行」——
> 否则会破坏本项目最关键的不变量「判定不可行 ⇒ 执行必失败」
> （贪心执行器可能仍然做成）。

## 5. 已经做了什么（安全、可替换、可度量的一步）

### 5.1 形态：多实现，不是改内层

原系统本来就有 `ISolver` 抽象（`src/JarSystem.Core/Abstractions/ISolver.cs`），
这就是"换算法不改调用方"的接缝：

```csharp
new FeasibilityChecker()                                   // 新版（已设为默认）
new FeasibilityChecker(new StateSpaceSolver())             // 换回裸实现
new FeasibilityChecker(new PrecheckedStateSpaceSolver())   // 显式指定
```

| 文件 | 性质 |
|---|---|
| `src/JarSystem.Core/Solver/SolverPrecheck.cs` | **新增**：健全性前置检查 + 进度下界 |
| `src/JarSystem.Core/Solver/PrecheckedStateSpaceSolver.cs` | **新增**：`ISolver` 第二实现，检查通过后原样委托 |
| `src/JarSystem.Core/Orders/FeasibilityChecker.cs` | **改 1 行默认构造** |
| `src/JarSystem.Core/Solver/StateSpaceSolver.cs` | **一行未动** |

### 5.2 思路：把"不可行"从指数拉到多项式

原求解器最坏的情形是**不可行的订单**——它必须走空整棵树才敢说"不可行"。
而"不可行"常常能用多项式时间证明。把这一部分提到搜索**之前**，
就得到"不可行的题秒回、可行的题才进搜索"的形状。

两条判据（**只放宽、不错杀**，这是它们的唯一契约）：

1. **一罐一操作容量**：`需求数 ≤ 非主台罐数 + min(主台罐数, 转移预算)`
2. **需求↔罐子二分图完美匹配**（Kuhn 增广路径）：一个可行解必然给每个需求分配
   一个**互不相同**的罐子；不存在这样的分配 ⇒ 必然无解

最锋利的一条来自操作集本身：

> **满罐需求只能由"形状已经是该形状"的罐子承担** ——
> 因为改形与灌液是两次操作，而一罐一操作。

### 5.3 实测（`dotnet run --project test/SolverBench/SolverBench.csproj -c Release`）

900 个场景，同一批喂给两个实现：

| 指标 | 旧（裸实现） | 新 |
|---|---|---|
| 判定不一致 | — | **0** |
| 健全性违反（旧说可行、新说不可行） | — | **0** |
| **未判定（预算耗尽）** | **2** | **0** |
| 搜索节点 | 1,076,419 | 10,744（**−99.0%**） |
| 总耗时 | 2,619 ms | 9 ms（**62.56×**） |

门禁仍全绿：`agree=4003` 逐字相同、`REPLAY` 逐字节未变、`VERDICT=OK` + `QUALITY-OK`。

### 5.4 值得记住的一次自我纠错

前置检查的第一版有 **105 个场景把"可行"错杀成"不可行"**。
根因不是笔误，而是一条我当时**确信无疑**的推理：

> "液体要么在池子里，要么在这只罐子里。"

漏掉的是第三条：**可以先把别的满罐倒空拿到液体**。这条路径在搜索里是合法的
（`POUR_OUT` 不推进下标，正是为了它），而我把它从判据里删掉了。
基准把它抓了出来——**这也是为什么要有一个会主动找反例的基准**，
而不能只靠门禁那 4000 个随机场景（`Program.cs:1389` 的注释已经警告过：
随机场景对剪枝假设是**盲的**）。

## 6. 真实瓶颈仍然在哪里

上面那一层**没有解决**指数问题。它只是把"不可行"这一半从指数拉到多项式。
真正的时间黑洞是 `EmptyOps` 的**改形扇出**：

```
分支因子 ≈ (可改形空罐数) × (可用成本液体数)      ← 每层
深度     = 需求数
乘数     = B 类的 2^N 个划分
```

前置检查对扇出**没有帮助**——恰恰相反，扇出最大的场景通常就是匹配能通过的那些。
基准里的 900 个场景只救回 2 个未判定样本，**不足以宣称"解决了 240 秒问题"**。

### 真正要动刀的地方（按风险排序）

| # | 目标 | 做法 | 风险 |
|---|---|---|---|
| 1 | **干掉 `ni = idx`** | 把液体预算从搜索里提出来当**可数的资源**（液体需求可数、供给可数），进 DFS 前先算"总供给 ≥ 总需求"，`idx` 永不原地 | **高**：要重写搜索语义并重新论证等价性 |
| 2 | **改形扇出收敛** | 2 种液体下"每个液体 × 每个罐"的候选其实高度同构，可按目标形状归并 | 中：需要新的支配性论证 |
| 3 | **需求排序换 MRV** | `RequirementOrdering.FullFirst` 现在排的是「满罐优先」，改成「能服务它的罐子数最少者优先」 | 低：只换 `OrderBy` 的键，但会改搜索路径 |
| 4 | **划分搜索换单调性** | 用已证不可行的**最小核**做上集剪枝，而非逐子集 | 中 |

关于 #1 已经有一个**原型**：`demo/puzzle_engine.js` 里的 `grow()`——它是贪心的
"幼苗"生长（逐条往上长，长不动就停，报出「灌注 3/7」的进度），复杂度 O(N × 罐子数)。
**但它既不能证可行也不能证不可行**（贪心失败 ≠ 无解），所以：
可以拿去给玩家显示进度，**不可以**拿来判定。两者必须分开，见
`SolverPrecheck.LowerBound`。

## 7. 想继续做，从这里开始

1. **先跑一遍现状**，确认基线：
   ```bat
   set CI=1
   重构报告\verify.bat
   ```
   末行必须是 `VERDICT=OK` 且 `QUALITY-OK`。

2. **跑基准看数据**：
   ```bat
   dotnet run --project test/SolverBench\SolverBench.csproj -c Release
   ```
   末行 `BENCH-OK`；出现 `UNSOUND` 就说明判据错杀了。

3. **要对拍就换实现**：
   `new FeasibilityChecker(new StateSpaceSolver())` 是旧算法，
   `new FeasibilityChecker()` 是新算法，两者在同一份代码里共存。

4. **要动搜索就记住三条红线**：
   - `undetermined` 必须保持 0（不能靠多报未判定降时间）
   - 不能把"未判定"当"不可行"（会破坏「判定不可行 ⇒ 执行必失败」）
   - 改完 `REPLAY-OK` 的四个字节数必须原样
