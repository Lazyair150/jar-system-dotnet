# 第 3 步：世界信息总线

## 一、问题

原系统里有三条**互不相通**的线：

| 线 | 现状 | 后果 |
|---|---|---|
| 进程 → 表现层 | `ProcessSystem.Observer` 单播，只接一个宿主 | 除了宿主，没人知道过程走到哪了 |
| 世界 → 日志 | `JarSystem.Record()` 只写 `_commandLog`，**只记不触发** | 世界变了，但没有任何模块被通知 |
| 业务模块之间 | 直接方法调用，模块 A 不知道 B 改了世界 | `OrderService.CheckAllFeasibility()` 只能靠 5 秒一次的定时全量重扫；换台改了 capability 但旧可行性结果没有失效标记 |

用户要求的形态是"**一个操作引发一系列世界变化**"——即总线不仅广播，还允许订阅方触发后续变化。

## 二、关键发现：这个落点本来就有

`ProcessSystem` 里早就有一个从没有人实现过的接口：

```csharp
// src/JarSystem.Core/Rules/IWorldEventSource.cs
public interface IWorldEventSource
{
    IReadOnlyList<WorldEvent> DrainForTick(int tick);
}
```

以及管线第 ① 步：

```csharp
// src/JarSystem.Core/Process/ProcessSystem.cs
internal void DrainEvents()
{
    var source = EventSource;
    if (source == null) return;
    foreach (var e in source.DrainForTick(_clock.Tick))
        e.Effect?.Invoke();
}
```

注释原文：「事件就会在每个 tick 的**过程推进之前**被执行。null（默认）= 空操作，行为与今天一致」。

**级联的确定性落点已经存在，只是没有实现者。** 于是总线不需要新开一条通往世界的路径——它住进这个已经存在的通道即可。

## 三、设计

### 3.1 总线同时扮演两个角色

```
src/JarSystem.Core/World/
├── WorldSignal.cs     信号（值类型、不可变、必带 tick + revision）
├── IWorldObserver.cs  观察者 / 反应器 / 效果出口
└── WorldBus.cs        总线本体，实现 IWorldEventSource + IWorldEffectSink
```

- **广播口**：`Publish(WorldSignal)` 同步分发给所有观察者（**按注册顺序**，不并发）。
- **事件源**：实现 `IWorldEventSource`，于是反应器请求的效果由管线在下一个 tick 的第 ① 步统一执行。

### 3.2 两个发布点覆盖全部三线

| 发布点 | 覆盖什么 | 为什么选这里 |
|---|---|---|
| `JarSystem.Record()` | **全部意图级世界变更** | 它是全类唯一的写入口（`JarSystem.cs:259` 注释原文「唯一的写入口：本类所有"改世界"的意图方法都调它」）。一处发布即全覆盖，不可能漏。 |
| `ProcessSystem.SignalSink` | 过程状态五态 | 与既有 `Observer` 槽位**并存**，不替换——宿主的观察者与内核的总线各接各线。 |

`SignalSink` 是新增的可选出口（null 时行为与今天逐字节相同）。选"两个出口"而不是"换掉 `Observer`"，是因为 `Observer` 是 Web 宿主的既有槽位（`Web/ProcessObserver.cs` 把它翻成 5 条对外消息），换掉会静默改宿主行为。

### 3.3 级联为什么跨 tick（这一步的全部难点）

同一 tick 内同步递归级联的问题是**"收敛"变成运行时性质**：两个反应器互相触发就会挂住，而这个挂住又依赖执行顺序 ⇒ 回放不可复现。

改成「这一 tick 排的队，下一 tick 收的果」之后：

| 性质 | 怎么保证的 |
|---|---|
| **可复现** | 顺序完全由队列决定，与墙钟、线程、哈希序无关 |
| **有界** | `MaxEffectsPerTick = 256`、`MaxSignalsPerDispatch = 1024`，超限拒收并计数，不抛异常 |
| **可审计** | 每条效果带名字与说明，过程日志与信号流能对上 |

`DrainForTick` 刻意实现为**先取走再清空**：效果执行期间新排进来的条目落在下一批，不会被本轮顺手吃掉 ⇒ 级联严格"一 tick 一跳"。

### 3.4 为什么默认什么都不做

没有订阅者、没有反应器时，`Publish` 只做一次循环判定，`DrainForTick` 恒返回空表。

这不是巧合，是**设计要求**：回放资产是本项目最硬的约束（`CONSTRAINTS.md` I2），总线不能因为"存在"就改变世界的走向。这一条有机器化检验，见下。

## 四、契约测试（`test/JarSystem.Tests/WorldBusTests.cs`，8 个）

| 测试 | 守的是什么 |
|---|---|
| `Publish_ReachesObserversInRegistrationOrder` | 顺序即语义，不能并发化 |
| `Signal_CarriesTickAndRevision` | 没有这两个字段，订阅方无法在回放里复现决策 |
| `ReactorEffects_AreDeferredAndTakenExactlyOnce` | 请求了效果但**还没执行**；取走即清空 |
| `EffectQueue_IsBoundedAndReportsRejection` | 级联必须死在明处，不能无限增长 |
| `ResetPending_DropsEffectsButKeepsSubscribers` | 旧世界的闭包不得伸进新世界 |
| `JarSystem_PublishesWorldChangedForEveryIntent` | `Record()` 一处发布覆盖全部意图 |
| `JarSystem_PublishesProcessChangedForOrderLifecycle` | 过程线已汇入 |
| **`Subscribers_DoNotChangeWorldOutcome`** | **最重要的一条**：两个种子/ID 源/命令序列完全相同的系统，一个挂订阅者+反应器、一个不挂，状态快照与修订号必须逐字相同 |

写第八条时抓到一个真的坑：`FeasibilityResultData.Timestamp` 是**墙钟耗时**（毫秒字符串），逐次不同。测试里必须把它抹成 `<volatile>` 再比对——否则测的是性能抖动，不是确定性。这正是 `CONSTRAINTS.md` 里"回放门须把 timestamp 当 volatile"那条的具体形态。

## 六、这一步没做什么

- **没有写任何具体的反应器**。总线是机制，不是玩法。哪个模块该在什么信号上做什么，属于世界内容（`设计分析_世界内核与成长框架.md` 的 L1/L2），不该由这一步替他决定。
- **没有替换宿主的 `Observer` 槽位**。表现层仍然走原来的线，同时也接到了总线。要不要在将来砍掉旧槽位，取决于宿主是否愿意改成订阅模式——那是宿主的决定。
- **没有让级联参与同一 tick**。理由见 3.3，这是刻意的取舍，不是没做完。

# 后续三件（按顺序）

## 一、第一个真实反应器：可行性缓存失效

`src/JarSystem.Core/World/FeasibilityInvalidationReactor.cs`

**它修的是一个真 bug**：`Order.FeasibilityResult` 是缓存，而 `ExecuteOrder` 会照着它的
`SolverPath` 执行（`OrderService.cs:167-168`）。这份缓存不记录"算于哪一版工作台"，
于是「先算可行性 → 换台 → 再执行」会**照着一份旧世界算出来的计划去动新世界**。

两个设计要点，都不是推测得来的：

1. **清空而不是重算。** 重算是把秒级判定塞进 tick 管线，一个 tick 花多久取决于世界上有多少张订单。
   清空是常数时间，语义也更诚实：旧结论**已经错了**，不是"过时但可用"。
2. **按引用清，而不是整片清。** 这是它第一版被自己的测试打回的地方：
   失效排到下一个 tick 才执行，而这中间世界可能又变了 ——
   最典型是「换台（排队失效）→ 同一 tick 里用户重新判定（写入新结论）→ tick 到了」。
   无差别清空会连**刚刚算出的、完全正确的新结论**一起抹掉。
   所以入队时记下每份结论的**对象引用**，执行时只清"还是当初那一个"的，
   中间重算过的引用已经换了，自然跳过。

配套：`Order.ClearFeasibility()`（新增）。

## 二、把两套出口收成一个，并当场抓到一处漏接

原本的打算是「让 Web 层不再设置 `Observer`，统一走总线」。**核完事实后否掉了**：
`IProcessObserver.OnChanged` 拿到的是**活的** `ProcessInstance`，Web 壳要从它身上读 10 个字段
（Id / Kind / Subject / DeclaredSteps / DeadlineTick / AppliedSteps / BlockedReason /
GraceTicks / Outcome / FailureReason）。而 `WorldSignal` 是值类型，只带
(Kind, Op, Subject, SubjectId, Tick, Revision)。改走总线就得按 SubjectId 回去查实例，
而 `ProcessRun.Close` 的顺序是「先 notify Finished（`ProcessRun.cs:163`）再进最近表
（`ProcessSystem.cs:266`）」—— 查得到查不到取决于恰好站在哪一刻。
**那是把一条信息完整的通路换成一条靠时序碰运气的通路。**

所以改成了守"线路不丢"，并写了一条测试钉住它：
`test/JarSystem.Tests/ProcessLineParityTests.cs` —— 过程状态变化的每一个事件，
必须同时到达宿主槽位与总线，且 reason + tick 一致。

**这条测试第一次跑就失败了**，差在总线少了 `progressed`。
根因：`ProcessSystem.AdvanceUnit`（`:217`）里直接调了 `Observer?.OnChanged(...)`，
绕过了 `Begin` 传入的 `notify` 回调 —— 于是在我接上 `SignalSink` 的那一刻，
两套出口就已经开始各自独立、互不一致。

修法：新增私有 `Notify(instance, reason, tick)` 作为**过程状态变化的唯一出口**，
`AdvanceUnit` 与 `begin` 的 lambda 全部走它。类注释里写明：新增任何过程状态变化只能走这里。

## 三、`MatchingSolver` 的结论：正确、但不是净收益

上一轮我说它"有缺陷"，**这个说法是过期的**。当前实测：

```
直接解出 452 / 回退 63 / 未判定 0 / 结论不一致 0 / 健全性违反 0
总耗时 83 ms（相对裸实现 24.10×）
```

但 composite 口径下「前置检查 + 精确」只要 11 ms —— 分配形**更慢**。
原因是 900 个场景里绝大多数本来就不贵，分配搜索白付一次再回退。

本轮加了标准 CSP 前向检查（每条剩余需求必须还有未用的候选罐子），收益很小（85→83 ms）。
剩余的回退 47 例集中在 `capacity` 类，是「分配成功但 `BuildPath` 的液体调度拿不准」，
要修得重做取液调度，性价比不高。

**结论：它应当作为第三套可替换实现保留，不做默认。** 默认仍是「前置检查 + 精确」。
