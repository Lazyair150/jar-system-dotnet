# 统一时间系统：tick 作为逻辑时间轴

## 0 一句话

这套系统不用帧循环当时间轴，它用 **tick**：世界不是"每帧重算"，而是"每次推进走一步"。
统一时间系统就是把"几点了、在不在走"收成一个可查询、可断言、可观察的入口，并守住"只增"与"冻结即不存在"两条不变式。

## 1 为什么需要它

大部分实时游戏按固定帧率更新（60fps），世界每帧重算一遍。这套系统的更新频率低得多、且以逻辑为主，
因此用 tick 替代帧：**一次 tick 就是一次完整的世界步进**。

这带来两个能力，也带来一笔债：

| 能力 | 债 |
|---|---|
| 判定与墙钟无关 ⇒ 回放可逐字节复现 | 时间概念散落在四处，没有一处代表"世界时间"本身 |
| 步进可以显式驱动 ⇒ 宿主能停、能手动推 | 世界不知道自己"停了" ⇒ 依赖时间的逻辑无法区分"没到点"与"世界停了" |

四处时间概念（改造前）：

| 时间概念 | 存在位置 | 谁读它 |
|---|---|---|
| 当前 tick | `Process/Scheduler/LogicalClock.cs:19` `public int Tick { get; private set; }` | 过程 / 日志 / 修饰器 |
| 产出节拍（定点累加） | `Production/ProducerModule.cs` 的 `_accumulatedMilli` | 只有产线自己 |
| 过程的时间字段 | `ProcessInstance.DeadlineTick` / `GraceTicks` / `NextUnitTick` | 过程系统 |
| 规则时效区间 | `ModifierStack` 的 tick 区间 | 规则层 |

心跳本身已有固定顺序（`Process/Scheduler/TickPipeline.cs:5-14` 的类注释）：

```
一个 tick（全程在同一串行闸门内）：
  0 逻辑时钟 +1               ← 本 tick 编号（过程步记的就是它）
  ① 事件注入                   ← 世界事件（事故 / 任命 / 禁令生效）
  ② 修饰器更新                 ← 区间生效/失效 + 冲突解析
  ③ 过程推进（每过程至多一步）
  ④ 世界产出                   ← ProducerModule，紧随本调用
```

顺序写死的理由（原文）：「只要允许事件与过程推进在同一 tick 内次序不定，回放就会出现两种结果」。

**它只有"走"，没有"停"。** 补的就是这个。

## 2 结构

```
LogicalClock（tick 的唯一权威，只增）
      ▲ Advance()（唯一入口，只由 TickPipeline 调用）
      │
TickPipeline.AdvanceOneTick()   ← 0 时钟 ①事件 ②修饰器 ③过程
      │
JarSystem.Tick(count)           ← ④产出（TickStep）+ FlushFlow + Record
      │
      └─ WorldTime.OnAdvanced() ← 时间状态：NotStarted → Running
```

新增 `src/JarSystem.Core/World/WorldTime.cs`：

```csharp
public enum WorldTimeState { NotStarted, Running, Paused }

public sealed class WorldTime
{
    public int Tick => _clock.Tick;              // 委托时钟，不自己存
    public WorldTimeState State { get; private set; }
    public bool IsFlowing => State == Running;
    public int FrozenAtTick { get; private set; }
    public int ElapsedSince(int tick);           // 拒绝负数与未来
}
```

**它不推进时钟。** 推进口仍然只有 `LogicalClock.Advance()`，`WorldTime` 只在推进后被通知。
这样"时间"与"时间门面"不会变成两份状态。

## 3 两条不变式

### 不变式 1：tick 只增

因此"某 tick 距今多久"恒非负，`ElapsedSince` 对负数与未来直接抛 `ArgumentOutOfRangeException`。
`Reset()`（世界重建）把时间退回 `NotStarted` 并让时钟归零 —— 那是"世界重建"，不是"时间倒流"的特例。

### 不变式 2：冻结即不存在

`JarSystem.PauseTime()` 之后：

- 时钟不动（`Tick` 不执行 `AdvanceOneTick`）；
- 产出不动（不执行 `TickStep`）；
- **命令日志不增长**（不执行 `Record`）。

第三条是**回放安全**的全部依据：冻结期间日志里没有 `tick` 条目，于是同一份命令日志在"停过"和"没停过"的两个世界里产生同一个世界。
实测门禁 `REPLAY-OK (commands=33, stateBytes=3125, logBytes=8797, journalBytes=725)` 逐字节未变。

副作用（是好处）：过程宽限期、订单截止、修饰器时效全部按 tick 计，
**暂停期间它们天然不流失** —— 不需要任何补偿逻辑，而"补偿"恰恰就是被禁止的"补算"。

## 4 与"宿主不调用 Tick"的区别

两者都让世界停住，但只有前者让**世界自己知道**自己停了：

| | 宿主不调用 `Tick` | `PauseTime()` |
|---|---|---|
| 时钟 | 不增 | 不增 |
| 世界知道吗 | **不知道** | 知道（`IsTimePaused` / `TimePaused` 信号） |
| 订阅方能否区分 | 不能 | 能 |
| 回放 | 一致 | 一致（日志无条目） |

"多久推进一次"仍然属于宿主（`TickIntervalMs = 2000`）；
"时间在不在走"从此属于世界。两者职责不重叠。

## 5 可观察

`WorldSignalKind` 新增两值：

```csharp
TimePaused,    // 时间被冻住
TimeResumed    // 时间恢复流动
```

二者**幂等**：重复暂停/重复恢复返回 `false` 且不重复发信号。

## 6 顺带修掉的一个日志污染

`Tick(int count)` 原先对负数没有任何校验：`for (int i = 0; i < count; i++)` 循环不执行，
但末尾仍 `Record(WorldOps.Tick, intA: count)` —— 一条 `intA = -1` 的命令被写进命令日志，凭空污染回放源。

现在 `count < 0` 直接抛 `ArgumentOutOfRangeException`，且**在写日志之前**抛。

## 8 长时运行的稳定性盘点

"随时间流逝依然正常运行"要问的是**有没有随 tick 无界增长的东西**。本轮盘点了全部容器：

| 容器 | 位置 | 有界吗 |
|---|---|---|
| 事件历史 | `JarSystem.cs:113-115` | ✅ `MaxEventHistory` 截断 |
| 最近终结的过程 | `ProcessSystem.cs:286-287` | ✅ `RecentCapacity` |
| 过程日志 | `ProcessJournal.cs:22` | ✅ `DefaultCapacity = 4096` |
| 仓库罐/液 | `Production/Warehouse.cs` | ✅ 200/200，溢出计数不回收 |
| 可行性缓存 | `OrderService` | ✅ 按订单数，且按内容指纹判失效 |
| 总线效果队列 | `WorldBus` | ✅ `MaxEffectsPerTick = 256` 拒绝并计数 |
| **命令日志** | `JarSystem.cs:54` | ⚠️ **刻意无界** |

命令日志是回放源（`CommandLog` → `SessionReplay`），截断它就等于截断回放。**这是有意的选择，不是遗漏**：
一个会话的完整历史就是它存在的理由。长跑场景的应对是"按会话切分"，不是"给当前会话设上限"。

## 9 刻意没做的

1. **没有给 `WorldTime` 加墙钟字段**（真实经过多少毫秒）。那是宿主的事，进核心就会破"判定与墙钟无关"。
2. **没有做"暂停时冻结产线累加器"**。产线的定点累加只在 `TickStep` 里动，冻结时 `TickStep` 根本不跑 —— 无需额外处理。
3. **没有把 `FlushFlow` 移进 tick 循环**。它现在是"每次宿主 Tick 调用一次"的批量语义，
   移进去会改变 `Tick(10)` 与 `Tick(1)×10` 的等价关系，那是重基线而不是修 bug。
   这条**语义含糊**已记录在此，作为待决项。
