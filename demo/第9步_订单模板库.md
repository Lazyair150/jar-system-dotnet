# 第 9 步：订单模板库

## 0. 这一步补的是一个**概念空缺**，不是一个功能

改前系统里有两个东西：

- **订单实例** `Order`：带 Id、状态、类型、需求、可行性结论。创建入口只有两个 —— 调用方直接给需求列表（`CreateOrder`），或者现掷骰子（`CreateRandomOrder`）。
- **世界配置** `WorldOptions`：描述工作台、产线、流入参数、初始库存、名字池。

中间那一层是空的：**"这个世界可以派哪些订单"没有落点**。它不在配置里，不在 `config/world.json` 里，只能活在调用方代码里（demo 里那张 `ORDER_POOL` 就是被迫长在代码里的那一层）。

所以这一步不是"加一个模板类"，而是把**内容（L1）**与**运行时对象**分开：

| | 是什么 | 可变性 | 归属 |
|---|---|---|---|
| `OrderTemplate` | 一张订单的**形状**（名字 + 类型 + 需求） | 不可变 | 内容 |
| `Order` | 一次真实的**派单**（Id/状态/可行性） | 可变，有生命周期 | 运行时对象 |

## 1. 分层位置与一个必须解释的取舍

```
Config (L0)   RequirementOptions / OrderTemplateOptions / WorldOptions.OrderTemplates   ← 纯数据
Orders (L7)   OrderTemplate / OrderTemplateLibrary                                       ← 校验 + 实例化
Services (L9) OrderService.CreateOrderFromTemplate / CreateOrderFromTemplate(门面)       ← 派单
```

**校验为什么放在 Orders 层而不是 Config 层**：`OrderTemplate` 要产出 `Requirement`（`Abstractions`，L2），失败要抛 `DomainValidationException`（`Domain`，L1）。Config 是 **L0 地板层**，它引用 L1/L2 会直接破层序（`ArchitectureTests` 会红）。所以 Config 只描述形状（`RequirementOptions.Shape/Liquid`），转换与校验在 Orders 层做。

这个取舍的收益是：**配置写错在装配时当场报出可读原因**，而不是等第一次派单才炸。

校验清单（`OrderTemplateLibrary.FromOptions`）：名字非空 / 名字不重复 / 类型只能是 `A` 或 `B` / 至少一条需求 / 不超过 `Constants.MAX_ORDER_REQUIREMENTS`（10）/ 形状必须在词表里 / 液体若给定也必须在词表里。全部抛 `DomainValidationException` 且消息带模板名与第几条需求。

## 2. 三个入口

**① 配置**（`config/world.json`，与内置默认世界逐值一致）

```json
"orderTemplates": [
  { "name": "空双罐",   "type": "A", "requirements": [{ "shape": "圆罐" }, { "shape": "方罐" }] },
  { "name": "灌酒圆罐", "type": "A", "requirements": [{ "shape": "圆罐" }, { "shape": "圆罐", "liquid": "酒" }] },
  { "name": "三角改形", "type": "A", "requirements": [{ "shape": "方罐" }, { "shape": "三角罐" }] },
  { "name": "主从高长", "type": "B", "requirements": [{ "shape": "高罐" }, { "shape": "长罐", "liquid": "蜜" }] },
  { "name": "三件套",   "type": "B", "requirements": [{ "shape": "鼓罐", "liquid": "酒" }, { "shape": "尖罐" }, { "shape": "扁罐" }] }
]
```

内置世界用 `WorldOptions.CreateDefault()` 里的同一份清单（顺序 = 索引 = "牌库"顺序）。

**② 库**（`JarSystem.OrderTemplates`）

`Count` / `IsEmpty` / `Templates` / `Names` / `Get(index)` / `TryGet(name, out)`（容忍首尾空白）/ `IndexOf(name)` / `Instantiate()`。
库是**值不是可变注册表**：构造后不变，可安全地被多个世界共享。空配置返回共享的 `OrderTemplateLibrary.Empty` 单例。

**③ 派单**

```csharp
sys.CreateOrderFromTemplate("主从高长");   // (bool Success, string? Error)
```

名字不存在返回 `(false, "没有这个订单模板: X")`，**不抛异常**（名字来自外部输入是常态），也不留下半张订单。

## 3. 刻意没做的事：没动 `CreateRandomOrder`

把随机派单改成"优先从模板抽"是很自然的下一步，但那会让 `CreateRandomOrder` 的行为**绑定到"这个世界有没有模板"**，而它是回放与随机场景生成的既有入口，改它属于重基线不是修 bug。要那件事请单独立项。

同理，模板**不自动参与**任何自动派单流程 —— 现有世界的行为在加了模板库之后没有任何变化（`REPLAY-OK` 与契约快照逐字未变即为证据）。

## 4. 一个新机制第一次被用到：行为审批基线

`test/JarSystem.Tests/PropertyAndSnapshotTests.DefaultWorldOptionsIsStable` 有一份 `Approvals/DefaultWorldOptions.approved.json`：把 `WorldOptions.Default` 序列化后与基线逐字比对，不一致就失败并生成 `received.json`，由人确认后覆盖 —— 这是审批测试（approval testing）的标准形态。

改内置世界必须走这一步。本次的 diff 是**纯新增**：

```
117a118,193     ← 只有插入，没有一行修改或删除
138 行 → 214 行 （+76 行 = 5 张模板的 JSON）
```

确认"新增的就是那 76 行 `orderTemplates`、其余逐字不变"之后才 `cp received approved`。这与第 8 步处理契约基线的口径一致：**移动基线要能指出移动的正好是哪几行**。

## 5. 新测试（`test/JarSystem.Tests/OrderTemplateTests.cs`，7 条）

| 测试 | 守什么 |
|---|---|
| `BuiltInWorldExposesTheConfiguredTemplatesInOrder` | 内置世界的模板清单、顺序、类型、逐值需求 |
| `InstantiationGivesIndependentRequirementLists` | 模板不可变 + 每次实例化给新列表（改一张单不影响模板或另一张） |
| `CreateOrderFromTemplateMakesARealOrder` | 派出的订单是真的 `Order`：类型、需求、`PENDING` 状态 |
| `UnknownTemplateNameFailsWithAReadableReasonAndAddsNothing` | 未知名字返回原因且**不留下半张订单** |
| `BadTemplateConfigIsRejectedAtBuildTime` | 7 类坏配置各自抛 `DomainValidationException` 且消息可读 |
| `EmptyConfigGivesTheSharedEmptyLibrary` | 空配置返回共享空库；`Get` 越界抛 `ArgumentOutOfRangeException` |
| `NameLookupTrimsWhitespace` | 名字查找容忍首尾空白，库里存修整后的名字 |

一条实现细节：`Requirement` 的属性是 **init-only**（构造后不可改），所以"模板被改脏"只能发生在列表这一层。测试因此用**替换列表元素**来制造污染 —— 这恰好也是模板必须每次 `Instantiate` 出新列表的理由。
