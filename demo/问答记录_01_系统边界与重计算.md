# 问答记录 01：系统边界与重计算

日期：本轮对话
参与者：用户 / 助手
涉及：陶罐系统（`D:\codex\jar-system-dotnet`）能否支撑"可成长的构筑类卡牌游戏"

---

## 问一（用户）

> 你说原版"多个竞争订单之间怎么分配罐子"是原系统中自动检验模块中唯一的重计算吗？而判断当前资源能不能支持某一个卡打出则是更轻的部分。那为什么会需要那个重计算，原版是为什么？并且这真的在系统运行的过程中的自动监测中会执行吗？那岂不是很重吗？

### 答

#### 1. 先纠正一句话

我上一轮说"重的是 `PartitionSearch`（多个竞争订单之间怎么分配）"——**不准确**。

`src/JarSystem.Core/Orders/FeasibilityChecker.cs:36-41` 显示可行性检查是条链：

```csharp
_checks = new IFeasibilityCheck[]
{
    new SinglePhaseCheck(),   // A 类：仅主台单阶段求解
    new SlaveOnlyCheck(),     // B 类快速路径：仅用从台自身资源
    new PartitionCheck(...)   // B 类兜底：需求子集划分搜索
};
```

真正的重计算核心是 **`StateSpaceSolver`**，不是 `PartitionSearch`。三个检查**每一个**都在调它：

- `Orders/Feasibility/FeasibilityChecks.cs:33`（A 类）
  `ctx.Solver.Solve(ctx.Requirements, ctx.MasterInfo, jars, liquids)`
- `Orders/Feasibility/FeasibilityChecks.cs:65`（B 类快速路径）
  `ctx.Solver.Solve(ctx.Requirements, ctx.SlaveInfo, ...)`
- `Orders/Feasibility/FeasibilityChecks.cs:92` → `PartitionSearch.cs:108`
  **在 2^N 的 mask 循环里，每个 mask 调两次**（主台一次 + 从台一次）

所以 `PartitionSearch` 不是"另一种重计算"，它是**重计算的乘数**：把一份需求切成 2^N 份，每份各解一次。

`Orders/Feasibility/PartitionSearch.cs:92-94` 的注释自己承认了：

> B 类不可行订单要对全部 2^N 个划分各做一次主台+从台求解，而最贵的正是"主台拿到很多需求"的那些 mask

另外我上次把 `JarMatcher.MatchAll` 说成"你要的轻活"——**也错了**。它在全仓只有 4 处调用（`Order.cs:96`、`OrderEvent.cs:187`、`PartitionSearch.cs:148`、`JarMatcher.cs:28` 定义），**全部是"终态校验"**（桌上这些罐子是不是刚好凑得出这些需求），不是可行性判定。

#### 2. 为什么原版需要这个重计算

因为**原版替你做了操作**。

玩家点"执行订单"，系统要做的是：从当前罐子/液体的状态出发，**找出一条操作序列**（倒液、改形、转移、交付）把需求满足掉，然后执行它。

这是**规划问题**，不是匹配问题。状态空间 = 罐子 × 形状 × 液体 × 操作标记，要搜。所以必须 `StateSpaceSolver`。

而 `JarMatcher.MatchAll` 只能回答"这些罐子**现在**凑不凑得出需求"，回答不了"我这么倒、这么改、这么转，**能不能**凑得出"。后者才是原版要的。

用户想要的"自动检查条件并高亮可释放的攻击卡"，要复用的正是这个模块。它不是负担，是**用户想要的东西本身**。

#### 3. 它真的在自动监测里跑吗？重不重？

跑了。而且确实重。

`src/JarSystem.Web/AutoCheckBackgroundService.cs:11`：

```csharp
public static readonly TimeSpan Interval = TimeSpan.FromSeconds(5);
```

`:27` 闸门：`if (!_svc.System.AutoCheckEnabled) continue;`

`src/JarSystem.Core/Services/OrderService.cs:94-108` 的 `CheckAllFeasibility()` 是**全量**的：

```csharp
for (int i = 0; i < _system.Orders.Count; i++)
    if (_system.Orders[i].Status == Constants.OrderStatus.PENDING)
        results.Add(new AutoCheckResultDto { Index = i, OrderId = ..., Result = CheckFeasibility(i) });
```

不只定时器：`src/JarSystem.Web/CommandDispatcher.cs:67` 和 `:73`，**特定命令之后只要开关开着就再全量跑一遍**。

单次代价：`Orders/FeasibilityChecker.cs:26` 注释 `StateSpaceSolver.DefaultNodeBudget`「**实测约 2 秒上限**」。

最坏情况 ≈ **待执行 B 类订单数 × 2 秒，每 5 秒一次**。

系统知道这件事，所以有三道闸：

1. **节点预算**（400k 节点）+ `IWorkBudgetedSolver` 接口
2. **三态结论**——预算耗尽返回 `Undetermined = true`，**不是"不可行"**。
   `FeasibilityChecks.cs:41-50` 与 `:103-113` 都写明：预算耗尽绝不能解释成不可行，否则会打穿"判定不可行 ⇒ 执行必失败"这条承重墙。为此专门补了确定性反例 S22（把 NodeBudget 压到 1）。
3. **单调性剪枝**（`PartitionSearch.cs:86-95`，2026-09 加）：子集在主台不可行 ⇒ 所有超集跳过。

**默认是关的**：`src/JarSystem.Core/JarSystem.cs:142`
`public bool AutoCheckEnabled { get; private set; } = false;`

一句话：**重是重，但它是可开关的、有预算的、有降级路径的。原版已经承认并处理过了。**

## 问二（用户）

> 原系统确定是没有回馈点，正反馈，是一种感觉，是越来越大、越快、越强、越轻松，然而我在玩 demo 的过程中，只体会到了烦躁，慢，无聊，没有目的，击败敌人也没有热情，我只想看到更多的更快的绿色可用提示出现，但是即使点击后也依然没有任何喜悦，就像一个漫长的工作，是我忽略或者掉入什么陷阱了吗？难道期待更多的可用绿色高亮提示的反馈是错误的？
>
> 过去我是把释放订单的点击当作自己的交互，而忘记了订单的实现是有一个巨大前提，而玩家的操作就是在前面，而不是这里，即前面的资源生产和工作台的配置升级才是努力的部分，订单实现才是奖赏，而努力提高它们实际上不需要与订单实现系统作抗争，而是可以是世界中的别的比如敌人，攻击它们，或者进入一个凶险的地区获取特定的生产卡，努力的方向或许并不是引导玩家过分在意原系统，而成长就是旅途中获取的道具，数值提升，奖励表现为能够使用的高级订单攻击卡越来越多且不会卡手。

### 答

#### 1. 订单完成是纯消耗（源码证实）

三处，都在成功路径上：

**`src/JarSystem.Core/Orders/OrderEvent.cs:185-203`** `Deliver()` 成功后做的全部事：

```
deliveryWorkshop.RemoveJar(jar)   // 把交付罐从场上拿走
RollbackSlaveToMaster()           // B 类才走
Master.ClearMarks(); Slave.ClearMarks();   // 清操作标记
Status = SUCCESS
```

**`src/JarSystem.Core/Orders/Order.cs:86`**：

```csharp
public void MarkSucceeded() { Status = Constants.OrderStatus.SUCCESS; }
```

函数体只有这一行。

**`src/JarSystem.Core/Services/OrderService.cs:201-211`** 成功后只记一条事件元数据（订单号、主从台、成败、时间戳、操作数），然后 `return`。

没有 `AddJar`，没有 `AddLiquid`，没有 `ProduceLiquid`。**一个订单完成，除了"完成"这个字，什么都没发生。**

而产出侧 `src/JarSystem.Core/Production/ProducerModule.cs` 是按 tick 的固定速率，与订单无关——不管这回合完成 3 个订单还是 0 个，产线速度不变。

整个系统是：**一台恒定速率的泵，接着一个有底的桶，订单按需从桶里取。** 唯一的变量是"你能不能把资源摆成订单要的样子"。**没有反馈回路。**

#### 2. 缺回馈不是缺陷，是这个品类成立的条件

给固定预算解谜加复利会发生什么：复利 = 本回合收益取决于上回合状态 ⇒ 领先者更领先。而解谜的张力来自**每局给定的固定约束**。两者互斥——一旦滚雪球，难局就不再是"这道题难"，而是"你前三回合没打好"。题目本身消失了。

原系统刻意把可变项全放在**配置**而非**成长**上：产线速率、工作台 BaseMarks/AdditionalMarks/Ban、罐位 6 与液池 5 或 4。可以在开局前把它们调成一套匹配订单需求的组合，但**局内这套组合是死的**。这是"校准"，不是"经营"。

`设计分析_世界内核与成长框架.md:34-38` 的分层里 L3 叫「玩家匠人（成长）」——但那明确指的是**局与局之间**的积累，不是单局内的复利。

#### 3. 如果要成长，唯一自洽的放法是局外

单局内归零，改变的是下一局的**起始配置**：解锁新的工作台、新的产线卡、新的订单族。

对比杀戮尖塔：它单局内有复利，但用「敌人同步变强 + 单局有限」来抵消。而陶罐系统的订单难度是**封顶的**（需求数上限 10，节点预算 40 万）。如果能力能复利，后期就没有题可做了。所以局内复利在这套规则下不只是不好玩，是**结构上装不下**。

#### 4. 关于"陷阱"

**用户没有掉进陷阱，而是踩到了这个系统的真实边界，并且自己把它描述对了。**

##### 用户说对的部分

> 过去我是把释放订单的点击当作自己的交互，而忘记了订单的实现是有一个巨大前提，而玩家的操作就是在前面

完全正确。这是一个**建筑/生产线类**游戏的骨架（Factorio、Opus Magnum、Shapez）：交付动作应该无摩擦，努力全在**配置**。

> 成长就是旅途中获取的道具，数值提升

方向对：成长必须来自系统外的世界，因为系统内没有回路。

##### 会自毁的部分

> 奖励表现为能够使用的高级订单攻击卡越来越多且不会卡手

**这句话如果靠"数值提升"实现，绿色高亮会自己消灭自己。**

玩 demo 时烦躁的根源是**卡手**——手里的卡打不出。之所以打不出，是因为资源不够/形状不对。

而如果成长 = "产线更快 / 攻击更强 / 资源更多"，那么越成长，越多的卡变成绿色，然后**没有卡会再变成红色**。到那一刻，绿色高亮不再是奖励，而是**默认状态**——不再需要看它，因为它永远是绿的。

想要的"越来越多绿色"，它的终点是"全是绿色"，而全绿的时候这个游戏就结束了。这不是数值平衡问题，是结构问题：**确定性引擎里，"变强"这个动作的本质是"减少需要做的决策"。**

##### 那成长应该是什么

**改变约束，而不是提高数值。**

- 解锁一台新工作台 → 换掉 `BaseMarks`/`AdditionalMarks`/`Ban` → **换掉题目的形状**
- 解锁一种新的产线卡 → 换掉"我能造什么"
- 解锁新的订单族（新需求组合） → **换掉题目本身**
- 罐位 6→8、液池 5→6 → 换掉容量约束

这些让"更多高级订单能用"的原因是**多了一个解题维度**，不是**分数更高了**。前者是新的可能性，后者是旧的答案。Opus Magnum 的重玩价值就是这个：不是角色变强，是能用更少操作解同一道题。

##### 关于"敌人"

如果敌人是**打你**的（压血量、逼赶时间），就退回到"确定性引擎 + 时间压力 = 作业"的坑。

敌人更适合做成 **PvE 的题目发生器**——它产出新的、更难的、有主题的订单。它不反抗你，它**出题**。打赢它 = 能解出它出的题。

#### 5. 这个游戏到底卖什么

诚实版：**它卖"调对"的那一下。**

这是 Opus Magnum / SpaceChem / Human Resource Machine 那一类。共同特征：短、一次性、靠关卡设计而非数值成长，重玩价值来自"更优解"而不是"更强的我"。

想要的"漫长旅途 + 不断变强"，和这一类是**两个不同的东西**。硬塞在一起，会得到"用强角色做简单题"——题太简单所以不刺激，打得太顺所以没成就感。

**但这不是死路。** 用户的方案其实是：**造一个新游戏，把陶罐系统当零件装进去。** 这完全做得了，只是要承认主体变了。

## 三条路（供选择）

| 方案 | 内容 | 成本 | 特点 |
|---|---|---|---|
| **A** | 承认它是解谜游戏，把它做对：战前配置 → 开跑 → 自动吃订单。拿掉 step、手动操作、血条，保留暗箱三态提示（可承/不明/不可承） | 约半天 | 最诚实，最快验证"是否真的喜欢这个引擎" |
| **B** | Opus Magnum 式"最优解"游戏：在 A 上加"本局用了多少操作/多少液体"的评分与历史最佳。奖励从"变强"换成"更省" | 约一天 | 最接近"让我想再玩一局" |
| **C** | 造外层世界，陶罐系统降级为战斗系统：战前配置 → 进入区域 → 遇到"敌人"（一个订单族）→ 吃掉它的需求来打它 → 赢了掉落新的工作台/产线卡/订单族。成长 = 工具箱变大 | 约三到五天，需持续拍板设计 | 最接近用户描述的愿景，但已不是"改造陶罐系统"，是"用陶罐系统做一个新游戏" |

**用户的裁决：A + C。**
