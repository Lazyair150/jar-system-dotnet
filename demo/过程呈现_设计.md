# 过程呈现：为什么"过程"是这款游戏的本体

> 触发：用户指出「我知道我为什么设计了过程系统吗，因为那是必须的展示……我需要的是它的过程被展现」。
> 这篇是把那句话展开成本轮要实现的东西，以及**从它推导出的、他没说但必然要的**那些。

---

## 1. 需求的本体（一句话）

**瞬间给出结果，等于把游戏变成报表。** 规则不是靠文字说明教会的，是靠玩家「看着世界动」学会的：

- 罐子从产线出来 → 进仓库 → 每回合只有 3 只流进主台（**这就是为什么罐位会挤**）；
- 一只罐子被灌注时，池子里少一份液体（**这就是为什么空罐改形要付液体**）；
- B 类订单的罐子必须**从主台移动到从台**才交付（**这就是 B 类的承重点**）；
- 换台要停两回合、期间不产出（**这就是为什么"换台"是一个决策而不是一个开关**）。

这些"为什么"只能被**看见**，不能被"告诉我"。内核里为此建了 `Process/`：
`ProcessInstance`（过程有时间、有状态、有 deadline）、`JournalEntry`（每一步都留痕）、
`TickPipeline` 的阶段表（事件 → 修饰器 → 过程 → 产出 → 流入）。
**过程系统不是为了"能跑"，是为了"能看"。**

## 2. 从这句话推导出的表现清单（六层）

| 层 | 要表现的东西 | 玩家由此学到的规则 | 本轮状态 |
|---|---|---|---|
| L1 物质流 | 产线产出 → 仓库 →（每回合 3 罐 / 每种液 2）→ 主台；溢出丢弃 | 仓库是缓冲、流入有上限、丢弃会计数 | ✅ 帧级：罐子逐只从仓库飞进主台（`flow` 搬一只发一条） |
| L2 操作流 | 同一回合内对每只罐子的操作：照用 / 灌注 / 倒出 / 改形（耗液体）/ 满罐改形（吃掉罐内液体） | 一罐一操作；改形有成本；满罐改形会损失液体 | ✅ 帧级：被操作的罐子在棋盘上高亮，形状/液体按帧变化 |
| L3 订单流 | 订单被尝试 → 铺路（部分完成）→ 完成 → **罐子飞向交付台** → 结束回流 | B 类交付在从台；失败不回滚已发生的操作 | ✅ 帧级：交付那一刻罐子从台面板飞向订单面板 |
| L4 配置流 | 换台迁徙（重组旧台 → 转移 → 落定，占 2 回合）；罐子主从转移 | 换台有代价；转移是物流动作 | ✅ 帧级：转移时罐子在两块台面板之间飞；迁徙期顶部有倒计时 |
| L5 排序流 | 一回合里**谁先执行**：订单顺序、同订单内满罐优先 / match 优先 | 排序会改变结果（谁先拿走罐子/液体） | ⬜ 引擎已按"满罐优先 + 订单顺序"执行，但**玩家还不能调整顺序**，UI 也没显示"为什么是这个顺序" |
| L6 时间流 | 节拍、可暂停 / 单步 / 调速 / 回看上一回合 | 时间是玩家的观察工具，不是惩罚 | 🟡 播放/暂停/单步/速度/跳过已有；**还没有跨回合回看** |

## 3. 本轮已落地（Stage 1）

**事件流是表现层的唯一契约。** 引擎在 `demo/puzzle_engine.js` 里 `emit(G, ev)`，
每回合一条完整时间线（`G.events` 每回合清空）：

```
turnStart → produce×n → flow×n → flowLiquid → orderTry#1 → op#1×n → deliver#1×n → orderTry#2 → …
```

事件种类：`turnStart / produce / flow / flowLiquid / orderTry / op / orderBlocked / deliver /
backflow / transfer / migrateReshape / migrateDone`。

UI 侧（`demo/puzzle_ui.js` 的「过程」面板）只做三件事：**按顺序念、显示进度、允许暂停/单步/调速**。
底部「推进一回合」在播放期间禁用，显示 `过程中…（3/12）`。

**两条纪律（防止"规则写第二遍"从 UI 侧长回来）**：

1. **UI 不推导任何东西**。它只把事件翻译成中文（`describe()`），
   一旦在里面写「如果……那就……」，规则就有了第二份实现 —— 这正是历史上出过三次 bug 的形状。
2. **顺序本身要被断言**。`_test_engine.js` 的「过程事件流」抽查断言：
   首条必须是 `turnStart`；`flow` 必须早于任何 `orderTry`；`deliver` 必须晚于同订单的 `orderTry`；
   同一条订单交付之后不许再有它的 `op`；A 类交付台必须是主台、B 类必须是从台。
   （写这条断言时它先红了一次，查出来是**我的断言**把"不同订单之间交替"误判成乱序 —— 断言写错也要能定位。）

## 3.5 Stage 2：中间态快照（棋盘按帧渲染）

Stage 1 的棋盘画的是回合**终态**，过程只在右栏用文字推进。Stage 2 让棋盘也进入时间：**每个事件附一张
"那一刻的世界"快照**（`ev.snap`），播放时 UI 直接渲染第 i 张，**不插值、不补算**。

快照的形状（刻意很窄）：

```js
{ master: { id, jars:[{uid,shape,liquid}], liquid },
  sub:    { id, jars:[...], liquid } | null,
  wh:     { jars:{形状:只数}, liquid:{液体:份数}, discardedJars },
  migrating: { side, to, turns } | null }
```

`def` 只存 **id**，渲染时再解析 —— 快照不复制规则表，否则规则又多一份副本。

**罐子身份**：`newJar()` 给每只罐子一个进程内唯一 `uid`，**只给表现层用**（动画要认出"同一只"）。
它不参与任何判定：规则只看形状与液体，所以 uid 不影响打手成绩、不影响规则对拍（实测八脚本全绿）。

**四条被断言的性质**（`_test_engine.js` 的「中间态快照」抽查）：

1. 每个事件都有 `snap`（缺帧 ⇒ 播放时会画出一个不存在世界）；
2. 流入是**搬一只发一条**，相邻两帧的主台只差一只（攒到最后一起发，每帧就会同时出现三只罐 ——
   那不是过程，那是结果）；
3. 交付那一帧里，这只罐子已经不在台上（否则动画会画出"交付了还在"）；
4. `uid` 跨台不变（转移是搬同一个对象，不是销毁再新建）。

**一条新纪律**：播放期间禁止在棋盘上点任何操作。因为棋盘画的是**快照副本**，
在副本上点"转移/换台"会改到真实世界 —— 屏幕上看到的和改到的不是一个东西。

## 4. 还没做（按价值排序）

1. **订单执行顺序可控**：让玩家拖订单列表决定先后，并在事件里带上 `order` 与"为什么这个订单先"。
   这会立刻产生新的策略维度（先做哪个订单会改变罐子归属）。
2. **回合历史回看**：保留最近 N 回合的事件流，可倒回去看"上回合的哪一步决定了结果"
   （快照已经存在，回看只是把 `pb.queue` 换成"第 k 回合的队列"）。
3. **战斗模式共用同一事件流**：现在战斗模式的反馈还是一句话"锁死/通过"，应该同源。
4. **换台迁徙的完整表现**：`migrateReshape` 现在是两条文字事件，缺"旧台罐子被改形、液体被灌进空罐带走"
   的逐只可见过程（快照里已经有 `migrating` 字段，缺的是让它自己走几帧）。

## 5. 与内核的对应（别在 demo 里造第二套）

| demo | 内核 |
|---|---|
| `G.events` 事件流 | `Process/Journal` 的 `JournalEntry` + `World/WorldSignal` |
| 播放/暂停/单步 | 宿主的 `TickIntervalMs`（表现层时间参数，不进判定） |
| 事件顺序 | `TickPipeline` 的阶段表（事件 → 修饰器 → 过程 → 产出 → 流入） |
| `orderTry` → `deliver` | `ProcessInstance` 的生命周期（Running → Succeeded）与 `OrderEvent.Deliver` |
| `migrateReshape/Done` | `WorkshopSwitchEvent` 的 `Begin → RunReshape → RunTransfer` |

**一条硬边界**：demo 的播放节奏可以随便调，但**不能改变世界** ——
`_test_engine.js` 的 `事件流抽查` 与 `_plan_levels.js` 的打手成绩都只依赖引擎，不依赖播放速度。
