# 过程呈现：为什么"过程"是这款游戏的本体

> 触发：用户指出「我知道我为什么设计了过程系统吗，因为那是必须的展示……我需要的是它的过程被展现」。
> 这篇是把那句话展开成本轮要实现的东西，以及**从它推导出的、他没说但必然要的**那些。

---

## 1. 需求的本体（一句话）

**瞬间给出结果，等于把游戏变成报表。** 规则不是靠文字说明教会的，是靠玩家「看着世界动」学会的：

- 罐子从产线出来 → 进仓库 → 每回合只有 3 只流进主台（**这就是为什么罐位会挤**）；
- 一只罐子被灌注时，池子里少一份液体（**这就是为什么空罐改形要付液体**）；
- B 类订单的罐子必须**从主台移动到从台**才交付（**这就是 B 类的承重点**）；
- 换台要停两回合、期间不产出（**这就是为什么"换台"是一个决策而不是一个开关**）。

这些"为什么"只能被**看见**，不能被"告诉我"。内核里为此建了 `Process/`：
`ProcessInstance`（过程有时间、有状态、有 deadline）、`JournalEntry`（每一步都留痕）、
`TickPipeline` 的阶段表（事件 → 修饰器 → 过程 → 产出 → 流入）。
**过程系统不是为了"能跑"，是为了"能看"。**

## 2. 从这句话推导出的表现清单（六层）

| 层 | 要表现的东西 | 玩家由此学到的规则 | 本轮状态 |
|---|---|---|---|
| L1 物质流 | 产线产出 → 仓库 →（每回合 3 罐 / 每种液 2）→ 主台；溢出丢弃 | 仓库是缓冲、流入有上限、丢弃会计数 | ✅ 帧级：罐子逐只从仓库飞进主台（`flow` 搬一只发一条） |
| L2 操作流 | 同一回合内对每只罐子的操作：照用 / 灌注 / 倒出 / 改形（耗液体）/ 满罐改形（吃掉罐内液体） | 一罐一操作；改形有成本；满罐改形会损失液体 | ✅ 帧级：被操作的罐子在棋盘上高亮，形状/液体按帧变化 |
| L3 订单流 | 订单被尝试 → 铺路（部分完成）→ 完成 → **罐子飞向交付台** → 结束回流 | B 类交付在从台；失败不回滚已发生的操作 | ✅ 帧级：交付那一刻罐子从台面板飞向订单面板 |
| L4 配置流 | 换台迁徙（重组旧台 → 转移 → 落定，占 2 回合）；罐子主从转移 | 换台有代价；转移是物流动作 | ✅ 帧级：转移时罐子在两块台面板之间飞；迁徙期顶部有倒计时 |
| L5 排序流 | 一回合里**谁先执行**：订单顺序、同订单内满罐优先 / match 优先 | 排序会改变结果（谁先拿走罐子/液体） | 🟡 机制已接通：`↑/↓` 改 `G.orders` 数组顺序（执行顺序=数组顺序，`od.idx` 是身份），`orderTry` 带 `rank`。**但实测 3,576 种产线组合里换顺序从不改变结果** ⇒ 缺的是会抢同一批资源的订单（关卡缺口，不是代码缺口） |
| L6 时间流 | 节拍、可暂停 / 单步 / 调速 / 回看上一回合 | 时间是玩家的观察工具，不是惩罚 | 🟡 播放/暂停/单步/速度/跳过已有；**还没有跨回合回看** |

## 3. 本轮已落地（Stage 1）

**事件流是表现层的唯一契约。** 引擎在 `demo/puzzle_engine.js` 里 `emit(G, ev)`，
每回合一条完整时间线（`G.events` 每回合清空）：

```
turnStart → produce×n → flow×n → flowLiquid → orderTry#1 → op#1×n → deliver#1×n → orderTry#2 → …
```

事件种类：`turnStart / produce / flow / flowLiquid / orderTry / op / orderBlocked / deliver /
backflow / transfer / migrateReshape / migrateDone`。

UI 侧（`demo/puzzle_ui.js` 的「过程」面板）只做三件事：**按顺序念、显示进度、允许暂停/单步/调速**。
底部「推进一回合」在播放期间禁用，显示 `过程中…（3/12）`。

**两条纪律（防止"规则写第二遍"从 UI 侧长回来）**：

1. **UI 不推导任何东西**。它只把事件翻译成中文（`describe()`），
   一旦在里面写「如果……那就……」，规则就有了第二份实现 —— 这正是历史上出过三次 bug 的形状。
2. **顺序本身要被断言**。`_test_engine.js` 的「过程事件流」抽查断言：
   首条必须是 `turnStart`；`flow` 必须早于任何 `orderTry`；`deliver` 必须晚于同订单的 `orderTry`；
   同一条订单交付之后不许再有它的 `op`；A 类交付台必须是主台、B 类必须是从台。
   （写这条断言时它先红了一次，查出来是**我的断言**把"不同订单之间交替"误判成乱序 —— 断言写错也要能定位。）

## 3.5 Stage 2：中间态快照（棋盘按帧渲染）

Stage 1 的棋盘画的是回合**终态**，过程只在右栏用文字推进。Stage 2 让棋盘也进入时间：**每个事件附一张
"那一刻的世界"快照**（`ev.snap`），播放时 UI 直接渲染第 i 张，**不插值、不补算**。

快照的形状（刻意很窄）：

```js
{ master: { id, jars:[{uid,shape,liquid}], liquid },
  sub:    { id, jars:[...], liquid } | null,
  wh:     { jars:{形状:只数}, liquid:{液体:份数}, discardedJars },
  migrating: { side, to, turns } | null }
```

`def` 只存 **id**，渲染时再解析 —— 快照不复制规则表，否则规则又多一份副本。

**罐子身份**：`newJar()` 给每只罐子一个进程内唯一 `uid`，**只给表现层用**（动画要认出"同一只"）。
它不参与任何判定：规则只看形状与液体，所以 uid 不影响打手成绩、不影响规则对拍（实测八脚本全绿）。

**四条被断言的性质**（`_test_engine.js` 的「中间态快照」抽查）：

1. 每个事件都有 `snap`（缺帧 ⇒ 播放时会画出一个不存在世界）；
2. 流入是**搬一只发一条**，相邻两帧的主台只差一只（攒到最后一起发，每帧就会同时出现三只罐 ——
   那不是过程，那是结果）；
3. 交付那一帧里，这只罐子已经不在台上（否则动画会画出"交付了还在"）；
4. `uid` 跨台不变（转移是搬同一个对象，不是销毁再新建）。

**一条新纪律**：播放期间禁止在棋盘上点任何操作。因为棋盘画的是**快照副本**，
在副本上点"转移/换台"会改到真实世界 —— 屏幕上看到的和改到的不是一个东西。

## 3.6 Stage 3：订单执行顺序（接通了，但还没有用处）

执行顺序 = `G.orders` 的数组顺序（`od.idx` 是身份，不随排序变），`ENG.moveOrder(G, i, dir)` 交换相邻两项，
`orderTry` 事件带 `rank`。UI 每张订单卡右上角有 `顺序 N` 与 `↑ / ↓`。

`_test_engine.js` 的「订单执行顺序」抽查断言：引擎确实按数组顺序执行（每回合的第一条 `orderTry` 必须是
"第一个未完成的订单"，`rank` 与实际位置一致）、越界移动被拒、排序跨回合保持。

**必须记住的实测结论**：我把五关的产线组合按 identity 级别扫了一遍 ——
**3,576 种组合，换执行顺序从不改变完成集合（0 处差异）**。
原因是现有关卡里两条订单从不真正抢同一批罐子：先执行的订单要么能完成（完成后它拿走的罐子本来也没别人要），
要么完成不了（而完成不了的计划不消耗罐子，只白白用掉液体）。

⇒ 这个旋钮现在是**接通了但还没有用处**。缺的不是代码，是**会抢同一批罐子/液体的订单**：
例如两条订单都要"长罐:酒"，或某关液体极度稀缺（1 回合只进 1 份而两条订单都要用）。
设计出这种订单之后，机制已经就位，不需要再改引擎。

## 3.7 Stage 4：跨回合回看（历史帧）

**要解决的事**：一回合放完就没了。玩家看到"第 5 回合订单没成"，但说不清是哪一步把罐子用掉了 ——
因为上一回合的过程已经不在屏幕上了。

**引擎侧**（`demo/puzzle_engine.js`）：

| 东西 | 形态 | 为什么这样 |
|---|---|---|
| `G.history` | `[{ turn, events }]`，只留最近 **8** 回合 | 每帧都带一份世界快照（`worldSnap`），不设上限长局会一直涨 |
| `archiveEvents(G)` | 只在**回合边界**调用 | 归档的是"已经说完的一段"，不是"正在说的那段" |
| 进行中的那一回合 | 就是 `G.events` 本身，**不进** history | 存两份等于同一段时间有两个真相，回看和实时迟早讲出不同的故事 |
| 游戏结束 | 收官那一回合也归档 | 它是玩家最想复盘的一段 |

**这里有一个顺序 bug，值得单独记下来**：`archiveEvents` 与 `G.events = []` 必须放在 `runTurnRaw` 的**最前面**，
不能放在迁徙分支（`if (G.migrating) { … return; }`）之后。放在之后的话，迁徙那两个事件（`migrateReshape`/`migrateDone`）
会被追加进**已经归档**的上一回合数组里 —— 于是"历史"跟着现在的回合一起变，而屏幕上不会有任何异样。
这条分支在加入 history 之前不会暴露，因为那时没有东西会记住旧数组。

**UI 侧**（`demo/puzzle_ui.js`）：`pb.review` 是回看游标（`null` = 实时）。回看只是把 `pb.queue` 换成
`G.history[k].events` 再走指针，**不重算任何东西**。面板多一排「回看：第 N 回合」按钮；回看态下按钮换成
「◀ 上一条 / 下一条 ▶ / 返回实时」，推进键被禁用并提示原因（棋盘画的是快照副本，推进等于在副本上按真实世界的键）。

**断言（都会变红的那种）**：

- `_test_engine.js`「跨回合回看」抽查 5 条：只有已结束回合进历史；归档后再推进历史**逐字节不变**；
  上限 8 且回合号连续（丢最旧的，不丢中间的）；迁徙回合的事件落在本回合；**一条历史只能属于一个回合**
  （对每条历史段断言 `events.every(e => e.turn === seg.turn)`）。
- 最后那条是这次唯一抓得住 bug 的断言：我先前只查"历史里有没有 `migrateDone`"，而把归档放回迁徙分支之后，
  那段混合体**后来仍会被整体归档**，`migrateDone` 照样"在历史里" —— 断言看不见污染。
  改成查 `turn` 一致性后，反例立刻报 `历史第 1 回合里混入了别的回合的 2 条事件（3:migrateReshape,3:migrateDone）`。
- `_smoke_ui.js` 四条：面板里有回看按钮；点进去进入回看态；第一帧继续往前必须停住；回看中点推进**不许改动世界**；
  返回实时后退出回看态。

**顺带修掉的一个陈旧画面**：换关/重开时没有清舞台状态，`currentFrame()` 会继续返回**上一局**的快照 ——
棋盘画的是旧世界，且不报任何错。现在 `resetStage()` 在 `restart`/`prevlv`/`nextlv` 里调用。

## 3.8 Stage 5：帧信封与拉模型（把 demo 对齐到内核的帧流契约）

内核在 `src/JarSystem.Core/Presentation/` 有正式的帧流：`PresentationFrame(seq, kind, op, subject, subjectId, tick, revision)`
与 `PresentationFeed`（`FirstSeq` / `DroppedFrames` / `Since(cursor)` 拉模型 / 满则成批丢最旧一半）。
demo 之前只有"这一回合的事件数组"：没有全局序号、没有世界修订号、没有窗口账目、没有拉取 API。
这四样恰好就是审计里点出的四条缺口，所以这一轮把它们补齐 —— **形状照抄内核，不另发明**。

| 补上的 | demo 里的落点 | 内核对应 | 为什么必须 |
|---|---|---|---|
| 全局序号 `seq` | `emit()` 里 `ev.seq = ++G.feed.seq` | `PresentationFrame.Seq` | 每回合从 1 重数的话，"第几条"在不同回合不可比，回看与拉取都失去游标 |
| 逻辑时间 `tick` | `ev.tick = G.turn` | `PresentationFrame.Tick` | 表现层永远按 tick 排序，而不是按"数组里第几个" |
| 世界修订号 `revision` | 只被 `WORLD_KINDS` 推进 | `PresentationFrame.Revision` | 若"只描述意图"的帧也推进修订号，则"修订号变了"不再等于"世界变了"，缓存失效会跟着一起坏 |
| 窗口账目 | `frameWindow(G)` → `{firstSeq, lastSeq, dropped}` | `PresentationFeed.FirstSeq/DroppedFrames` | 丢了就要**记账**，恒等式 `firstSeq == dropped + 1`（与内核同一口径） |
| 拉模型 | `framesSince(G, cursor)`、`framesOfTurn(G, turn)` | `PresentationFeed.Since(int afterSeq)` | 节奏归消费方：同一份帧流可以 62ms 播一遍，也可以被测试一次读空 |

`WORLD_KINDS = { produce, flow, flowLiquid, op, deliver, transfer, backflow, migrateReshape, migrateDone }` ——
`turnStart` / `orderTry` / `orderBlocked` 只描述意图，不算世界变化。

**两处踩到的坑（都写成了断言）**
1. 收官回合会被归档，而 `G.events` 仍指向**同一批帧** ⇒ `framesSince` 把这一回合读了两遍（帧数 12，末序号才 9）。
   修法是记 `feed.archivedSeq`，拉取时跳过 `seq <= archivedSeq` 的实时帧。断言：序号连续（读重了立刻不连续）。
2. 不是所有"世界"都由 `newGame` 建：`battle_engine.js` 与 `_check_flow.js` 的夹具自己搭 G
   ⇒ `emit` 撞上 `G.feed === undefined`。修法不是加防御性兜底（那会把"半个世界"变成静默），
   而是抽出 `ENG.newFeed()`，三处世界构造都显式带信封，并让 `emit` 在缺信封时**当场报错**。

**负向验证**：把 `ev.seq` 改成 `G.events.length + 1`（每回合从 1 重数）⇒ `帧信封抽查 FAIL 3 处`，还原后 OK。

**UI 也换成拉模型**：`openReview(k)` 走 `framesOfTurn`、`liveFrames()` 走 `framesOfTurn(G, evs[0].tick)`，
不再直接切 `G.history[k].events` 数组。这一层现在只是"换了个调用点"，但等 demo 真的接上 .NET 内核的
`PresentationFeed`，要改的是实现，不是调用点 —— 这就是先按契约写消费方的价值。
过程面板同时显示 `帧 #seq · tick N · rev M`：玩家不需要懂，但"过程是一串带编号的帧"必须看得见。

## 4. 还没做（按价值排序）

1. **设计"抢资源"的订单让顺序真正有意义**（机制已在，缺关卡）：让玩家拖订单列表决定先后，并在事件里带上 `order` 与"为什么这个订单先"。
   这会立刻产生新的策略维度（先做哪个订单会改变罐子归属）。
2. ~~**回合历史回看**~~ —— 已完成，见 §3.7（`G.history` + `pb.review`）。
3. **战斗模式共用同一事件流**：现在战斗模式的反馈还是一句话"锁死/通过"，应该同源。
   （帧信封已经先铺过去了 —— `battle_engine.js` 的 `newBattle` 现在也带 `feed: ENG.newFeed()`，
   缺的是把战斗的过程也 emit 出来。）
4. **换台迁徙的完整表现**：`migrateReshape` 现在是两条文字事件，缺"旧台罐子被改形、液体被灌进空罐带走"
   的逐只可见过程（快照里已经有 `migrating` 字段，缺的是让它自己走几帧）。

## 5. 与内核的对应（别在 demo 里造第二套）

| demo | 内核 |
|---|---|
| `G.events` 事件流 | `Process/Journal` 的 `JournalEntry` + `World/WorldSignal` |
| `G.feed` 的 `seq/tick/revision`、`framesSince`、`frameWindow` | `Presentation/PresentationFrame` + `PresentationFeed`（`Since` / `FirstSeq` / `DroppedFrames`） |
| 播放/暂停/单步 | 宿主的 `TickIntervalMs`（表现层时间参数，不进判定） |
| 事件顺序 | `TickPipeline` 的阶段表（事件 → 修饰器 → 过程 → 产出 → 流入） |
| `orderTry` → `deliver` | `ProcessInstance` 的生命周期（Running → Succeeded）与 `OrderEvent.Deliver` |
| `migrateReshape/Done` | `WorkshopSwitchEvent` 的 `Begin → RunReshape → RunTransfer` |

**一条硬边界**：demo 的播放节奏可以随便调，但**不能改变世界** ——
`_test_engine.js` 的 `事件流抽查` 与 `_plan_levels.js` 的打手成绩都只依赖引擎，不依赖播放速度。
