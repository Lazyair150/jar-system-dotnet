# 第 6 步：依赖分层（按概念拆解，再把关系钉死）

## 0. 起点

审计实测：`src/JarSystem.Core` 有 **7 组双向依赖环**。

```
Domain        ↔ Abstractions
Domain        ↔ Rules
Domain        ↔ Services
Orders        ↔ Abstractions
Orders        ↔ Solver
Orders        ↔ Services
Solver        ↔ Abstractions
```

单工程内互相 `using` 编译得过，所以没有任何东西会报警——环只会在"想单独复用一层""想知道这次改动会影响谁"的时候以维护成本的形式显现。

## 1. 方法：概念拆解，不是搬文件

判别标准只有一句：**一处依赖之所以别扭，是因为有一个概念没有被独立出来。**

从这条推下去，发现 7 个环其实只有 **6 个概念** 放错了位置，且每一个都是"本该属于 A 层的东西被写在了 B 层"：

| 别扭的依赖 | 没独立出来的概念 | 归位 |
|---|---|---|
| `Domain → Services`（一行 `DefaultIdGenerators.Jars`） | **身份**（Id 从哪来）是领域概念，不是"服务" | `Domain/Identity.cs` |
| `Abstractions ↔ Orders`/`↔ Solver` | **求解器的输入输出词汇**（`Requirement`/`JarState`/`WorkshopInfo`/`SolverResult`/`SolverStep`/`SolverOperation`）被写在两个实现层里 | `Abstractions/SolverContracts.cs` |
| `Orders ↔ Solver` | **"谁来选求解器实现"** 是装配问题，不是分析器的问题（无参构造里 `new PrecheckedStateSpaceSolver()`） | 删掉无参构造，装配交回组合根 |
| `Abstractions → Domain` | **罐子→求解器词汇的映射**是实体的职责，不是词汇的职责（`JarState.From(Jar)`） | `Orders/Feasibility/JarStateMapper.cs` |
| `Commands ↔ Orders` | **命令的记账口**只是"写一笔"，不需要认识"订单执行"这个更大的概念（三个命令文件每个签名都写着 `OrderEvent? event_`） | `Abstractions/CommandJournal.cs`（`LogError` + `ICommandJournal`，实测只用三个成员） |
| `Abstractions → Orders`（`IProcessStepPrimitives`） | 这个契约的**词汇全是订单执行概念**，放在抽象层等于让抽象层认识实现层 | `Orders/IProcessStepPrimitives.cs` |
| `Domain ↔ Rules` | **工作台"当前生效的法则"（含修饰器栈）是工作台状态**，而"法则如何被驱动/从哪来"才是规则策略 | `ModifierStack`/`RuleContext`/修饰器类型 → `Domain`；`ModifierAwareSolver`/`WorldQuery`/`Scenario*` 留在 `Rules` |
| `Domain → Abstractions`（`IIntensitySource`） | **强度折算出口**是修饰器栈的对外读数，消费方是 `Production`/`Services` | `Domain/IIntensitySource.cs` |
| `Commands → Services` | 默认日志实现属于契约层，不属于服务层 | `Abstractions/ConsoleSystemLog.cs` |

有几处**没有**按"搬文件"处理，而是**删掉概念**：

- `Orders/Order.cs` 对 `Services` 的 `using` 只在注释里被提到 ⇒ 直接删（`CONSTRAINTS.md:56` 的口径：改结构要删分支/概念，不是搬位置）。
- `FeasibilityChecker` 的无参构造删掉——它不是被搬到别处，是**这一类不再拥有那个决定权**。

## 3. 更牢固的结构：可执行的层序

零环**是一次手术的结果，不是结构**——下一个人再加一个 `using` 就能把环悄悄装回去。

所以顺序写成一张表，由测试守着：`test/JarSystem.Tests/ArchitectureTests.cs`。

| 层 | 排位 |
|---|---|
| Config | 0 |
| Domain | 1 |
| Abstractions | 2 |
| Rules | 3 |
| Production | 4 |
| Solver | 5 |
| Commands | 6 |
| Orders | 7 |
| Process | 8 |
| Services | 9 |
| Sessions | 10 |
| Executor | 11 |
| World | 12 |
| Bootstrap | 13 |

规则只有一句：**一个命名空间只许引用排位比它低的命名空间。**

顺序不是审美，是被真实依赖推出来的，例如：
- `Commands` 必须排在 `Orders` 之前——`Orders/OrderEvent` 要驱动 `CommandExecutor`；
- `Services` 排在 `Process` 之后——`ProductionService` 要跑 `Process` 的管线。

两条测试：
- `CoreLayersOnlyDependDownward`：扫全部 `.cs`，报出**文件:行号 + 双方排位 + 违反了哪一格**。
- `EveryNamespaceIsRanked`：新增命名空间必须登记层号；已删的层必须从表里删掉（防止表格腐烂）。

**已做的反向验证**（一个不能失败的测试等于没有测试）：往 `Config/Constants.cs` 顶部插一行 `using JarSystem.Core.Bootstrap;`，测试立即报

```
Constants.cs:1  `Config`(L0) 引用了 `Bootstrap`(L13) —— 只许向下，不许同层或向上
```

## 5. 两个会咬人的坑（都踩过）

1. **`重构报告/quality-gate.ps1` 的 `$coreSources` 循环不做 `Test-Path` 过滤**（`:61-66` 直接对 `git ls-files --cached` 的结果 `ReadAllText`）。删掉一个 `.cs` 却不 `git add -A -- <路径>`，质量门就抛 `FileNotFoundException` ⇒ `QUALITY-GATE-FAILED`，而中文异常在 GBK 输出里会被吞掉，只看到 `VERDICT=FAIL`。读 `重构报告/_quality_output.txt` 要 `iconv -f GBK -t UTF-8`。
2. **`hosts/godot/Jar` 不在 `JarSystem.slnx`**，由 `verify.bat` 第 1b 步单独编译。搬类型后漏改那里会 `STEP-FAILED step1-godot`，而 `dotnet build JarSystem.slnx` 是绿的——只看 slnx 会误判通过。
