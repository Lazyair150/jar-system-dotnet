## 1. 设计裁决：把"条件"从端口升级为**受校验的结构化查询**

用户提出的方向：**既然系统本身是严谨规则的，新条框与约束应当建立在一个"有规则、可复现、可扩展"的结构上**。

**结论：赞同，而且这个项目已经拥有那份结构** —— 契约里的规范状态（`StateDto` + `state.schema.json` +
逐字节快照 + `worldRevision`）：键名钉死（严谨）、同世界同版本必同值（可复现）、只加不改（可扩展）。

于是把上一轮那个"每种条件加一个端口方法"的 `IWorldQuery` 重构为**两层**：

| 层 | 名字 | 职责 |
|---|---|---|
| **事实层** | `Rules/IWorldFacts`（6 个取值：工作台罐子/液体、仓库罐子/液体、累计丢弃罐子/液体） | 如实报数，只读、不抛异常、取不到报 0 |
| **查询层** | `Rules/WorldQuery`（**受校验的词汇表**：`what` × `shape/liquid/empty` × `op` × `value`） | 把"条件"变成**数据**；加载时校验、运行时只读求值、失败时给世界语言的原因 |

为什么不做"任意路径 + 自由表达式"：那需要一个解析器与求值器 —— 正是本项目明确拒绝的
"规则引擎式过度设计"；这里的扩展方式是**加词汇**（例：将来要查"从台"已由 `workshop: slave` 覆盖；
要查"订单数"就是给 `what` 加一个取值），不是加重语言。

## 2. 场景编辑器（界面 + 三个后端端点）

| 端点 | 语义 |
|---|---|
| `GET /api/scenario` | 返回当前 `config/scenario.json`（若存在）与仓库里的示例 |
| `POST /api/scenario/validate` | 逐字校验提交的文本（走核心 `Validate()`），返回 `{valid, errors, warnings}` |
| `POST /api/scenario` | **先校验、通过才落盘**到仓库根的 `config/scenario.json`；IO 失败如实回报（不 500） |

三个端点都做了来源校验（与 `/api/state` 同一判据），只在本机回环壳里可用；保存路径**固定**（不接受任意路径）。
前端加了一个"🧪 场景"弹窗：文本域 + 载入示例 / 校验 / 保存，结果区直接显示逐条错误。

### 冒烟实测（真实缺陷修掉后）

第一轮冒烟暴露**两个真实缺陷**：

1. **路径解析错了**：端点用相对当前目录的路径，而 `dotnet run` 的当前目录是 `src\JarSystem.Web`
   ⇒ `GET /api/scenario` 返回空示例。修法：复用世界配置那套**向上查找**（把 `ResolveConfigPath` 改 internal）。
2. **返回元组被序列化成 `{}`**：`System.Text.Json` 不序列化 `ValueTuple` 的字段 ⇒ 校验结果全空。
   修法：改回匿名对象（并把这条教训写进注释）。

第二轮冒烟又抓到第三个：**保存目标在首次保存前并不存在**，而 `ResolveConfigPath` 只找"已存在"的文件
⇒ 它退回了服务的当前目录并抛 `DirectoryNotFoundException`（500）。修法：新增 `ResolveConfigDir()`
（以必然存在的世界配置为锚点）+ 写文件包 try/catch。

最终实测：

```
GET  /api/scenario            → {"exists":false,"source":"","sample":"{…}"}          # 向上查找生效
POST /api/scenario/validate   → {"valid":true,"errors":[],"warnings":[]}             # 合法示例
POST /api/scenario/validate   → {"valid":false,"errors":["events(x)：未知 kind \"nope\"（数据侧支持：suppress / retime / intensity / grant / require）"]}
POST /api/scenario            → {"saved":true,"path":"D:\\codex\\jar-system-dotnet\\config\\scenario.json", …}
重启后启动日志               → [scenario] loaded: …（事件 3 个，初始修饰器 1 条）
```

最后一行是**端到端证据**：编辑 → 保存 → 重启 → 世界确实带上了场景。
（冒烟产物 `config/scenario.json` 已删除，仓库回到"没有生效场景"的状态 ⇒ 默认行为不变。）

## 3. 校验入门（保持九步形状）

`--validate-scenario` 作为**第 7 步的子检查**接入（而不是加第 10 步）：

```bat
dotnet run --project test\JarSystem.Test -c Release -- --validate-scenario config\scenario.sample.json >> "%LOG%" 2>&1
if errorlevel 1 echo SCENARIO-GATE-FAILED >> "%LOG%"
```

`SCENARIO-GATE-FAILED` 已进 VERDICT 列表（⇒ 校验失败会让门变红），`SCENARIO-` 也进 KEY LINES（⇒ 结论可见）。

## 5. 遗留

1. **`IWorldFacts` 的口径**：目前"工作台"支持 `master` / `slave` / 名字；仓库与丢弃计数是全局的。
   若将来要表达"某个具体工作台的丢弃量"这类条款，`what` 加取值即可（词汇表扩展）。
2. **编辑器的保存不热重载**：保存后需重启服务（与 `world.json` 同一约定）；要热重载需在设计上回答
   "运行中的世界怎么换规则"——属玩法决策。
3. **场景的自动施放**：目前"初始修饰器"由宿主作用域持有；若要做"临时场景"（不重启切换），
   需要一个"换场景"的意图（会进世界命令日志 ⇒ 可回放）。
