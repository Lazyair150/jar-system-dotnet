## 1. 三项边界重构（已实现）

### A1 `Rules` 独立成层（修掉 `Domain → Process` 的错层）

`RuleContext` / `IRuleModifier` / `ModifierStack` / `ModifierAwareSolver` 从 `Process/Rules/`
移到 **`src/JarSystem.Core/Rules/`**（命名空间 `JarSystem.Core.Rules`）—— 世界规则不再是过程基础设施。

依赖方向现在是这样（两侧单向）：

```
Domain ──▶ Rules ◀── Process ──▶ Abstractions
                ▲
        Services（投影/收尾实现）
```

顺带清掉一处**陈旧 using**：`Workshop.cs` 里还留着 P3b 时代的 `using JarSystem.Core.Process;`
（当时 `ModifierStack` 还在那边）⇒ 它会让"Domain → Process"这条反向依赖在**静态检查里假阳性**，
已删除。

### A2 打破 `Process ↔ Services`

在 `Process/Ports/` 新增 `IOrderExecutionCompletion`（`Complete(OrderExecutionSession)`），
由 `OrderService` 显式实现（转发到既有的 `CompleteOrderExecution`）。
过程系统从此**不认识 `Services`**，而 Services 侧继续单向使用 Process（投影与收尾实现）。

### A3 打破 `Process ↔ Executor`

在 `Abstractions/` 新增 `IProcessStepPrimitives`（`ApplyPlannedStep` / `RunGreedyStage`），
由 `OrderExecutor` 实现、会话持有接口。返回形状刻意**中性**（不出现 Executor 内部类型
`WorkshopStageResult`），因此宿主也能自己实现它（录制/回放替身）。
**与项目先例一致**：`ISolver` 当初就是这样把"可行性 ↔ 求解器"解开的。

### 反向依赖自检（可复现的证据）

```powershell
rg -c "using JarSystem\.Core\.Process" src\JarSystem.Core\Rules  -g "*.cs"   # 空
rg -c "using JarSystem\.Core\.Process" src\JarSystem.Core\Domain -g "*.cs"   # 空
rg -c "using JarSystem\.Core\.Services" src\JarSystem.Core\Process -g "*.cs" # 空
rg -c "using JarSystem\.Core\.Executor" src\JarSystem.Core\Process -g "*.cs" # 空
```

四项全空 ⇒ `Process` 的对外依赖收敛为 `Abstractions` + 内核数据（Config/Domain/Orders/Solver），
`Domain` 不再依赖过程系统。

## 2. 阶段推进：`Intensity` 的第二个消费者（生产者速率）

为了不引入 `Production → Rules` 这条新依赖，先抽了一个薄抽象
`Abstractions/IIntensitySource`（`int Apply(string target, int value)`），由 `ModifierStack` 实现
（无匹配修饰器 ⇒ **恒等**，全程整数 ⇒ 确定性）。

消费点：`ShapeProductionLine.Tick()` 对本线每 tick 的总速率做折算，目标名 `producer:形状`；
`ProducerModule` 与门面在**构造与 Reset 复位**两处注入同一个栈。
于是现在有两类强度目标可用：`liquid:酒`（每 tick 液体产出）与 `producer:圆罐`（某形状生产者速率）。

S27 顺带扩了断言（**不新增用例** ⇒ 不用再同步 9 个载体）：同一段里再跑一个"圆罐生产者归零"的系统，
断言对照组有圆罐、停摆组一个都没有。

> 写这条断言时踩到一个细节：**仓库会向主台流入（3 罐/次）**，罐子可能已经在主台上了 ⇒
> 统计必须"仓库 + 全部工作台"两处都算，只看仓库会得到假阴性。已写进用例注释。

## 3. 本轮刻意未做（附理由）

| 项 | 为什么不做 |
|---|---|
| A9 `ProcessSchedule` 值对象（把 `TicksPerStep`/`NextUnitTick`/`BlockedAtTick` 收成一个不可变值 + 纯函数 `Advance`） | 收益是"调度变成纯函数、可单测"，但目前只有**一个**使用者（管线），属"为将来抽象"；等出现第二个使用者（例：存档/回放要重算排程）再做 |
| A10 拆分会话的"阶段机状态"与"结果" | 它是 **P5（存档）的前置**，而现在没有任何"执行中订单存档"的消费者 ⇒ 现在拆是纯增负担（项目原则："引入能消除具体缺陷的模式，而不是凑齐名词"） |
| `checkJs` 全量类型校验进门 | 需要 TS 编译器（项目刻意不引 npm 依赖）；门里保留 `node --check` 语法门，类型检查靠编辑器/手动 `tsc --noEmit` |
