## 2. 本轮三项遗留（都已落地）

### 2.1 数据驱动的修饰器与事件（`Rules/ScenarioOptions.cs` 等 3 个文件）

关卡/剧本现在可以用 **JSON** 描述"什么规则、什么时候"，宿主一行规则代码都不写：

```json
{ "events": [ { "atTick": 2, "name": "忌律生效",
    "modifiers": [ { "kind": "suppress", "operation": "POUR_IN", "from": 2, "to": 3, "reason": "此刻不得灌注" } ] } ] }
```

* `ScenarioOptions`：数据 + **跨字段校验**（`Validate()`）——未知 kind、缺 `to`、`from > to`、
  `suppress` 三要素全空、`retime` 非正、`intensity` 缺参…… 一次性报出；
  **区间必填**：数据里没有"撤销"这个动作，允许无终点会让规则一直挂着；
* `ScenarioJson`：读写 JSON（**核心不碰文件**，与 `WorldOptionsJson` 同一分工），未知键名报错；
* `ScenarioBinder`：数据 → `IRuleModifier` / `IWorldEventSource`（事件在第 N 刻把带区间的修饰器压进栈，
  到期由 `Expire` 自动摘除 —— "临时禁令会自己解除"的数据版）。

**数据侧暂不支持 `Require`**（它的"条件"需要一个世界查询端口），如实写在类注释与校验的 known 列表里。

### 2.2 装饰器表达力升级（在受限输入上重跑）

`ModifierAwareSolver` 新增一类**可精确判定**的规则：**整个形状被禁**（`operation` 为空、`shape` 有值）
⇒ 等价于"该形状的罐子不在池子里"，于是把池子过滤后**重跑**基础求解器即可给出精确结论
（此前这一类只能回"未判定"）。

差分门同步升级为**四类判据**（400 场景 × 4 = **1600 次比对**）：
直通一致 / 液体抑制≡等价禁令世界 / **整形状抑制≡受限池重跑** / 操作级抑制必须回未判定：

```
MODDIFF-OK (scenarios=400, checks=1600, passthrough=1, liquid=1, inexpressible=1, wholeShape=1)
```

`S28` 也随之改写成更准确的形式：同一局面下断言"操作级抑制（不可表达）⇒ 未判定"与
"整形状抑制（可表达）⇒ 精确不可行"**同时成立**。

### 2.3 `Intensity` 的更多消费者：流入参数

`ProductionService.FlushFlow` 对**每次流入**的罐子数与液体量做折算（目标名 `flow:jars` / `flow:liquid`；
无匹配 ⇒ 恒等）。于是强度目标现在有四类：`liquid:酒`、`producer:圆罐`、`flow:jars`、`flow:liquid`。

### 2.4 顺带的一次归位

`IWorldEventSource`/`WorldEvent` 从 `Process/Ports/` 移到 **`Rules/`** —— 它们是"世界里发生的事"，
不是过程基础设施。移动后反向依赖自检仍然全空（`Rules → Process` 空、`Domain → Process` 空）。

## 3. 阶段五开场：宿主侧时间参数（第一片）

阶段五（可选）原定两项：**引擎时间对接**与**世界事件注入编辑器**。本轮落地第一片：

* `TickBackgroundService` 的推进间隔改为**读宿主配置** `JarSystem:TickIntervalMs`（默认 2000 ms，
  下限 100 ms 防呆），并在改动时打一行日志；
* `appsettings.json` 补上该键；
* 数据驱动的场景（§2.1）本身就是"世界事件注入"的数据形态 —— 编辑器只是给这份 JSON 做个界面。

**为什么放在宿主侧**：核心只认逻辑 tick（判定必须与墙钟无关），"多久推进一次"纯属表现层参数。
这条边界是阶段五的设计前提：以后要加"倍速/暂停"也只会动宿主，不会污染判定。
