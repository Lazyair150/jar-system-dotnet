## 1. `Require` 数据化（新增"世界查询"端口）

**问题**：`Require` 的语义是"某条件此刻必须成立"，而条件离不开读世界；数据里不能写代码 ⇒ 之前只能由宿主给谓词。

**解法**：把"读世界"收成一个**只读端口** `Rules/IWorldQuery`：

```csharp
int CountJars(string shape, bool empty);   // 当前主台上某形状的空罐/满罐数
int CountLiquid(string liquid);            // 当前主台的游离液体量
```

* 实现方是**门面** `JarSystem`（按当前主台统计；无主台返回 0 ⇒ 条件不成立，表现为阻断而不是崩溃）；
  宿主也可以提供自己的实现（例如改按从台统计）。
* 数据形态：`{ "kind": "require", "shape": "圆罐", "minEmptyJars": 2, "from": 12, "to": 20, "reason": "…" }`
  （也支持 `minLiquid` + `liquid`）；`ScenarioBinder` 把它绑成谓词，守卫在每个单位前问它一次。
* 校验补齐：`require` 进入 known 列表；"至少写一个下限"、"写了 minEmptyJars 就必须写 shape"等规则
  由 `Validate()` 一次性报出。

## 2. 倍速（表现层时间适配）

* 宿主 `JarSystemService.TickIntervalMs`（默认 2000 ms，下限 100 ms 防呆）；
* `TickBackgroundService` 从 `PeriodicTimer` 改为**每轮读一次间隔**的等待循环
  —— 于是配置与客户端都能随时改节奏；"不重入"由顺序 `await` 保证（与原先等价）；
* 新命令 `setTickInterval`（载荷 `intervalMs`，校验 100~60000）+ 新消息 `tickIntervalChanged`；
* 前端：工具栏加 `⏩ 1×/2×/4×` 循环按钮（基准 2000 ms ⇒ 500/1000/2000），收到回包即刷新文案；
  暂停沿用既有的 `startTick`/`stopTick`（不新增机制）。

**边界**：倍速只改"多久推一次"，**判定永远只认逻辑 tick** ⇒ 加速不会改变任何结论（这也是把它放宿主侧的原因）。

## 3. 场景编辑器（后端 + 校验工具 + 示例）

* **宿主装配**：`config/scenario.json` 存在时加载（与 `world.json` 同一套查找与"校验失败即拒绝启动"口径）；
  初始修饰器由宿主作用域持有，事件源挂到过程系统的管线第 ① 步 ⇒ **改 JSON → 重启 → 世界就有事故与临时规则**；
  文件不存在 ⇒ 行为与今天完全一致（仓库只提供示例，不提供生效文件）。
* **校验工具**（编辑器后端）：
  ```bat
  dotnet run --project test\JarSystem.Test -c Release -- --validate-scenario config\scenario.sample.json
  ```
  实测：`SCENARIO-OK (name=示例场景：忌律与涌流, events=3, initialModifiers=1, warnings=0)`
  （非法数据输出 `SCENARIO-INVALID (n)` + 逐条原因，退出码 1 ⇒ 将来可直接做成门）。
* **示例场景**（`config/scenario.sample.json`）演示三种数据形态：操作级抑制（忌律）、强度折减（井流减半）、
  条件类规则（契约：主台需常备空罐）。

## 5. 阶段五剩余的候选（未做）

1. **场景编辑器界面**：现在有数据格式 + 校验后端 + 示例；缺的是一个真界面（可放在 Web 的模态或独立工具里）。
2. **把场景校验做成门**：`--validate-scenario` 已有退出码，接进 `verify.bat` 时要注意它会把"九步"变成十步
   （或作为第 9 步的子检查）。
3. **`IWorldQuery` 的口径扩展**：目前只查主台；若要表达"从台需备 N 个罐"这类条款，需要按工作台名查询
   （属数据侧设计，改动集中在端口 + 门面实现）。
