# 技能驱动全项目审查与加固

> 日期：2026-10-18
> 触发：用户要求把本轮更新的 Agent Skills 全量用于当前项目构建与审查，并允许在证据支持时做大规模必要性改动。
> 结论：完成一轮“质量契约 → 缺陷复现 → 修复 → 门禁 → 运行时复验 → 文档”的闭环；最终 `VERDICT=OK` + `QUALITY-OK`。

## 1. 任务理解

`SKILL-README.md` 描述的不是“再写一个功能”，而是一套完整生命周期：DEFINE → PLAN → BUILD → VERIFY →
REVIEW → SHIP。它要求把质量线写成可执行契约、用失败测试证明缺陷、用真实运行数据证明修复，并且
不能通过删测试、降阈值、加 suppression 或空实现来让门变绿。

本项目的既有基础很强：九步验证、逐字节契约快照、协议门、求解器差分、修饰器差分、回放门、
32 条确定性用例都已经存在。因此本轮不重造验证体系，而是把这些能力变成**更难被绕过的质量门**，
再处理审查中发现的真实缺陷。

## 2. 工作假设

1. 现有九步门是唯一完整验证回路；新增检查应挂在它里面，避免第二套逻辑漂移。
2. 契约只加不改：不改键名、命令名、消息名、回放格式；如果行为有意变化，必须由快照/回放/报告共同证明。
3. 逻辑 tick 仍是唯一判定时间源；墙钟只允许用于表现层诊断或已知的“分析耗时”字段。
4. 当前是本地 Web 壳 + 核心库，不是公网多租户服务；安全加固以本机边界和可验证输入上限为主。
5. 没有 Chrome DevTools MCP，因此浏览器自动化测试不伪装成已完成；用 HTTP + WebSocket 真实运行时冒烟补足传输层证据。

## 4. 审查发现与修复

| # | 严重度 | 发现 | 证据 | 修复 |
|---|---|---|---|---|
| F1 | Critical | `Reset()` 不清活动/最近过程与过程日志；旧过程可继续引用被移除的工作台/订单 | 新增测试直接断言 Reset 后 Recent 仍非空，红灯 | `Processes.Clear()`；清运行时/时钟/Journal seq；过程 ID 与累计数保持单调 |
| F2 | Critical | 过程收尾只读会话结果，不看最终交付结果 | 虚假 completion 返回失败时会话仍让 `Succeeded=true`，红灯 | `OrderProcessAdvancer` 收尾后以 `Result.Success/Reason` 为准 |
| F3 | High | 22 条聚焦 xUnit 不在 solution、不在九步门 | `dotnet test` 与解决方案构建都不覆盖它 | 加入 `JarSystem.slnx`，第 2 步执行，`quality-gate` 要求 ≥22 |
| F4 | High | 直接运行 DLL 时 ContentRoot=仓库根，`wwwroot` 找不到；同时 appsettings 未加载 | 运行时日志 `WebRootPath was not found`，`/` 404 | 显式解析 WebRoot；ContentRoot 指向输出目录 |
| F5 | High | 场景编辑 POST 无请求体上限，可把任意大文本读进内存 | 代码审查；无 `ContentLength` 限制 | 1 MiB 上限，chunked 也按累计字节拒绝（413） |
| F6 | High | `AllowedHosts` 配置存在但没有生效；Host 头仍可伪造 | `curl -H "Host: evil.example"` 返回 200 | 显式 Host 允许集；非法 Host 返回 400，保留 Origin 403 |
| F7 | High | WebSocket 初始 `init` 快照不经过串行闸门，可能和后台 Tick 并发枚举世界 | 代码审查 | 初始快照在同一 `Gate` 内生成 |
| F8 | Medium | 数据侧 intensity 负值/超大值可导致负产出或 int 溢出；负窗口被静默当作 0 | 新增测试得到 `-760209212`（溢出）与零错误校验结果 | `factorPerMille` 0~100000；`ApplyIntensity` 饱和到 `[0,int.MaxValue]` |
| F9 | Medium | `WorldQuery.WhatValues/OpValues` 是 public 可变数组 | 新增测试尝试改写成功 | 改为只读 `IReadOnlyList`（`Array.AsReadOnly`） |
| F10 | Medium | 审批基线缺失时会自动写回，删除基线也能“自愈”为绿 | 代码审查 | 缺失即失败，要求从版本控制恢复 |
| F11 | Medium | WebSocket 收尾空 catch 静默吞异常 | 全仓模式扫描 | 改为记录 `[ws] 关闭失败` |
| F12 | Low | 过程系统 README 的基线数字停留在旧版本（22/10 类型/223 行等） | `CheckDocs` 与 README 对照 | 更新为 32/11 类型/225 行/22 xUnit/QUALITY-OK |
| F13 | Medium | Reset 后 ModifierStack 的窗口时钟仍停在旧 tick，旧修饰器会按旧时间线继续生效 | 代码审查；新增 `ResetClock_ReanchorsModifierWindows` | `ProcessSystem.Clear()` 同步把修饰器窗口时钟归零 |

### 未改的已知问题

1. `state.eventHistory` 仍是弱类型 `List<Dictionary<string, object?>>`，是 schema 唯一的 `loose=1`。
   收紧它需要封闭事件联合类型并迁移契约，不应顺手做。
2. `feasibilityResult.timestamp` 是墙钟分析耗时，回放门必须把它规范化为 `<volatile>`。
   它不是判定输入，但确实不是逐字节确定字段；改名需要新的契约键迁移。
3. 场景热重载仍是“保存后重启”，没有引入运行中换规则。
4. 未启用 .NET 全量推荐分析器：实测有 42 条既有命名/文化/风格问题；本轮坚持编译器警告即错误，
   并把结构性质量门落地，没有为了分析器绿灯做大规模改名。

## 5. 新增与修改的关键结构

| 文件 | 作用 |
|---|---|
| `CONSTRAINTS.md` | 项目质量契约：floor、数字门、例外、变更纪律 |
| `AGENTS.md` | 告诉后续 agent 先读质量契约、只认唯一验证回路 |
| `重构报告/quality-gate.ps1` | 扫描 suppression/stub/空 catch/跳过测试/核心外部包，并核对证据计数 |
| `Directory.Build.props` | 编译器警告即错误、确定性构建、CI 构建设置 |
| `global.json` | 固定 .NET 主/次版本，允许最新 feature band |
| `test/JarSystem.Tests/*` | 聚焦回归：过程生命周期、收尾一致性、场景边界、词表只读、审批基线 |
| `docs/decisions/0001-*.md` | 记录本轮关键架构裁决与替代方案 |

Godot 宿主也纳入了 Release 构建子步骤。审查时曾因全局 `ImplicitUsings` 引入
`System.IO.FileAccess` / `Godot.FileAccess` 冲突，已改为“各项目自管 using”，并复验 Godot 构建为 0 警告/0 错误。

九步门结构保持不变：第 1 步改为 Release 全量构建，第 2 步内增加 xUnit 子步骤，末尾增加质量地板。
这样既没有复制验证逻辑，也没有把“文档里的九步”改成第二套编号。

### 6.2 质量门本身的有效性

临时加入 `quality-probe.cs`（内容为 `// TODO: ...`），质量门输出：


## 7. 结论

本轮没有把项目改造成另一个系统，也没有为了“技能全量使用”堆入无关依赖。实际完成的是：

- 把质量线从隐含经验变成可执行契约；
- 把原本游离的聚焦测试纳入 Release 门；
- 修掉过程生命周期和收尾一致性的两个承重缺陷；
- 修掉直接运行 DLL 的静态资源/配置加载缺陷；
- 给 Web 边界补上可验证的 Host/Origin/大小限制；
- 用真实 HTTP/WebSocket 运行数据，而不是“看起来正确”，证明修复有效。

当前过程系统可以继续作为更大的游戏世界中的确定性规则内核使用。下一阶段若要继续提升“玩家可玩性”，
应另立规格处理“玩家可决策参数、订单目标生成、工作台成长、过程可视化反馈”，而不是继续在核心里堆内部机制。

## 8. 提交拆分建议

用户尚未要求自动提交；建议按以下原子提交拆分：

1. `chore: establish quality constraints and unified verification floor`
2. `fix(process): reset runtime lifecycle and honor completion outcome`
3. `fix(web): resolve web root and harden request boundaries`
4. `test: add focused regressions and wire xUnit into the gate`
5. `docs: record skill-driven audit and architecture decisions`
