## 2. 已做的修正与其证据

* **A4（热路径）**：`ModifierStack` 新增 `IsEmpty`；`SuppressionReason`/`TicksPerStepOverride` 在空栈时直接返回；
  `GrantedShapes()` 改为**按 revision 失效的缓存**（`Push`/`Remove`/`Expire` 都会 `_revision++`）；
  `RuleContext.IsAdditionalMarked` 在空栈时直接返回 false。**等价性**：空栈行为不变（门全绿），只是不再分配。
* **A5（归位）**：`IProcessAdvancer.cs` / `GuardResult.cs` / `IWorldEventSource.cs` → `Process/Ports/`（同命名空间，
  纯文件移动；`Execution/` 现在只剩 `OrderExecutionSession` + `OrderProcessAdvancer` 两个"订单专用"件）。
* **第四条：带修饰器的差分门**（§4）。

## 3. 记录在案但本轮未改的三项（附方案与理由）

**为什么不改**：A1–A3 都是**同一个程序集内的边界改名/接口抽离**，运行时零影响，收益是概念清晰；
而代价是每个都要动 6–10 个文件并重跑全部门。本项目已有先例把这类问题**记录而非立即修**
（`UML/07` 的 note 明说："Abstractions 与 Solver/Orders 互相引用 …… 同程序集内成环，编译无碍，但接口并不是零依赖的"）。
在**同一回合已经上线多个机制**的前提下，我选择先留下方案、把它作为一次**独立的边界重构**来做（门就是安全网）。

| # | 方案（下次一次做完） | 触及面 |
|---|---|---|
| A1 | 建 `src/JarSystem.Core/Rules/`（命名空间 `JarSystem.Core.Rules`），把 `RuleContext`/`IRuleModifier`/`ModifierStack`/`ModifierAwareSolver` 搬过去 ⇒ 依赖变成 `Domain → Rules ← Process`（单向两侧） | 4 个文件搬移 + `Workshop`/`ProcessSystem`/`TickPipeline`/`JarSystem`/测试 5 处 using |
| A2 | 在 `Process/Ports/` 定义 `IOrderExecutionCompletion`（方法 `Complete(OrderExecutionSession)`），由 `OrderService` 实现；`OrderProcessAdvancer` 只依赖这个端口 | 3 处（端口新文件 + Service 实现 + 门面接线） |
| A3 | 把会话需要的两个执行原语（`ApplyPlannedStep` / `RunGreedyStage`）抽到 `Abstractions`（例 `IProcessStepPrimitives`，返回中性形状而非 Executor 内部类型），由 `OrderExecutor` 实现 —— **项目已有先例**：`ISolver` 正是这样把"可行性 ↔ 求解器"解开的 | 4 处（接口新文件 + Executor 实现 + 会话字段类型 + 返中性化） |

## 4. 第四条已落地：**修饰器差分门**（`--check-solver` 的修饰器段）

判据三条，正好对应 `ModifierAwareSolver` 的三条 sound 语义：

| # | 判据 | 实现 |
|---|---|---|
| ① | **无修饰器 ⇒ 直通**：装饰器结果与基础求解器一致（可行性与路径长度都要一致） | 每个场景跑两遍比对 |
| ② | **可表达的规则 ⇒ 等价改写**：抑制某种液体，必须与"把该液体写进禁令表"的等价基础世界**判定一致** | 每个场景构造"等效禁令世界"比对 |
| ③ | **不可表达的规则 ⇒ 未判定**：抑制某个形状时，必须 `Feasible=false && BudgetExceeded && InconclusiveReason!=null`，**绝不能自称"不可行"** | 断言三件事同时成立 |

实测（400 场景 × 3 判据 = 1200 次比对）：

```
MODDIFF-OK (scenarios=400, checks=1200, passthrough=1, expressible=1, inexpressible=1)
```

它现在是**硬门的一部分**：`verify.bat` 的 VERDICT 列表加了 `MODDIFF-MISMATCH ⇒ FAIL`，
KEY LINES 也回显该标记（否则它只躺在日志里、人看不到）。

## 6. 更好但更大的解法（供决策，不擅自做）

1. **`ProcessSchedule` 值对象**（A9）：把 `TicksPerStep`/`NextUnitTick`/`BlockedAtTick`/宽限收成一个不可变值 + 一个纯函数 `Advance(schedule, tick) ⇒ (schedule', units)`。
   好处：调度变成**纯函数**（可单测、可存档）；代价：现在这三处状态都在 `ProcessInstance` 上，属"能用但不优雅"。
2. **过程可存档/可迁移**（A10）：拆分"阶段机状态"与"结果"，让过程可序列化 ⇒ 支持"存读档时正在执行中的订单"。
   这是 P5 若做"关卡/存档"的前置。
3. **事件与修饰器的数据驱动**：现在由宿主代码构造（含 `Require` 的谓词）；要做成关卡 JSON →
   修饰器/事件，需要一个小条件语言（`Require` 的谓词是唯一挡路的东西）。
